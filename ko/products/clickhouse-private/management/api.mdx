<div id="starting-with-the-clickhouse-private-api">
  #### ClickHouse Private API 시작하기
</div>

ClickHouse Private API는 백업 생성이나 수직 스케일링과 같이 ClickHouse 클러스터를 관리할 때 자주 필요한 작업을 지원합니다.

관리 작업을 간소화하기 위해 환경에 추가할 수 있는 별도의 선택적 구성 요소입니다.

<div id="installation">
  #### 설치
</div>

ClickHouse Private API는 Docker image와 Helm 차트 형태로 제공되며, 이를 프라이빗 ECR 리포지토리에 복사한 뒤 EKS 클러스터에 설치해야 합니다.

<div id="prerequisites">
  ##### 사전 요구 사항
</div>

* ClickHouse Operator가 설치되어 있어야 합니다([Install Operator via Helm](/ko/products/clickhouse-private/deployment/aws#install-operator-via-helm) 참조)
* 최소 1개의 ClickHouse 클러스터가 배포되어 있어야 합니다([ClickHouseCluster CR](/ko/products/clickhouse-private/deployment/aws#clickhousecluster-cr) 참조)
* ClickHouse 프라이빗 ECR 리포지토리에 대한 접근 권한이 있어야 합니다
* AWS 계정에 대상 ECR 리포지토리가 생성되어 있어야 합니다:
  * `airgap-management`
  * `helm/airgap-management`

<div id="copy-ecr-artifacts-for-private-api">
  ##### Private API용 ECR 아티팩트 복사
</div>

**이미지 복사에는 [skopeo](https://github.com/containers/skopeo) 사용을 강력히 권장합니다.** 이렇게 하면 Docker 이미지에 포함된 모든 아키텍처가 그대로 유지됩니다. 아래의 `TARGET_REGION` 및 `TARGET_ECR_REPO`를 ECR 리전과 호스트에 맞게 설정하십시오.

```bash
SOURCE_REGION=us-east-1
SOURCE_ECR_REPO=349290138304.dkr.ecr.$SOURCE_REGION.amazonaws.com

TARGET_REGION=us-west-2
TARGET_ECR_REPO=0000000000.dkr.ecr.$TARGET_REGION.amazonaws.com

# 당사 ECR에 로그인
aws ecr get-login-password --region $SOURCE_REGION | skopeo login --username AWS --password-stdin $SOURCE_ECR_REPO

# 대상 AWS 리포지토리에 로그인
aws ecr get-login-password --region $TARGET_REGION | skopeo login --username AWS --password-stdin $TARGET_ECR_REPO

# 각 이미지를 대상 ECR에 복사 (--all 플래그를 반드시 포함할 것)
skopeo copy --all docker://$SOURCE_ECR_REPO/airgap-management:<<API_TAG>> docker://$TARGET_ECR_REPO/airgap-management:<<API_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/airgap-management:<<API_HELM_TAG>> docker://$TARGET_ECR_REPO/helm/airgap-management:<<API_HELM_TAG>>
```

<div id="install-private-api-via-helm">
  ##### Helm을 사용한 Private API 설치
</div>

Private API는 전용 네임스페이스에 설치해야 합니다. 필요에 따라 ECR 호스트, 버전 태그, 인증 설정을 업데이트하십시오.

```bash
# 필요에 따라 ECR_HOST를 업데이트하세요
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com

# API의 Helm 차트 버전을 사용해야 합니다
API_HELM_VERSION=<<API_HELM_TAG>>

# API 이미지 태그를 설정하세요
API_IMAGE_TAG=<<API_TAG>>

helm install clickhouse-private-api \
   oci://$ECR_HOST/helm/airgap-management \
   --version=$API_HELM_VERSION \
   --create-namespace \
   -n clickhouse-private-api \
   --set-json="image.repository=\"$ECR_HOST/airgap-management\"" \
   --set-json="image.tag=\"$API_IMAGE_TAG\""
```

**인증 관련 참고 사항:**

* 기본적으로 기본 인증은 비활성화되어 있습니다. 프로덕션 환경에서는 `api.basicAuth.enabled=true`로 설정하고 안전한 자격 증명을 지정하여 기본 인증을 활성화할 수 있습니다.
* 사용자 이름과 비밀번호는 안전하게 저장하고, 조직의 보안 정책에 따라 정기적으로 변경해야 합니다.

<div id="verify-installation">
  ##### 설치 확인
</div>

Private API 파드가 실행 중인지 확인하십시오:

```bash
kubectl get pods -n clickhouse-private-api
```

다음과 비슷한 출력이 표시됩니다:

```
NAME                                    READY   STATUS    RESTARTS   AGE
clickhouse-private-api-xxxxxxxxxx-xxxxx   1/1     Running   0          1m
```

서비스를 포트 포워딩하여 API에 액세스할 수 있는지 확인하십시오:

```bash
kubectl port-forward svc/clickhouse-private-api-airgap-management 8080:8080 -n clickhouse-private-api
```

API 상태 확인 엔드포인트를 테스트합니다:

```bash
curl http://localhost:8080/readiness
```

인증이 활성화되어 있으면 자격 증명을 포함하십시오:

```bash
curl -u admin:YOUR_SECURE_PASSWORD_HERE http://localhost:8080/readiness
```

<div id="configuration-options">
  ##### 구성 옵션
</div>

다음 주요 구성 옵션은 Helm 값에서 설정할 수 있습니다:

* `image.repository`: Private API 이미지용 ECR 리포지토리
* `image.tag`: 배포할 이미지 태그
* `api.port`: API가 수신 대기하는 포트(기본값: 8080)
* `api.basicAuth.enabled`: HTTP 기본 인증 사용 여부(기본값: false)
* `api.basicAuth.username`: 기본 인증용 사용자 이름(기본값: &quot;admin&quot;)
* `api.basicAuth.password`: 기본 인증용 비밀번호(기본값: &quot;changeme&quot;)
* `serviceAccount.enabled`: API용 서비스 계정 생성(기본값: true)
* `serviceAccount.annotations`: 서비스 계정용 어노테이션(예: IRSA)

전체 구성 옵션 목록은 Helm 차트의 `README.md`를 참조하십시오.

<div id="tutorial-managing-backups-through-the-api">
  #### 튜토리얼: API를 통한 백업 관리
</div>

ClickHouse Private API는 백업 관리를 간소화할 수 있도록 지원합니다. `api/v1/backups` REST 리소스를 사용하면 배포된 ClickHouse 클러스터의
백업과 상호작용할 수 있습니다.

이 가이드에서는 Kubernetes 파드를 포트 포워딩하여 `http://localhost:8080/`을 통해 API에 접근할 수 있다고 가정합니다. 예를 들어 [curl](https://curl.se/)을 사용해 API와 상호작용하고 HTTP 요청을 보냅니다. 또한 default-xx-01이라는 이름의 ClickHouse 클러스터가 배포되어 있다고 가정합니다(ClickHouse 클러스터 배포 방법에 대한 자세한 내용은 [설정 가이드](/ko/products/clickhouse-private/deployment/aws)를 참조하십시오).

먼저 백업을 생성하겠습니다. 다음과 같이 전체 백업을 생성하십시오:

backup.json

```json
{
    "incremental": false
}
```

cURL 명령

```sh
curl -X POST "http://localhost:8080/api/v1/backups?instance_id=default-xx-01" \
    -H "Content-Type: application/json" \
    --data-binary "@backup.json"
```

백업을 생성할 ClickHouse 클러스터를 지정하려면 `instance_id` 쿼리 매개변수를 사용합니다. 이 값에는 배포 시 사용한 ClickHouse 클러스터 이름을 지정합니다.

이렇게 하면 본문의 `incremental` 필드에 지정된 증분 백업이 아니라 전체 백업이 생성됩니다. 또한 `backupObject`를 사용해 백업할 테이블이나 데이터베이스를 지정할 수 있습니다. 이 경우 `type`으로 Common을 사용하며, 이는 모든 테이블과 데이터베이스를 의미합니다.

응답에는 생성된 백업에 대한 정보가 포함되며, 여기에는 백업을 참조할 때 사용할 수 있는 UUID도 포함됩니다.

내부적으로 API는 ClickHouse 클러스터의 네임스페이스 안에 `Backup` 객체를 생성합니다.
ClickHouse Operator는 ClickHouse 클러스터 네임스페이스의 `Backup`을 감시하고, 새 `Backup` 객체가 생성되면 클러스터에서 관련 Backup SQL statement를 실행한 뒤 상태를 모니터링합니다(`system tables` 사용).

이 백업의 UUID는 API를 통해 백업 상태를 모니터링하는 데 사용할 수 있습니다:

```sh
curl "http://localhost:8080/api/v1/backups/{uuid}?instance_id=default-xx-01
```

이렇게 하면 백업 객체가 반환되며, `status` 필드를 통해 백업 정보를 확인할 수 있습니다. 백업이 성공적으로 완료되면 `state` 필드의 값은 `Ready`가 됩니다.

또한 다음과 같이 생성된 모든 백업을 모니터링할 수도 있습니다:

```sh
curl "http://localhost:8080/api/v1/backups?instance_id=default-xx-01"
```

<div id="tutorial-vertically-scaling-clickhouse-clusters-through-the-api">
  #### 튜토리얼: API를 통해 ClickHouse 클러스터를 수직 스케일링하기
</div>

ClickHouse Private API는 CPU 및 메모리 리소스를 조정해 ClickHouse 클러스터를 수직 스케일링할 수 있도록 지원합니다. `api/v1/instances/{instance_id}/scale` REST 리소스를 사용하면 배포된 ClickHouse 클러스터의 리소스 할당을 변경할 수 있습니다.

이 가이드에서는 `http://localhost:8080/`을 통해 API에 접근할 수 있다고 가정합니다. 예를 들어 Kubernetes 파드에 포트 포워딩을 설정하면 됩니다. API를 호출하고 HTTP 요청을 보내기 위해 [curl](https://curl.se/)을 사용합니다. 또한 default-xx-01이라는 이름의 ClickHouse 클러스터가 이미 배포되어 있다고 가정합니다(ClickHouse 클러스터 배포 방법에 대한 자세한 내용은 [설정 가이드](/ko/products/clickhouse-private/deployment/aws)를 참조하십시오).

리소스를 조정해 클러스터를 스케일링해 보겠습니다. 다음과 같이 스케일 요청을 생성합니다.

scale.json

```json
{
  "vertical": {
    "resources": {
        "cpu": "4",
        "memory": "16Gi"
    }
  }
}
```

cURL 명령어

```sh
curl -X POST "http://localhost:8080/api/v1/instances/default-xx-01/scale" \
    -H "Content-Type: application/json" \
    --data-binary "@scale.json"
```

스케일링할 ClickHouse 클러스터를 지정하려면 `instance_id` 경로 매개변수를 사용합니다. 이 값에는 배포 시 사용한 ClickHouse 클러스터 이름이 들어갑니다.

`resources` 필드는 클러스터에 할당할 CPU와 메모리를 지정합니다. CPU와 메모리는 모두 Kubernetes 리소스 수량 포맷을 사용해 지정합니다(예: CPU 코어 4개는 &quot;4&quot;, 메모리 16GiB는 &quot;16Gi&quot;).

**중요**: API는 1:4 CPU 대 메모리 비율(메모리 4GiB당 CPU 코어 1개)을 5% 오차 범위 내에서 강제합니다. 리소스 유형 하나만 제공하면 API가 이 비율을 유지하도록 나머지 리소스를 자동으로 계산합니다. 예를 들어 `"memory": "16Gi"`만 지정하면 CPU는 자동으로 4코어로 설정됩니다.

ClickHouse는 리소스를 추가할수록 뛰어난 확장성을 보이며, 일반적으로 스케일 아웃(수평 스케일링)을 고려하기 전에 먼저 ClickHouse를 스케일 업하는 것이 좋습니다. ClickHouse는 사용 가능한 모든 코어를 활용해 쿼리 성능을 향상합니다.

내부적으로 API는 Kubernetes의 `ClickhouseCluster` 사용자 지정 리소스(custom resource)에 있는 `ServerPodPolicy`를 업데이트합니다. ClickHouse Operator는 이 변경을 감지하고, 새 리소스 할당을 적용하기 위해 ClickHouse 서버를 관리하는 Stateful Set의 롤링 재시작을 트리거합니다.

**중요**: ClickHouse Cloud와 달리 ClickHouse Private의 수직 스케일링 기능은 [Make Before Break (MBB) scaling](/ko/products/cloud/features/autoscaling/overview#how-scaling-works-in-clickhouse-cloud)을 사용하지 않습니다. 즉, ClickHouse 서버를 관리하는 StatefulSets에 롤링 재시작이 적용되므로 수직 스케일링 중 서비스 중단이 발생할 수 있습니다.

<div id="tutorial-resetting-the-main-clickhouse-user-password">
  #### 튜토리얼: 기본 ClickHouse 사용자 비밀번호 재설정
</div>

ClickHouse Private API는 ClickHouse 클러스터 사용자의 비밀번호를 재설정하는 기능을 제공합니다. `api/v1/instances/{instance_id}/reset-user-password` 엔드포인트를 사용하면 배포된 ClickHouse 클러스터에서 사용자 자격 증명을 업데이트할 수 있습니다.

이 가이드에서는 `http://localhost:8080/`을 통해 API에 접근할 수 있다고 가정합니다. 예를 들어 Kubernetes 파드에 포트 포워딩을 설정하면 됩니다. API와 상호 작용하고 HTTP 요청을 보내기 위해 [curl](https://curl.se/)을 사용합니다. 또한 `default-xx-01`이라는 이름의 ClickHouse 클러스터가 배포되어 있다고 가정합니다(ClickHouse 클러스터 배포 방법에 대한 자세한 내용은 [설정 가이드](/ko/products/clickhouse-private/deployment/aws)를 참조하십시오).

**중요**: Hydra 하위 인스턴스에서는 비밀번호를 재설정할 수 없습니다. Hydra 하위 인스턴스의 비밀번호를 재설정해야 하는 경우에는 대신 상위 인스턴스에서 재설정해야 합니다.

비밀번호를 재설정하기 전에 해시된 비밀번호를 생성해야 합니다. API에서는 비밀번호를 SHA-256(또는 다른 지원 해시 함수)으로 해시한 후 base64로 인코딩해야 합니다. 해시된 비밀번호는 다음과 같이 생성하십시오:

```sh
# 사용자의 새 비밀번호로 사용될 값입니다
PASSWORD='My super secret p@$$w0rd'
HASHED_PASSWORD=$(echo -n $PASSWORD | shasum -a 256 | awk '{printf $1}' | base64)
```

이제 비밀번호 재설정 요청을 생성하세요. 요청 본문에는 해시된 비밀번호를 포함해야 합니다:

password&#95;reset.json

```json
{
  "user_hashed_password": "<base64-encoded-sha256-hash>",
  "hashing_function": "sha256",
  "username": "default"
}
```

필드는 다음과 같습니다:

* `user_hashed_password` (필수): 새 비밀번호의 base64로 인코딩된 hash
* `hashing_function` (선택 사항): 사용할 해싱 알고리즘입니다. 지정하지 않으면 기본값은 `"sha256"`입니다
* `username` (선택 사항): 비밀번호를 재설정할 사용자 이름입니다. 지정하지 않으면 기본값은 `"default"`입니다

CURL 명령:

```sh
curl -X POST "http://localhost:8080/api/v1/instances/default-xx-01/reset-user-password" \
    -H "Content-Type: application/json" \
    --data-binary "@password_reset.json"
```

비밀번호를 재설정할 ClickHouse 클러스터를 지정하려면 `instance_id` 경로 매개변수를 사용합니다. 이 값에는 배포 시 사용한 ClickHouse 클러스터 이름을 지정합니다.

요청이 성공하면 다음과 같은 응답을 받습니다:

```json
{
  "message": "User password reset successfully"
}
```

내부적으로 API는 Kubernetes의 `ClickhouseCluster` 사용자 지정 리소스에 있는 `CustomerAccount` 필드를 업데이트합니다. 그러면 ClickHouse Operator가 이 변경 사항을 감지하고 ClickHouse 클러스터의 사용자 자격 증명을 그에 맞게 업데이트합니다.

**참고**: 비밀번호 재설정은 ClickHouse Operator가 변경 사항을 처리한 후 적용됩니다. 새 비밀번호로 클러스터 연결을 시도해 비밀번호가 업데이트되었는지 확인할 수 있습니다.

<div id="how-to">
  ### 사용 가이드
</div>

<div id="how-to-check-the-current-state-of-a-clickhouse-cluster-and-monitor-state-transitions">
  #### 방법: ClickHouse 클러스터의 현재 상태를 확인하고 상태 전환을 모니터링합니다.
</div>

ClickHouse Private API는 지정된 ClickHouse 클러스터의 현재 상태를 확인할 수 있는 엔드포인트 `http://{api_base_url}/api/v1/instances/{instance_id}/status`를 제공합니다.

`status` 엔드포인트는 다음 필드를 포함한 JSON을 반환합니다.

* `state`: ClickHouse 클러스터의 현재 상태입니다.
* `previousState`: ClickHouse 클러스터가 전환되기 전의 상태입니다.
* `message`: 상태 전환과 관련된 메시지입니다. 여기에는 클러스터가 해당 상태로 전환된 이유에 대한 세부 정보가 포함됩니다.
* `stateProvidedBy`: 상태 전환을 유발한 프로세스입니다.

이 엔드포인트는 여러 상황에서 유용하게 사용할 수 있습니다. 예를 들면 다음과 같습니다.

* API를 통해 vertical scaling 작업을 시작한 뒤, 연산자가 스케일링 작업을 완료했는지 확인하려는 경우
* 사용자 비밀번호를 재설정한 뒤, API가 변경 사항을 클러스터 전체에 적용했는지 확인하려는 경우

<div id="how-to-incremental-backups">
  #### 방법: 증분 백업
</div>

증분 백업은 마지막 백업 이후 변경된 데이터만 백업하는 데 사용할 수 있습니다. 이렇게 하면 전체적으로 필요한 저장소 용량을 줄일 수

증분 백업은 항상 백업 체인 형태로 생성되며, 각 백업은 직전 백업을 참조하고 전체 백업이 시작점이 됩니다.

이전에 백업을 이미 생성했다고 가정하면 다음과 같이 만들 수 있습니다:

```json
{
    "incremental": true,
    "baseBackupUuid": <uuid of previous backup>
}
```

```sh
curl -X POST "http://localhost:8080/api/v1/backups?instance_id=default-xx-01" \
    -H "Content-Type: application/json" \
    --data-binary "@backup.json"
```

마지막으로 성공한 백업을 찾고 UUID를 확인하려면, List backups API(`http://localhost:8080/api/v1/backups`)에서 마지막으로 성공한 백업을 찾기 위한 쿼리 매개변수를 지원합니다: `http://localhost:8080/api/v1/backups?instance_id=default-xx-01&status__state__eq=Ready&sort=status__effictiveFinishTime&limit=1 | jq -r '.[].id'`.

<div id="how-to-scheduling-backups">
  #### 방법: 백업 예약하기
</div>

Kubernetes CronJob을 사용하면 백업을 간단하게 예약할 수 있습니다:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: clickhouse-daily-backup
  namespace: clickhouse-private-api
spec:
  schedule: "0 2 * * *"  # 매일 오전 2시에 실행
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: curlimages/curl:latest
            command:
            - /bin/sh
            - -c
            - |
              curl -X POST "http://clickhouse-private-api-airgap-management:8080/api/v1/backups?instance_id=default-xx-01" \
                -H "Content-Type: application/json" \
                -d '{
                  "incremental": false
                }'
          restartPolicy: OnFailure
```

위의 CronJob은 매일 오전 2시에 전체 백업이 수행되도록 예약합니다. Private API에 `http://clickhouse-private-api-airgap-management:8080`으로 연결할 수 있다고 가정합니다.

<div id="how-to-backing-up-only-specific-tables-or-databases">
  #### 사용 가이드: 특정 테이블 또는 데이터베이스만 백업하기
</div>

어떤 테이블과 데이터베이스를 백업할지 지정할 수 있습니다. 이는 요청 본문의 `databases` 및 `tables`
필드로 제어합니다.

`tables` 필드에는 정규화된 전체 테이블 이름(예: `db.table`)을 지정해야 합니다.

특정 데이터베이스와 테이블만 포함된 백업을 생성하려면 다음 요청을 사용하십시오:

```json
{
    "incremental": false,
    "databases": ["mydb"],
    "tables": ["mydb2.table"]
}
```

```sh
curl -X POST "http://localhost:8080/api/v1/backups?instance_id=default-xx-01" \
    -H "Content-Type: application/json" \
    --data-binary "@backup.json"
```

<div id="how-to-restoring-backups">
  #### 사용 가이드: 백업 복원
</div>

백업을 복원할 때는 원래 클러스터의 과부하를 방지하기 위해 새 ClickHouse 클러스터를 생성하고([ClickhouseCluster 리소스 생성 단계](/ko/products/clickhouse-private/deployment/aws#clickhousecluster-cr) 참고) 해당 새 클러스터로 복원하는 것을 권장합니다.

API는 대상 인스턴스에서 지정된 백업의 복원을 트리거하는 엔드포인트 `api/v1/backups/<uuid>/restore?instance_id=default-xx-01&target_instance_id=default-xx-02`를 제공합니다. 그러면 대상 인스턴스에서 해당 백업에 대해 `RESTORE ALL`이 수행됩니다.

안전상의 이유로 이 API는 동일한 인스턴스로의 복원을 허용하지 않습니다.

또는 백업을 수동으로 복원할 수도 있으며, 이 경우 복원할 대상을 더 세밀하게 제어할 수 있습니다. 예를 들어 데이터베이스 `example`의 경우 다음 SQL 문을 실행할 수 있습니다:

```sql
RESTORE DATABASE example
AS example_restored
FROM S3('https://<bucket_name>.s3.amazonaws.com/backups/<uuid>')
```

지정된 uuid의 백업에서 데이터베이스 `example`을 `example_restored`라는 새 데이터베이스로 복원합니다.

<div id="how-to-manage-the-lifecycle-of-backups-on-s3">
  #### 사용 가이드: S3에서 백업 수명 주기 관리
</div>

백업 수명 주기를 관리할 때는 몇 가지 고려할 사항이 있습니다.

* 백업을 얼마나 오래 보관할 계획입니까? 예를 들어, 컴플라이언스 요구 사항 때문에 과거 백업을 유지해야 합니까? 스토리지에 어느 정도 비용을 지불할 수 있습니까?
* 증분 백업을 생성한 경우에는 전체 백업 체인을 모두 사용할 수 있어야 합니다.

일반적으로 S3에서 수명 주기를 관리하는 방법은 두 가지입니다.

* S3 수명 주기 기능 사용
* 예를 들어 cronjob을 사용해 Backup을 수동으로 삭제

아래에서 S3 수명 주기 정책 예시를 확인할 수 있습니다.

```json
{
  "Rules": [
    {
      "ID": "ClickHouseBackupLifecycle",
      "Prefix": "backups/",
      "Status": "Enabled",
      "Transitions": [
        { "Days": 7, "StorageClass": "STANDARD_IA" },
        { "Days": 30, "StorageClass": "GLACIER_IR" }
      ],
      "Expiration": { "Days": 90 }
    }
  ]
}
```

이 백업은 7일이 지난 모든 백업을 더 낮은 S3 스토리지 계층(Intelligent Archive)으로 이동하고, 30일 후에는 Glacier로 이동합니다. 90일이 지나면 백업이 삭제됩니다.

S3 수명 주기 정책은 백업 체인의 일부인 백업을 추적할 수 없습니다. 예를 들어 위 예시에서 7일 후 백업을 삭제하고 전체
백업을 14일마다 한 번만 수행했다면, 백업 체인이 끊어지게 되고 이로 인해 백업을 정상적으로 사용할 수 없게 됩니다.

따라서 백업의 수명 주기 관리를 구현하는 방식을 선택할 때는 주의해야 하며, 백업을 복원할 수 있는지 정기적으로 테스트하는 것이 좋습니다.

<div id="how-to-understanding-resource-quantity-formats">
  #### 사용 방법: 리소스 수량 포맷 이해하기
</div>

API는 CPU 및 메모리에 Kubernetes 리소스 수량 포맷을 허용합니다.

**CPU 수량:**

* 정수 값: `"4"` (CPU 코어 4개)
* 소수 값: `"2.5"` (CPU 코어 2.5개)
* 밀리코어: `"500m"` (CPU 코어 0.5개)

**메모리 수량:**

* 바이너리 단위: `"16Gi"` (16기비바이트), `"4096Mi"` (4096메비바이트)
* 십진 단위: `"16G"` (16기가바이트), `"16000M"` (16000메가바이트)

메모리에는 Kubernetes 관례에 맞도록 바이너리 단위(Ki, Mi, Gi)를 사용하는 것이 권장됩니다.
