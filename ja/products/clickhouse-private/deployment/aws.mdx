* 独自のECRでアーティファクトのコピーをホストするためのECRリポジトリを作成します。このガイドでは、以下の名前をECRリポジトリ名として使用することを前提としています。各アーティファクトには、指定されたタグを使用してください。
* [当社のECRからご利用のECRリポジトリにECRアーティファクトをコピーする](#copy-ecr-artifacts)
* [VPC を作成する](#example-vpc-configuration)
* [EKS クラスターを作成する](#creating-eks-cluster)
  * 以下のコンポーネントが必要です:
    * 使用する CNI (ipv4 必須) 。例: [Amazon VPC CNI](https://github.com/aws/amazon-vpc-cni-k8s)
      * Amazon VPC CNI を使用する場合は、IRSA の使用を推奨します。次のガイドの ipv4 の手順に従ってください: [https://docs.aws.amazon.com/eks/latest/userguide/cni-iam-role.html](https://docs.aws.amazon.com/eks/latest/userguide/cni-iam-role.html)
    * EBS CSI Driver。例: [aws-ebs-csi-driver](#install-aws-ebs-csi-driver)
    * DNS。例: CoreDNS
    * 推奨: オートスケーリング。[cluster autoscaler](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/cloudprovider/aws/README.md) などのコンポーネントが必要になる場合があります
  * 事前に作成した VPC に関連付けます
  * ノードグループ
    * **すべてのノードで認証のために [IMDS](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instancedata-data-retrieval.html) が必要です**
    * keeper および server のノードグループでは、AZ をまたいで cluster autoscaler をサポートする場合、[こちら](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/FAQ.md#i-have-a-couple-of-pending-pods-but-there-was-no-scale-up) の推奨どおり **AZ ごとに 1 つのノードグループを作成してください**。そうしない場合は、適切な AZ サブネットを指定して単一のノードグループとして作成できます
    * Keeper ノードグループ
      * AMI イメージ:
        * x86: AL2023&#95;x86&#95;64
        * arm64: AL2023&#95;ARM&#95;64
      * ディスクサイズ: 20gb
      * オートスケーリングを使用しない場合、最小ノード数と希望ノード数は ClickHouse クラスターごとに 3 にする必要があります
      * 推奨インスタンスタイプ: `m7g.2xlarge`
      * Kubernetes ラベル
        * x86: `clickhouseGroup: keeper`
        * arm64: `clickhouseGroup: keeper-arm64`
      * Kubernetes taints
        * `clickhouse.com/do-not-schedule: true, NoSchedule`
        * arm64: [`clickhouse.com/arch`](http://clickhouse.com/arch)`: arm64, NoSchedule`
      * タグ
        * 使用する場合、cluster-autoscaler で必要になることがあります
          * 例:
            * `k8s.io/cluster-autoscaler/enabled: true`
            * `k8s.io/cluster-autoscaler/$CLUSTER_NAME: owned`
    * Server ノードグループ
      * AMI イメージ
        * x86: AL2023&#95;x86&#95;64
        * arm64: AL2023&#95;ARM&#95;64
      * ディスクサイズ: 20gb
      * [ノードグループ用 EC2 Launch Template](#ec2-launch-template-for-node-group-server))
      * オートスケーリングを使用しない場合、最小ノード数と希望ノード数は、必要な ClickHouse レプリカ数と同じにする必要があります
      * 推奨インスタンスタイプ: `m7gd.16xlarge`
        * ClickHouse が cache として使用する NVME SSD を含む **「d」シリーズのインスタンス** (例: `m7gd.*`) の使用を強く推奨します
          * NVME SSD を搭載したインスタンスでは、NVME SSD を自動的にマウントするために [カスタム launch template](#ec2-launch-template-for-node-group-server) を使用してください
      * Kubernetes ラベル
        * x86: `clickhouseGroup: server`
        * arm64: `clickhouseGroup: server-arm64`
      * Kubernetes taints
        * `clickhouse.com/do-not-schedule: true, NoSchedule`
        * arm64: [`clickhouse.com/arch`](http://clickhouse.com/arch)`: arm64, NoSchedule`
      * タグ
        * 使用する場合、cluster-autoscaler で必要になることがあります
          * 例:
            * `k8s.io/cluster-autoscaler/enabled: true`
            * `k8s.io/cluster-autoscaler/$CLUSTER_NAME: owned`
    * x86 のその他のプロセス (operator, ...) を実行するための x86 ノードグループ
      * EKS クラスターがすでに存在する場合、最小サイズが xlarge ノードで x86 互換であれば、既存のノードグループを使用できます
      * 新しいノードグループの場合
        * AMI イメージ: AL2023&#95;x86&#95;64
        * ディスクサイズ: 20gb
        * インスタンスサイズ: 最小 xlarge
        * インスタンスタイプ: 任意の x86 互換タイプ
* EKSクラスター用のOIDCプロバイダーを作成する
* 暗号化を有効にした S3 バケット (S3 標準クラス) を作成
  * バケットは EKS クラスターと同じリージョン内にある必要があります
  * プロビジョニングした ClickHouse クラスターごとにバケットを作成することも、1 つのバケットを共用することもできますが、その場合は ClickHouse クラスターごとに一意のプレフィックスが必要です (clickhouse CR/helm チャートで定義)
* NLB を作成します。Kubernetes クラスター外からのイングレスが必要な場合は必須です
  * NLB が必要な**場合は、[istio](https://istio.io/) のような仕組みでリクエストを適切なクラスターにルーティングしない限り、ClickHouse クラスターごとに**プロビジョニングする必要があります
  * Route 53 のエントリを作成します。これは、Kubernetes annotations を使用して [external-dns](https://github.com/kubernetes-sigs/external-dns) などで自動化できます (セットアップ手順はこのドキュメントには含まれていません)
* IAM ロールを作成します:
  * **特に指定がない限り、以下のロールでは [このような信頼ポリシー](#example-trust-policy) を使用する必要があります (つまり、IRSA を使用する必要があります)&#x20;**
  * clickhouse-server/keeper ロール
    * **このロールは、プロビジョニングされた ClickHouse クラスターごとに必要です**
    * 命名規則は `CH-S3-$NAME-$REGION-$ORDINAL-Role` とします
      * `$NAME`：クラスター名。例：`default-xx-01`
      * `$REGION`：クラスターのリージョンを識別するためのもので、同じクラスター名を使用する場合にリージョン間での命名競合を避けるために使います。
        * リージョンの正式名称を使う必要はなく、使うとロール名が許可された長さの上限を超える可能性があります。`us-west-2` には `uw2` のような短縮名を使用してかまいません
      * `$ORDINAL`：予約済みのため、`00` に設定します
      * us-west-2 にある `default-xx-01` という名前のサービスのロール名の例：`CH-S3-default-xx-01-uw2-00-Role`
    * バケット権限
      * 最小限必要な権限は次のとおりです：バケットリソースに対する `s3:*`、`s3:ListBucket`

* IPv4 CIDR ブロック: 10.20.0.0/16

  * us-west-2a: 10.20.0.0/18
  * us-west-2b: 10.20.64.0/18
  * us-west-2c: 10.20.128.0/18

* VPC エンドポイント: S3 ゲートウェイ
* DNS オプション:
  * DNS ホスト名を有効化: true
  * DNS 名前解決を有効化: true

<div id="copy-ecr-artifacts">
  ### ECRアーティファクトをコピーする
</div>

**イメージのコピーには [skopeo](https://github.com/containers/skopeo) を使用することを強く推奨します**。これにより、Dockerイメージに含まれるすべてのアーキテクチャを保持できます。以下の `TARGET_REGION` と `TARGET_ECR_REPO` は、使用する ECR のリージョンとホストに合わせて必ず設定してください。

```bash
SOURCE_REGION=us-east-1
SOURCE_ECR_REPO=349290138304.dkr.ecr.$SOURCE_REGION.amazonaws.com

TARGET_REGION=us-west-2
TARGET_ECR_REPO=0000000000.dkr.ecr.$TARGET_REGION.amazonaws.com

# 弊社にログイン（認証プロセスはお客様によって異なる場合があります）
aws ecr get-login-password --region $SOURCE_REGION | skopeo login --username AWS --password-stdin $SOURCE_ECR_REPO

# ターゲットのAWSリポジトリにログイン（認証プロセスはお客様によって異なる場合があります）
aws ecr get-login-password --region $TARGET_REGION | skopeo login --username AWS --password-stdin $TARGET_ECR_REPO

# 各イメージをターゲットECRにコピー。--all フラグを必ず指定してください
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-server:<<SERVER_TAG>> docker://$TARGET_ECR_REPO/clickhouse-server:<<SERVER_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-keeper:<<KEEPER_TAG>> docker://$TARGET_ECR_REPO/clickhouse-keeper:<<KEEPER_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-operator:main-<<OPERATOR_TAG>> docker://$TARGET_ECR_REPO/clickhouse-operator:<<OPERATOR_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/clickhouse-operator-helm:<<OPERATOR_TAG>> docker://$TARGET_ECR_REPO/helm/clickhouse-operator-helm:<<OPERATOR_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/onprem-clickhouse-cluster:<<CR_HELM_TAG>> docker://$TARGET_ECR_REPO/helm/onprem-clickhouse-cluster:<<CR_HELM_TAG>>
```

  ### EKS クラスターの作成
</div>

クラスター IAM ロールとノード IAM ロールが必要です。AWS コンソール UI でデフォルトの権限を使用し、&quot;Create recommended role&quot; ボタンから作成したロールで十分です。

<div id="cloud-formation-to-create-iam-role-to-pull-images">
  ### イメージをプルするための IAMロールを作成する CloudFormation
</div>

ClickHouse のプライベート ECR からイメージをプルするには IAMロールが必要です。このロールは CloudFormation テンプレートを使用して作成します。ロール ARN が作成されたら、**その ARN (出力を参照) を ClickHouse チームに提供する必要があります**。

**CloudFormation**

```yaml expandable
AWSTemplateFormatVersion: 2010-09-09
Description: このCloudFormationテンプレートはClickHouseAirgapECRPullRoleを作成します。

Resources:
  ClickHouseAirgapECRPullRole:
    Type: AWS::IAM::Role
    Properties:
      RoleName: ClickHouseAirgapECRPullRole
      AssumeRolePolicyDocument:
        Version: 2012-10-17
        Statement:
          - Effect: Allow
            Principal:
              AWS: !Sub "arn:aws:iam::${AWS::AccountId}:root"
            Action:
              - sts:AssumeRole
          - Effect: Allow
            Principal:
              Service:
                - ec2.amazonaws.com
            Action:
              - sts:AssumeRole
      Policies:
        - PolicyName: ClickHouseAirgapECRPullPolicy
          PolicyDocument:
            Version: 2012-10-17
            Statement:
              - Effect: Allow
                Action:
                  - ecr:GetDownloadUrlForLayer
                  - ecr:BatchGetImage
                  - ecr:BatchCheckLayerAvailability
                  - ecr:DescribeImages
                  - ecr:ListImages
                Resource:
                  - arn:aws:ecr:us-east-1:349290138304:repository/*
              - Effect: Allow
                Action:
                  - ecr:GetAuthorizationToken
                Resource:
                  - "*"

Outputs:
  RoleArn:
    Description: すべてのECRリポジトリからイメージをプルするためのIAMロールARN
    Value: !GetAtt ClickHouseAirgapECRPullRole.Arn

```

<div id="ec2-launch-template-for-node-group-server">
  ### ノードグループサーバー向け EC2 起動テンプレート
</div>

サーバーノードグループを作成する前に、ClickHouse クエリをキャッシュするための SSD ディスクを備えたノードをプロビジョニングできるよう、EC2 起動テンプレートを作成しておくことを推奨します。

テンプレートには、以下のスクリプトを含めてください。**起動テンプレートが以前に作成されている場合は、既存のデータが含まれている可能性がありますが、それらは保持したままにする必要がある点に注意してください**。その場合は、各ファイルが指定された境界で区切られていることを必ず確認してください。

**詳細設定  (ユーザーデータ**):

```bash expandable
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="==MYBOUNDARY=="

--==MYBOUNDARY==
Content-Type: text/x-shellscript; charset="us-ascii"

#!/bin/bash
sudo sysctl net.ipv4.tcp_fin_timeout=15
sudo sysctl net.ipv4.tcp_keepalive_time=15

function build_raid() {
set -x
mapfile -t SSD_NVME_DEVICE_LIST < <(nvme list | grep "Amazon EC2 NVMe Instance Storage" | cut -d " " -f 1 || true)
SSD_NVME_DEVICE_COUNT=${#SSD_NVME_DEVICE_LIST[@]}
RAID_DEVICE=${RAID_DEVICE:-/dev/md0}
RAID_CHUNK_SIZE=${RAID_CHUNK_SIZE:-512}              # キロバイト
FILESYSTEM_BLOCK_SIZE=${FILESYSTEM_BLOCK_SIZE:-4096} # バイト
STRIDE=$((RAID_CHUNK_SIZE * 1024 / FILESYSTEM_BLOCK_SIZE))
STRIPE_WIDTH=$((SSD_NVME_DEVICE_COUNT * STRIDE))
BLK_LABEL=ssdcache
MD_DEV_LABEL=dpssdcache

# fstabにマウントが存在する場合 - 終了
grep "${BLK_LABEL}" /etc/fstab && return 0

nvme list
echo "${SSD_NVME_DEVICE_COUNT}" "${SSD_NVME_DEVICE_LIST[*]}"

# nvmeデバイス数に基づいてプロビジョニングを実行
case  "${SSD_NVME_DEVICE_COUNT}" in
"0")
  echo 'No devices found of type "Amazon EC2 NVMe Instance Storage"'
  echo "Maybe your node selectors are not set correct"
  return 0
  ;;
"1")
  mkfs.ext4 -L "${BLK_LABEL}" -m 0 -b "${FILESYSTEM_BLOCK_SIZE}" "${SSD_NVME_DEVICE_LIST[0]}"
  ;;
*)
  mdadm --create --verbose "${RAID_DEVICE}" --name="${MD_DEV_LABEL}" --level=0 -c "${RAID_CHUNK_SIZE}" \
    --raid-devices="${#SSD_NVME_DEVICE_LIST[@]}" "${SSD_NVME_DEVICE_LIST[@]}"

  while mdadm --detail "${RAID_DEVICE}" | grep -q -ioE 'State :.*resyncing'
  do
    echo "Raid is resyncing.."
    sleep 1
  done
  echo "Raid0 device  ${RAID_DEVICE} has been created with disks  ${SSD_NVME_DEVICE_LIST[*]}"
  mkfs.ext4 -L "${BLK_LABEL}" -m 0 -b "${FILESYSTEM_BLOCK_SIZE}" -E "stride=${STRIDE},stripe-width=${STRIPE_WIDTH}" "${RAID_DEVICE}"
  ;;
esac

# マウントしてfstabに追加
# UUIDはEKS NVMEプロビジョナーツールとの互換性のために使用
DEV_NAME=$(blkid -s UUID -o value -L "${BLK_LABEL}")
UUID=$(blkid -s UUID -o value "${DEV_NAME}")
# UUIDが定義されていることを確認
test -z ${UUID} && return 1
mkdir -p /pv-disks/"${UUID}" /nvme/
test -h /nvme/disk || ln -fs /pv-disks/"${UUID}" /nvme/disk

cat<<EOF | tee -a /etc/fstab

LABEL=${BLK_LABEL} /pv-disks/${UUID} ext4 defaults,noatime,discard,nobarrier  0 0
EOF
mount -a
set +x
}

yum install -y nvme-cli mdadm
build_raid
mountpoint /nvme/disk/ || systemctl stop kubelet

--==MYBOUNDARY==--
```

<div id="install-storageclass-via-helm">
  ### Helm で StorageClass をインストールする
</div>

StorageClass が必要な場合は、これらの clickhouse-operator の依存関係を、実際の clickhousecluster CR の作成とは分けて、提供されている Helm チャートで個別にインストールすることを推奨します。こうすることで、複数の CR を作成した場合でも、依存関係が特定のクラスターに紐付かず、そのクラスターを削除しても一緒に削除されません。**この手順が必要なのは、clickhouser-server と clickhouse-keeper で使用するカスタムまたは既存の StorageClass CR がない場合のみです。**

```bash
# 必要に応じてECR_HOSTを更新してください
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
CHART_VERSION=<<CR_HELM_TAG>>

helm install clickhouse-prerequisites \
    oci://$ECR_HOST/helm/onprem-clickhouse-cluster \
    --version=$CHART_VERSION \
    -n default \
    --set-json="storageClass.create=true" \
    --set-json="createCluster=false" \
    --set-json="serviceAccount.create=false"
```

<div id="install-operator-via-helm">
  ### Helm で Operator をインストールする
</div>

必要に応じて、バージョン、ECR ホスト、アベイラビリティゾーン (作成した VPC によって決まります) を更新してください。

```bash expandable
# 必要に応じてECR_HOSTを更新する
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com

# operatorそのものではなく、operatorのHelmチャートのバージョンを使用すること（例：main.<<OPERATOR_TAG>>ではなく<<OPERATOR_TAG>>）
OPERATOR_VERSION=<<OPERATOR_TAG>>

# VPCサブネットによって決定されたAZを設定する
AZ_LIST='["us-west-2a","us-west-2b","us-west-2c"]'

helm install clickhouse-operator \
   oci://$ECR_HOST/helm/clickhouse-operator-helm \
   --version=$OPERATOR_VERSION \
   --create-namespace \
   -n clickhouse-operator-system \
   --set-json="image.repository=\"$ECR_HOST/clickhouse-operator\"" \
   --set-json='cilium.enabled=false' \
   --set-json='idleScalerEnabled=false' \
   --set-json='webhooks.enabled=false' \
   --set-json='operator.debug=true' \
   --set-json='operator.metricsScraper.enabled=false' \
   --set-json="operator.availabilityZones=$AZ_LIST" \
   --set-json='operator.featureFlags.backupOnASeparatePod=true' \
   --set-json='operator.featureFlags.serverCMEKEnabled=true'
```

<div id="install-operator-via-kustomize">
  ##### Kustomize 経由で Operator をインストールする
</div>

kustomize を使用している場合は、既知の問題により、values の一部として `namespaceOperator` に Operator をインストールするネームスペース (デフォルトのネームスペース名: `clickhouse-operator-system`) を明示的に指定する必要があります: [https://github.com/kubernetes-sigs/kustomize/issues/5566](https://github.com/kubernetes-sigs/kustomize/issues/5566)。

<div id="install-aws-ebs-csi-driver">
  ### aws-ebs-csi-driver をインストールする
</div>

以下を満たす IAM ロールが必要です。

* マネージドポリシー `arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy` を使用する
* 信頼ポリシーには、EKS クラスターの OIDC プロバイダーで `sts:AssumeRoleWithWebIdentity` を使用することを推奨します ([例](#example-trust-policy))
* 選択するロール名は、aws-ebs-csi-driver を実行するサービスアカウントのアノテーションと一致している必要があります
  * 名前の例: `ClickHouse_EksEbsCsiDriverRole`

IAM ロールをサービスアカウントに関連付けるための追加の values を指定して、[Helm installation](https://github.com/kubernetes-sigs/aws-ebs-csi-driver/blob/master/docs/install.md#helm) ガイドに従ってください。

```bash
# 必要に応じてロール名を更新する
AWS_EBS_CSI_DRIVER_IAM_ROLE_ARN=arn:aws:iam::0000000000:role/ClickHouse_EksEbsCsiDriverRole

helm upgrade --install aws-ebs-csi-driver \
--namespace kube-system \
aws-ebs-csi-driver/aws-ebs-csi-driver \
--set-json="controller.serviceAccount.annotations={\"eks.amazonaws.com/role-arn\":\"$AWS_EBS_CSI_DRIVER_IAM_ROLE_ARN\"}"
```

<div id="install-volumesnapshot-crds">
  ### VolumeSnapshot CRD をインストールする
</div>

現在、これらは当社の Operator で必要ですが、このセットアップではまだ使用されていません。


<div id="naming-your-clickhouse-cluster">
  ### ClickHouse クラスターの命名
</div>

プロビジョニングする各 ClickHouse クラスターについて、対象の EKS クラスター内で**一意のクラスター名**を選択してください。この名前は AWS および Kubernetes のさまざまなリソースで使用され、クラスターを一意に識別するためにも使われます。

1. 命名規則は `$DESCRIPTOR-$LETTERS-$ORDINAL` とします
   1. $DESCRIPTOR - 文字のみで構成された、クラスターを表す説明的な名前
   2. $LETTERS - 予約済みです。任意の 2 文字を選択してください。簡単にするため、`xx` で構いません
   3. $ORDINAL - 同じ descriptor を持つクラスターに対して、`01` から始まる連番
2. 名前の例: `default-xx-01`

<div id="clickhousecluster-cr">
  ### Clickhousecluster CR
</div>

以下の値は、本番環境向けに確認のうえ更新してください (例: リソース、機能フラグ、サーバー設定など) 。`CLUSTER_NAME` を設定する前に、[命名に関するセクション](#naming-your-clickhouse-cluster)を参照してください。
次のコマンド (OS X) を使用して指定した `$PASSWORD` のパスワードハッシュを生成し、その値を Helm チャートの `account.hashedPassword` に設定します:

```bash expandable
# これは `default` ユーザーのパスワードになります
PASSWORD='My super secret p@$$w0rd'
HASHED_PASSWORD=`echo -n $PASSWORD | shasum -a 256 | awk '{printf $1}' | base64`

# 必要に応じて以下の値を更新してください。
# ecr ホストはご自身のアカウントのものを指定してください。
# s3 バケットは事前に作成したものを指定してください。
CLUSTER_NAME=default-xx-01
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
SA_IAM_ROLE_ARN=arn:aws:iam::0000000000:role/CH-S3-${CLUSTER_NAME}-uw2-00-Role
S3_BUCKET_NAME=my-clickhouse-data

# s3 キープレフィックスには任意の UUID 値を使用できますが、上記で指定したバケットにデータを保存するすべてのクラスターで一意である必要があります
S3_KEY_PREFIX=ch-s3-$(uuidgen | tr '[:upper:]' '[:lower:]')

# これらはノードグループに追加された clickhouseGroup ラベルの値と一致させてください
SERVER_NG_GROUP=server-arm64
KEEPER_NG_GROUP=keeper-arm64

# これらの値は選択したインスタンスサイズに応じて変更してください。
# CPU および MEMORY の値を設定する際は、デーモンセットの要件も考慮してください。
SERVER_CPU=64
SERVER_MEMORY=256Gi
KEEPER_CPU=4
KEEPER_MEMORY=16Gi

CHART_VERSION=<<CR_HELM_TAG>>

# bytesPerGiRAM はディスクキャッシュサイズを自動計算するためのスケーリング係数です。
# 一般的な目安として、キャッシュサイズは利用可能な SSD キャッシュディスクサイズの 80〜90% に設定してください。
# Helm チャートで bytesPerGiRAM を設定すると、ポッド起動時に以下の計算式が使用されます:
#
# CONFIG_DISK_CACHE_SIZE = bytesPerGiRAM * pod_memory_limit
#
# 例:
# bytesPerGiRAM = 11.3Gi
# pod_memory_limit = 250Gi
# CONFIG_DISK_CACHE_SIZE = 11.3 * 250 = 2825Gi
CACHE_BYTES_PER_GI_RAM=11Gi

helm install $CLUSTER_NAME \    oci://$ECR_HOST/helm/onprem-clickhouse-cluster \
    --version=$CHART_VERSION \
    -n ns-$CLUSTER_NAME \
    --create-namespace \
    --set-json="account.hashedPassword=\"$HASHED_PASSWORD\"" \
    --set-json="server.image.repository=\"$ECR_HOST/clickhouse-server\"" \
    --set-json="server.storage.s3.bucketName=\"$S3_BUCKET_NAME\"" \
    --set-json="server.storage.s3.keyPrefix=\"$S3_KEY_PREFIX\"" \
    --set-json='server.arm64=true' \
    --set-json="server.image.tag=\"<<SERVER_TAG>>\"" \
    --set-json="server.podPolicy.nodeSelector.clickhouseGroup=\"$SERVER_NG_GROUP\"" \
    --set-json="keeper.image.repository=\"$ECR_HOST/clickhouse-keeper\"" \
    --set-json='keeper.arm64=true' \
    --set-json="keeper.image.tag=\"<<KEEPER_TAG>>\"" \
    --set-json="keeper.podPolicy.nodeSelector.clickhouseGroup=\"$KEEPER_NG_GROUP\"" \
    --set-json="serviceAccount.annotations={\"eks.amazonaws.com/role-arn\":\"$SA_IAM_ROLE_ARN\"}" \
    --set-json='server.tolerations=[{"effect":"NoSchedule","key":"clickhouse.com/do-not-schedule","operator":"Exists"}]' \
    --set-json='keeper.tolerations=[{"effect":"NoSchedule","key":"clickhouse.com/do-not-schedule","operator":"Exists"}]' \
    --set-json="server.ssdCacheConfiguration.bytesPerGiRAM=\"$CACHE_BYTES_PER_GI_RAM\"" \
    --set-json="server.podPolicy.resources.limits.cpu=\"$SERVER_CPU\"" \
    --set-json="server.podPolicy.resources.limits.memory=\"$SERVER_MEMORY\"" \
    --set-json="server.podPolicy.resources.requests.cpu=\"$SERVER_CPU\"" \
    --set-json="server.podPolicy.resources.requests.memory=\"$SERVER_MEMORY\"" \
    --set-json="keeper.podPolicy.resources.limits.cpu=\"$KEEPER_CPU\"" \
    --set-json="keeper.podPolicy.resources.limits.memory=\"$KEEPER_MEMORY\"" \
    --set-json="keeper.podPolicy.resources.requests.cpu=\"$KEEPER_CPU\"" \
    --set-json="keeper.podPolicy.resources.requests.memory=\"$KEEPER_MEMORY\""
```

<div id="hydra-setup">
  ## Hydra のセットアップ
</div>

1 つの ClickHouse クラスター内に複数のノードグループを作成する、という考え方です。各ノードグループは、それぞれ異なる数のノード (メモリ容量も異なる) と個別のエンドポイントを持ちます。こうしたノードグループは、共有 S3 バケット内で 1 つの Keeper インスタンスと 1 つのデータセット／フォルダーを共有します。

<div id="provisioning-hydra-children-instances">
  ### Hydra の子インスタンスのプロビジョニング
</div>

<div id="prerequisites">
  ##### 前提条件
</div>

operator は、Hydra 機能を有効にする設定 (デフォルトは false) を指定して[インストール](#install-operator-via-helm)しておく必要があります。

```bash
--set operator.featureFlags.privateHydraEnabled="true"
```

<div id="setup">
  ##### セットアップ
</div>

*子インスタンスを作成する前に、既存の親 ClickHouse クラスターを選択するか、新しい親 ClickHouse クラスターを作成する必要があります。そのため、子インスタンスで使用する親の**名前**と**ネームスペース**を事前に把握しておく必要があります。*

新しい子サービスを作成するには、サービス作成の[同じ手順](#clickhousecluster-cr)に従い、`ClickHouseCluster` カスタムリソース (CR) の作成時に追加の Helm 値を指定するだけです。

```bash
--set-json='parentCluster.name="c-${PARENT_NAME}'"'
--set-json='parentCluster.namespace="ns-'${PARENT_NAME}'"'
```

**PARENT&#95;NAME** - 既存または新規の親 ClickHouse クラスター名。

必要に応じて、新しい子クラスターを読み取り専用にする場合は (既定値は false) 、次を追加できます。

```bash
--set-json='isReadonly=true'
```

<div id="limitations">
  ### 制限事項
</div>

1. 親インスタンスが停止中、終了済み、またはアイドル状態では、子インスタンスをプロビジョニングできません。
2. 親クラスターを削除する場合は、先に子インスタンスを削除する必要があります。

<div id="install-validation">
  ## インストールの確認
</div>

<div id="preflight-checks">
  ### 事前チェック
</div>

クラスター診断用の Kubernetes プラグインである [Troubleshoot](https://troubleshoot.sh/) を使って、任意で事前チェックを実行できます。

必要なプラグインのインストールには、Krew を使用できます。

```console
kubectl krew install preflight
```

または、他のインストールオプションについては Troubleshoot の[ドキュメント](https://troubleshoot.sh/docs/)を参照してください。

ClickHouse では、Helm チャート (`helm/preflight-check`) を提供しています。これを ECR にコピーし、ローカルでレンダリングして preflight spec を生成したうえで、`kubectl preflight` に渡すことができます。

<div id="copying-the-preflight-check-helm-chart">
  ##### Preflight Check 用 Helm チャートのコピー
</div>

[ECR のコピー手順](#copy-ecr-artifacts)に preflight チャートを追加します。

```bash
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/preflight-check:<<PREFLIGHT_CHART_TAG>> docker://$TARGET_ECR_REPO/helm/preflight-check:<<PREFLIGHT_CHART_TAG>>
```

<div id="running-the-preflight-checks">
  ##### Preflight チェックの実行
</div>

`helm template` を使って preflight spec をレンダリングし、その出力をそのまま `kubectl preflight` にパイプします。検証対象の ClickHouse クラスター名を `CLUSTER_NAME` に設定してください ([ClickHouse クラスターの命名](#naming-your-clickhouse-cluster) を参照) :

```bash
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
CHART_VERSION=<<PREFLIGHT_CHART_TAG>>
CLUSTER_NAME=default-xx-01

helm template clickhouse-preflight \
    oci://$ECR_HOST/helm/preflight-check \
    --version=$CHART_VERSION \
    --set preflight.clickhouseClusterName=$CLUSTER_NAME | \
kubectl preflight -
```

これは、ClickHouse Operator の実行と ClickHouse クラスターのデプロイに必要な要件を検証するものです。必要なノードラベルが
存在するか、Storage Class が正しく設定されているか、などを確認します。

出力には、各種事前チェックとそのステータスが表示されます。
![Preflight Example](/products/clickhouse-private/images/preflight-example.png)

出力をスクロールして、各チェックが正常に通過していることを確認できます。チェックが失敗した場合は、セットアップに (潜在的な) 問題があり、
ClickHouse クラスターを正常に稼働させるうえで支障となる可能性があることを示しています。各チェックには、問題を修正するための推奨事項も含まれています。

デフォルト (`gp3-encrypted`) 以外の Storage Class を対象に検証するには、追加の `--set` フラグで上書きします。

```bash
    --set preflight.checks.prerequisites.storageClassName=<your-storage-class>
```

<div id="required-permissions">
  ##### 必要な権限
</div>

`kubectl preflight` を実行するユーザーまたはサービス アカウントには、クラスター レベルおよびネームスペース レベルのリソースを読み取る権限が必要です。少なくとも、次のアクセス権が必要です。

| スコープ                                          | リソース                                                                                      |
| --------------------------------------------- | ----------------------------------------------------------------------------------------- |
| クラスター全体                                       | `nodes`, `namespaces`, `persistentvolumes`, `storageclasses`, `customresourcedefinitions` |
| Operator のネームスペース (`clickhouse-operator-system`) | `deployments`, `replicasets`, `pods`, `services`, `configmaps`, `events`                  |
| クラスターのネームスペース (`ns-<cluster-name>`)           | `statefulsets`, `pods`, `persistentvolumeclaims`, `services`, `configmaps`, `events`      |

実運用では、組み込みの `view` クラスター ロールと、関連するネームスペースに対する `view` アクセス権を持つプリンシパルであれば十分です。`cluster-admin` バインディングでも動作し、単発の検証実行ではこちらのほうが設定は簡単です。

<div id="port-forward-the-clickhouse-service-to-your-local-machine">
  ### ClickHouseサービスをローカルマシンにポートフォワードする
</div>

ローカルマシンから `c-default-xx-01-server-any` サービスにトラフィックを転送するには、次を実行します。

```bash
kubectl port-forward svc/c-default-xx-01-server-any 9000:9000 -n ns-default-xx-01
```

これにより、サービスのポート `9000` がローカルマシンのポート `9000` にポートフォワードされます。これで、`http://localhost:9000` から ClickHouse HTTP インターフェイスにアクセスできます。

<div id="access-clickhouse-and-run-query">
  ### ClickHouse にアクセスしてクエリを実行する
</div>

ポートフォワーディングを設定したら、`clickhouse-client` などのツールを使ってローカル環境から ClickHouse に接続できます。

```bash
clickhouse client --host localhost --port 9000 --password $PASSWORD
```

次に、簡単なクエリを実行します:

```sql
clickhouse-cloud :) select 1;
```

次のような出力が表示されます。

```text
SELECT 1
Query id: 825591bf-a8e5-4995-ac9f-afb864854ba2
   ┌─1─┐
1. │ 1  │
   └───┘
1 row in set. Elapsed: 0.001 sec.
```
