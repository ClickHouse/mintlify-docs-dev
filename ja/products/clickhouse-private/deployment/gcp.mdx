<div id="overview">
  ## 概要
</div>

このガイドでは、Google Kubernetes Engine (GKE) を使用して Google Cloud Platform (GCP) 上に ClickHouse Private をデプロイする方法を説明します。標準的な AWS のデプロイ手順をベースに、Artifact Registry、S3 互換 API を備えた GCS、Workload Identity など、GCP 固有のサービスに合わせて調整しています。

このガイドは、**標準**デプロイと **FIPS 140-2 準拠**デプロイの両方に対応しています。FIPS 固有の手順と設定には、本文全体で **(FIPS)** と明記しています。FIPS モードを有効にするには、`00-env.sh` で `ENABLE_FIPS=true` を設定してください。

<div id="prerequisites">
  ## 前提条件
</div>

* 課金が有効な GCP プロジェクト
* インストール済みで認証済みの `gcloud` CLI
* `kubectl` インストール済み
* `helm` v3.x インストール済み
* `skopeo` インストール済み (コンテナーイメージのコピー用) 
* ClickHouse ECR への読み取りアクセス権を持つ AWS 認証情報 (イメージコピー用) 
* プライベートクラスターにアクセスするための VPC 内の **踏み台サーバー**
* 適切な権限を持つ **デプロイ用サービスアカウント** (以下を参照) 
* **(FIPS)** Red Hat UBI8 コンテナーイメージへのアクセス (証明書生成のため、GKE 経由でプル)

<div id="creating-a-service-account-for-clickhouse-deployment">
  ## ClickHouseのデプロイ用サービスアカウントの作成
</div>

FedRAMP 環境ではユーザーの直接認証が制限されるため、権限借用用のサービスアカウントを作成します。

<div id="option-1-via-gcp-console">
  ### オプション 1: GCP Console 経由
</div>

1. **IAM &amp; Admin** → **Service Accounts** に移動します
2. **+ CREATE SERVICE ACCOUNT** をクリックします
3. 以下を入力します:
   * **Name:** `clickhouse-deployer`
   * **ID:** `clickhouse-deployer`
   * **Description:** `ClickHouse インフラストラクチャのデプロイ用サービスアカウント`
4. **CREATE AND CONTINUE** をクリックします
5. 次のロールを追加します:

| Role                                    | Purpose                         |
| --------------------------------------- | ------------------------------- |
| `roles/compute.networkAdmin`            | VPC、サブネット、NAT、ルーターの作成と管理        |
| `roles/container.admin`                 | GKE クラスターとノードプールの作成と管理          |
| `roles/storage.admin`                   | GCS バケットの作成と管理                  |
| `roles/iam.serviceAccountAdmin`         | サービスアカウントの作成と管理                 |
| `roles/iam.serviceAccountUser`          | Workload Identity でサービスアカウントを使用 |
| `roles/iam.workloadIdentityUser`        | Workload Identity のバインディングを設定   |
| `roles/artifactregistry.admin`          | Artifact Registry リポジトリの作成と管理   |
| `roles/resourcemanager.projectIamAdmin` | プロジェクトの IAM ポリシーを管理             |

6. **CONTINUE** → **DONE** をクリックします

**Token Creator 権限を付与する:**

1. 新しく作成した `clickhouse-deployer` サービスアカウントをクリックします
2. **PERMISSIONS** タブに移動します
3. **GRANT ACCESS** をクリックします
4. プリンシパルを追加します: `<COMPUTE_SERVICE_ACCOUNT>@developer.gserviceaccount.com` (踏み台サーバーのサービスアカウント) 
5. `roles/iam.serviceAccountTokenCreator` ロールを割り当てます
6. **SAVE** をクリックします

<div id="option-2-via-cli-requires-iam-admin-access">
  ### オプション 2: CLI 経由 (IAM 管理者権限が必要)
</div>

```bash expandable
PROJECT_ID=your-project-id
SA_EMAIL=clickhouse-deployer@${PROJECT_ID}.iam.gserviceaccount.com
COMPUTE_SA=<COMPUTE_PROJECT_NUMBER>-compute@developer.gserviceaccount.com

# サービスアカウントを作成する
gcloud iam service-accounts create clickhouse-deployer \
  --display-name="ClickHouse Deployer" \
  --project=${PROJECT_ID}

# ロールを付与する
for role in \
  roles/compute.networkAdmin \
  roles/container.admin \
  roles/storage.admin \
  roles/iam.serviceAccountAdmin \
  roles/iam.serviceAccountUser \
  roles/iam.workloadIdentityUser \
  roles/artifactregistry.admin \
  roles/resourcemanager.projectIamAdmin
do
  gcloud projects add-iam-policy-binding ${PROJECT_ID} \
    --member="serviceAccount:${SA_EMAIL}" \
    --role="${role}"
done

# コンピュートSAによる権限借用を許可する
gcloud iam service-accounts add-iam-policy-binding ${SA_EMAIL} \
  --member="serviceAccount:${COMPUTE_SA}" \
  --role="roles/iam.serviceAccountTokenCreator" \
  --project=${PROJECT_ID}
```

<div id="configure-impersonation-on-bastion">
  ### 踏み台サーバー で 権限借用 を設定する
</div>

以下を `00-env.sh` に追加するか、スクリプトの実行前に実行してください。

```bash
# デプロイヤーサービスアカウントの権限借用を設定する
gcloud config set auth/impersonate_service_account clickhouse-deployer@${GCP_PROJECT}.iam.gserviceaccount.com

# 動作確認
gcloud compute networks list --project=${GCP_PROJECT}
```

後で権限借用を解除するには:

```bash
gcloud config unset auth/impersonate_service_account
```

<div id="00-environment-variables">
  ## 00. 環境変数
</div>

**ファイル: `00-env.sh`**

```bash expandable
#!/bin/bash
# ============================================
# ClickHouse Private GCP - 環境セットアップ
# ============================================
# 環境に合わせてこれらの値を更新してください

# GCP プロジェクトとリージョン
export GCP_PROJECT=your-project-id
export GCP_REGION=us-central1
export GCP_ZONES="us-central1-a,us-central1-b,us-central1-c"

# GKE クラスター
export GKE_CLUSTER_NAME=clickhouse-cluster

# ClickHouse クラスター（GKE クラスターごとに複数設定可能）
export CLUSTER_NAME=default-xx-01
export NAMESPACE=ns-${CLUSTER_NAME}

# ネットワーク - 踏み台サーバーが存在する既存の VPC を使用
export VPC_NAME=clickhouse-vpc
export SUBNET_NAME=gke-subnet
export SUBNET_RANGE=10.1.0.0/24
export POD_RANGE=10.244.0.0/14         # /14 境界である必要があります（第3オクテットが4の倍数）
export SERVICE_RANGE=10.252.0.0/20     # /20 境界である必要があります
export MASTER_IPV4_CIDR=172.16.0.0/28  # プライベートクラスターのコントロールプレーン用
export BASTION_SUBNET_RANGE=10.0.0.0/24  # 踏み台サーバーのサブネット（master-authorized-networks 用）

# ストレージ
export BUCKET_NAME=clickhouse-data-${GCP_PROJECT}
export S3_KEY_PREFIX=ch-s3-$(uuidgen | tr '[:upper:]' '[:lower:]')

# サービスアカウント
export GSA_NAME=clickhouse
export GSA_EMAIL=${GSA_NAME}@${GCP_PROJECT}.iam.gserviceaccount.com
export KSA_NAME=clickhouse

# Artifact Registry
export GAR_REPO_NAME=clickhouse
export GAR_HOST=${GCP_REGION}-docker.pkg.dev/${GCP_PROJECT}/${GAR_REPO_NAME}

# FIPS 設定（FIPS 140-2 準拠にする場合は true に設定）
export ENABLE_FIPS=false

# イメージバージョン - FIPS モードでは FIPS 準拠のビルドを使用
if [ "$ENABLE_FIPS" = "true" ]; then
  export CLICKHOUSE_SERVER_VERSION=25.8.1.9104-fips
  export CLICKHOUSE_KEEPER_VERSION=26.1.1.1493
else
  export CLICKHOUSE_SERVER_VERSION=25.8.1.9104
  export CLICKHOUSE_KEEPER_VERSION=25.10.1.6624
fi
export CLICKHOUSE_OPERATOR_VERSION=main-1.16067.1
export OPERATOR_HELM_VERSION=1.16067.1
export CLUSTER_HELM_VERSION=1.1.155

# AWS ECR ソース（イメージのコピー用）
export SOURCE_ECR_REGION=us-east-1
export SOURCE_ECR_REPO=349290138304.dkr.ecr.${SOURCE_ECR_REGION}.amazonaws.com
export AWS_PROFILE=clickhouse-ecr

# ノードプール設定
export KEEPER_MACHINE_TYPE=n2-standard-4      # 本番環境では n2-standard-8 を推奨
export SERVER_MACHINE_TYPE=n2-standard-8      # 本番環境では n2-standard-64 を推奨
export DEFAULT_MACHINE_TYPE=n2-standard-4

# リソース制限（インスタンスサイズに合わせて調整）
export SERVER_CPU=4                           # マシンタイプに合わせる
export SERVER_MEMORY=16Gi                     # マシンタイプに合わせる
export KEEPER_CPU=2
export KEEPER_MEMORY=8Gi

# キャッシュ設定
export CACHE_BYTES_PER_GI_RAM=11Gi

# FIPS 証明書設定（ENABLE_FIPS=true の場合のみ使用）
if [ "$ENABLE_FIPS" = "true" ]; then
  export KUBERNETES_DOMAIN=cluster.local
  export CERT_DIR=./certs
  export SELF_SIGNED=true  # 既存の CA を使用する場合は false に設定
fi

# ClickHouse パスワード
# 本番環境/FIPS の場合: 代わりに Secret Manager を使用してください:
#   export CLICKHOUSE_PASSWORD=$(gcloud secrets versions access latest --secret=clickhouse-password --project=${GCP_PROJECT})
export CLICKHOUSE_PASSWORD='change-me-not-for-production'

echo "=========================================="
echo "Environment Variables Set"
echo "=========================================="
echo "GCP Project:     ${GCP_PROJECT}"
echo "GCP Region:      ${GCP_REGION}"
echo "GKE Cluster:     ${GKE_CLUSTER_NAME}"
echo "CH Cluster:      ${CLUSTER_NAME}"
echo "Namespace:       ${NAMESPACE}"
echo "VPC:             ${VPC_NAME}"
echo "Subnet:          ${SUBNET_NAME}"
echo "Bucket:          ${BUCKET_NAME}"
echo "GAR Host:        ${GAR_HOST}"
echo "FIPS Mode:       ${ENABLE_FIPS}"
echo "=========================================="
```

**重要:** 他のスクリプトを実行する前に、source コマンドでこのファイルを読み込んでください:

```bash
source ./00-env.sh
```

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "01. Creating Artifact Registry"
echo "=========================================="

# リポジトリを作成する
echo "Creating repository: ${GAR_REPO_NAME}..."

  --location=${GCP_REGION} \
  --project=${GCP_PROJECT} &>/dev/null; then

fi

# Docker 認証を設定する
echo ""
echo "Configuring Docker authentication..."
gcloud auth configure-docker ${GCP_REGION}-docker.pkg.dev --quiet
echo "   ✓ Docker authentication configured"

echo ""
echo "=========================================="
echo "✅ Artifact Registry Setup Complete!"
echo "=========================================="
echo ""
echo "Repository URL: ${GAR_HOST}"
```

<div id="02-copy-container-images">
  ## 02. コンテナーイメージのコピー
</div>

**File: `02-copy-images.sh`**

すべてのアーキテクチャを保持するには、[skopeo](https://github.com/containers/skopeo) が必要です。

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "02. Copying ClickHouse Images"
echo "=========================================="

# AWSプロファイルの存在を確認
if ! aws configure list --profile ${AWS_PROFILE} &>/dev/null; then
  echo "ERROR: AWS profile '${AWS_PROFILE}' not found"
  echo "To create the profile, run: aws configure --profile ${AWS_PROFILE}"
  exit 1
fi

# ソースECRへの認証
echo "Authenticating to AWS ECR..."
aws ecr get-login-password --region ${SOURCE_ECR_REGION} --profile ${AWS_PROFILE} | \
  skopeo login --username AWS --password-stdin ${SOURCE_ECR_REPO}
echo "✓ ECR authentication successful"

# GCP Artifact Registryへの認証
echo "Authenticating to GCP Artifact Registry..."
gcloud auth configure-docker ${GCP_REGION}-docker.pkg.dev --quiet
echo "✓ GAR authentication successful"

echo ""
echo "Copying images..."

echo "1/5 Copying ClickHouse Server ${CLICKHOUSE_SERVER_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/clickhouse-server:${CLICKHOUSE_SERVER_VERSION} \
  docker://${GAR_HOST}/clickhouse-server:${CLICKHOUSE_SERVER_VERSION}
echo "✓ Server copied"

echo "2/5 Copying ClickHouse Keeper ${CLICKHOUSE_KEEPER_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/clickhouse-keeper:${CLICKHOUSE_KEEPER_VERSION} \
  docker://${GAR_HOST}/clickhouse-keeper:${CLICKHOUSE_KEEPER_VERSION}
echo "✓ Keeper copied"

echo "3/5 Copying ClickHouse Operator ${CLICKHOUSE_OPERATOR_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/clickhouse-operator:${CLICKHOUSE_OPERATOR_VERSION} \
  docker://${GAR_HOST}/clickhouse-operator:${CLICKHOUSE_OPERATOR_VERSION}
echo "✓ Operator copied"

echo "4/5 Copying Operator Helm Chart ${OPERATOR_HELM_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/helm/clickhouse-operator-helm:${OPERATOR_HELM_VERSION} \
  docker://${GAR_HOST}/helm/clickhouse-operator-helm:${OPERATOR_HELM_VERSION}
echo "✓ Operator Helm chart copied"

echo "5/5 Copying Cluster Helm Chart ${CLUSTER_HELM_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/helm/onprem-clickhouse-cluster:${CLUSTER_HELM_VERSION} \
  docker://${GAR_HOST}/helm/onprem-clickhouse-cluster:${CLUSTER_HELM_VERSION}
echo "✓ Cluster Helm chart copied"

echo ""
echo "=========================================="
echo "✅ All images copied successfully!"
echo "=========================================="

# 確認
echo ""
echo "Verifying images in Artifact Registry..."
gcloud artifacts docker images list ${GAR_HOST} --format="table(package,version)"
```

<div id="03-configure-vpc-and-subnet">
  ## 03. VPC とサブネットを設定する
</div>

**ファイル: `03-vpc-subnet.sh`**

このスクリプトは、踏み台ホストを備えた既存の VPC があることを前提としています。必要なセカンダリ範囲を持つ GKE サブネットを作成または更新します。

**重要: CIDR 境界の要件**

* `/14` ブロック: 第 3 オクテットは 4 の倍数である必要があります (例: `10.244.0.0`、`10.245.0.0` は不可) 
* `/20` ブロック: 第 4 オクテットは 0、第 3 オクテットは 16 の倍数境界である必要があります (例: `10.252.0.0`) 

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "03. Configuring VPC and GKE Subnet"
echo "=========================================="

# VPCが存在するか確認
echo "Checking VPC: ${VPC_NAME}..."
if gcloud compute networks describe ${VPC_NAME} --project=${GCP_PROJECT} &>/dev/null; then
  echo "   ✓ VPC exists"
else
  echo "   Creating VPC..."
  gcloud compute networks create ${VPC_NAME} \
    --subnet-mode=custom \
    --project=${GCP_PROJECT}
  echo "   ✓ VPC created"
fi

# GKEサブネットが存在するか確認
echo ""
echo "Checking GKE subnet: ${SUBNET_NAME}..."
if gcloud compute networks subnets describe ${SUBNET_NAME} --region=${GCP_REGION} --project=${GCP_PROJECT} &>/dev/null; then
  # サブネットが存在する - セカンダリ範囲を確認
  EXISTING_SECONDARY=$(gcloud compute networks subnets describe ${SUBNET_NAME} \
    --region=${GCP_REGION} \
    --project=${GCP_PROJECT} \
    --format="value(secondaryIpRanges.rangeName)" 2>/dev/null | grep -E "^pods$" || true)
  
  if [ -z "$EXISTING_SECONDARY" ]; then
    echo "   ⚠️ Subnet exists but missing secondary ranges"
    echo "   Adding secondary ranges for pods and services..."
    gcloud compute networks subnets update ${SUBNET_NAME} \
      --region=${GCP_REGION} \
      --add-secondary-ranges=pods=${POD_RANGE},services=${SERVICE_RANGE} \
      --project=${GCP_PROJECT}
    echo "   ✓ Secondary ranges added"
  else
    echo "   ✓ Subnet exists with secondary ranges"
  fi
else
  echo "   Creating GKE subnet..."
  gcloud compute networks subnets create ${SUBNET_NAME} \
    --network=${VPC_NAME} \
    --region=${GCP_REGION} \
    --range=${SUBNET_RANGE} \
    --secondary-range=pods=${POD_RANGE},services=${SERVICE_RANGE} \
    --enable-private-ip-google-access \
    --project=${GCP_PROJECT}
  echo "   ✓ Subnet created"
fi

# Private Google Accessを有効化
echo ""
echo "Ensuring Private Google Access is enabled..."
gcloud compute networks subnets update ${SUBNET_NAME} \
  --region=${GCP_REGION} \
  --enable-private-ip-google-access \
  --project=${GCP_PROJECT} 2>/dev/null || true
echo "   ✓ Private Google Access enabled"

echo ""
echo "=========================================="
echo "✅ VPC/Subnet Configuration Complete!"
echo "=========================================="
echo ""
echo "VPC:          ${VPC_NAME}"
echo "GKE Subnet:   ${SUBNET_NAME} (${SUBNET_RANGE})"
echo "Pods:         ${POD_RANGE}"
echo "Services:     ${SERVICE_RANGE}"
echo "Bastion:      ${BASTION_SUBNET_RANGE}"
```

<div id="04-create-cloud-nat">
  ## 04. Cloud NAT を作成する
</div>

**File: `04-cloud-nat.sh`**

プライベート GKE ノードがインターネットへ外向きにアクセスするには (イメージの取得など) 、Cloud NAT が必要です。

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "04. Creating Cloud NAT for Private Nodes"
echo "=========================================="

# Cloud Routerを作成する
echo "Creating Cloud Router..."
if gcloud compute routers describe clickhouse-router --region=${GCP_REGION} --project=${GCP_PROJECT} &>/dev/null; then
  echo "   ✓ Router already exists"
else
  gcloud compute routers create clickhouse-router \
    --network=${VPC_NAME} \
    --region=${GCP_REGION} \
    --project=${GCP_PROJECT}
  echo "   ✓ Router created"
fi

# Cloud NATを作成する
echo ""
echo "Creating Cloud NAT..."
if gcloud compute routers nats describe clickhouse-nat --router=clickhouse-router --region=${GCP_REGION} --project=${GCP_PROJECT} &>/dev/null; then
  echo "   ✓ NAT already exists"
else
  gcloud compute routers nats create clickhouse-nat \
    --router=clickhouse-router \
    --region=${GCP_REGION} \
    --nat-all-subnet-ip-ranges \
    --auto-allocate-nat-external-ips \
    --enable-logging \
    --log-filter=ERRORS_ONLY \
    --project=${GCP_PROJECT}
  echo "   ✓ NAT created"
fi

echo ""
echo "=========================================="
echo "✅ Cloud NAT Setup Complete!"
echo "=========================================="
echo ""
echo "Router: clickhouse-router"
echo "NAT:    clickhouse-nat"
echo "Region: ${GCP_REGION}"
```

  ## 05. GCPのサービス アカウントを作成

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
```

<div id="09-local-ssd-daemonset">
  ## 09. ローカルSSDデーモンセット
</div>

**ファイル: `09-local-ssd-daemonset.sh`**

GKE Container-Optimized OS (COS) のルートファイルシステムは読み取り専用のため、`/nvme` は作成できません。代わりに、ローカルSSDを `/mnt/disks/ssd0` にマウントし、ClickHouse がそのパスを使用するように設定します。

**注:** GKE ではノードプールで `--metadata-from-file=startup-script` (予約済みキー) を使用できないため、ローカルSSDをフォーマットしてマウントするにはデーモンセットが必要です。

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "09. ローカルSSD デーモンセットのデプロイ"
echo "=========================================="

kubectl apply -f - <<'EOF'
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: local-ssd-setup
  namespace: kube-system
spec:
  selector:
    matchLabels:
      app: local-ssd-setup
  template:
    metadata:
      labels:
        app: local-ssd-setup
    spec:
      hostPID: true
      nodeSelector:
        clickhouseGroup: server
      tolerations:
      - key: "clickhouse.com/do-not-schedule"
        operator: "Exists"
        effect: "NoSchedule"
      initContainers:
      - name: setup-ssd
        image: busybox:1.36
        command:
        - /bin/sh
        - -c
        - |
          set -e
          
          # nsenterを使用してホスト上でコマンドを実行する
          nsenter -t 1 -m -- /bin/sh -c '
            # ローカルSSDデバイスを検索する
            if [ -b /dev/disk/by-id/google-local-nvme-ssd-0 ]; then
              DEV=/dev/disk/by-id/google-local-nvme-ssd-0
            elif [ -b /dev/disk/by-id/google-local-ssd-0 ]; then
              DEV=/dev/disk/by-id/google-local-ssd-0
            else
              echo "No local SSD found"
              exit 0
            fi
            
            mkdir -p /mnt/disks/ssd0
            
            # 必要に応じてフォーマットする
            if ! blkid $DEV 2>/dev/null | grep -q ext4; then
              echo "Formatting $DEV..."
              mkfs.ext4 -F $DEV
            fi
            
            # 必要に応じてマウントする
            if ! mountpoint -q /mnt/disks/ssd0; then
              echo "Mounting $DEV to /mnt/disks/ssd0..."
              mount $DEV /mnt/disks/ssd0
            fi
            chmod 755 /mnt/disks/ssd0
            
            echo "Local SSD ready at /mnt/disks/ssd0"
            df -h /mnt/disks/ssd0
          '
        securityContext:
          privileged: true
      containers:
      - name: pause
        image: gcr.io/google-containers/pause:3.2
EOF

echo ""
echo "デーモンセットの準備が完了するまで待機中..."
sleep 15
kubectl get ds -n kube-system local-ssd-setup
kubectl get pods -n kube-system -l app=local-ssd-setup
kubectl logs -n kube-system -l app=local-ssd-setup -c setup-ssd

echo ""
echo "=========================================="
echo "✓ ローカルSSD デーモンセットのデプロイ完了！"
echo "=========================================="
echo ""
echo "重要: SSDは /mnt/disks/ssd0 にマウントされています"
echo "ClickHouseがこのパスを使用するよう設定してください"
echo "（/nvme/disk の代わりに使用します。GKE COSはルートファイルシステムが読み取り専用です）"
```

**重要な注意事項:**

* GKE Container-Optimized OS では **ルートファイルシステムが読み取り専用** のため、`/nvme` は作成できません
* ローカルSSD は `/mnt/disks/ssd0` にマウントされます
* `busybox:1.36` イメージを使用します (`apt-get` にインターネット接続は不要) 
* `nsenter` を使用して、ホストのファイルシステム上でコマンドを実行します
* 競合状態を避けるため、ClickHouse クラスターより**前に**デーモンセットをデプロイする必要があります

<div id="14-create-fips-certificates-fips-only">
  ## 14. FIPS 証明書を作成する (FIPS のみ)
</div>

**ファイル: `14-create-fips-certs.sh`** — `ENABLE_FIPS=false` の場合は、この手順をスキップしてください。

FIPS 準拠の証明書は、FIPS が有効な環境で、FIPS 承認済みアルゴリズムを使用して生成する必要があります。このスクリプトは、FIPS 暗号ポリシーを有効にした Red Hat UBI8 ポッドを GKE クラスター上で実行し、生成した証明書を `kubectl cp` を使って bastion ホストにコピーします。

**要件:**

* RSA 3072 ビット以上の鍵長
* SHA-256 以上の署名アルゴリズム
* Subject Alternative Names (SANs) にはクラスターの DNS 名を含める必要があります
* GKE クラスターへの `kubectl` アクセス (`docker` は不要) 

**証明書の種類:**

| 証明書    | ファイル                                     | 用途                      | 必要な SANs                                                                          |
| ------ | ---------------------------------------- | ----------------------- | --------------------------------------------------------------------------------- |
| CA     | `ca/ca.crt`, `ca/ca.key`                 | 認証局                     | 該当なし                                                                              |
| Server | `server/server.crt`, `server/server.key` | clickhouse-server への接続  | `*.c-${CLUSTER_NAME}-server-headless.ns-${CLUSTER_NAME}.svc.${KUBERNETES_DOMAIN}` |
| Client | `client/client.crt`, `client/client.key` | clickhouse-server からの接続 | 不要                                                                                |
| Keeper | `keeper/keeper.crt`, `keeper/keeper.key` | clickhouse-keeper への接続  | `*.c-${CLUSTER_NAME}-keeper-headless.ns-${CLUSTER_NAME}.svc.${KUBERNETES_DOMAIN}` |

このスクリプトでは、次の手順を実行します。

1. 証明書生成スクリプトを含む ConfigMap を作成します
2. OpenSSL をインストールし、`update-crypto-policies --set FIPS` で FIPS 暗号ポリシーを設定して、すべての証明書を生成する initContainer を備えた UBI8 ポッドを実行します
3. `kubectl cp` を使って証明書を bastion ホストにコピーします
4. ポッドと ConfigMap をクリーンアップします

完全なスクリプトについては、`fips/14-create-fips-certs.sh` を参照してください。

**重要な注意事項:**

* 証明書の有効期限はデフォルトで 365 日です — 必要に応じて `CERT_VALIDITY` を調整してください
* CA 証明書の有効期限は 3650 日 (10 年) です
* RSA 3072 ビット鍵 (FIPS 準拠の最小要件) を使用します
* 秘密鍵 (`*.key` ファイル) は安全に保管し、バージョン管理にコミットしないでください

<div id="15-create-certificate-secrets-fips-only">
  ## 15. 証明書シークレットの作成 (FIPS の場合のみ)
</div>

**File: `15-create-cert-secrets.sh`** — `ENABLE_FIPS=false` の場合は、この手順をスキップしてください。

FIPS 準拠の証明書を含む Kubernetes シークレットを作成します。シークレットは ClickHouse クラスターと同じネームスペースに配置する必要があります。

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "15. Creating Certificate Secrets"
echo "=========================================="

# ネームスペースが存在しない場合は作成する
kubectl create namespace ${NAMESPACE} 2>/dev/null || echo "   Namespace exists"

# サーバー証明書シークレットを作成する
echo ""
echo "Creating server certificate secret..."
kubectl create secret generic -n ${NAMESPACE} ${CLUSTER_NAME}-server-cert-secret \
  --from-file=ca.crt="${CERT_DIR}/ca/ca.crt" \
  --from-file=server.crt="${CERT_DIR}/server/server.crt" \
  --from-file=server.key="${CERT_DIR}/server/server.key" \
  --from-file=client.crt="${CERT_DIR}/client/client.crt" \
  --from-file=client.key="${CERT_DIR}/client/client.key" \
  --dry-run=client -o yaml | kubectl apply -f -
echo "   ✓ Server certificate secret created"

# Keeper 証明書シークレットを作成する
echo ""
echo "Creating keeper certificate secret..."
kubectl create secret generic -n ${NAMESPACE} ${CLUSTER_NAME}-keeper-cert-secret \
  --from-file=ca.crt="${CERT_DIR}/ca/ca.crt" \
  --from-file=keeper.crt="${CERT_DIR}/keeper/keeper.crt" \
  --from-file=keeper.key="${CERT_DIR}/keeper/keeper.key" \
  --dry-run=client -o yaml | kubectl apply -f -
echo "   ✓ Keeper certificate secret created"

echo ""
echo "=========================================="
echo "✅ Certificate Secrets Created!"
echo "=========================================="
```

**シークレットの構成:**

| Secret Name                          | Keys                                                             | Purpose               |
| ------------------------------------ | ---------------------------------------------------------------- | --------------------- |
| `${CLUSTER_NAME}-server-cert-secret` | `ca.crt`, `server.crt`, `server.key`, `client.crt`, `client.key` | サーバーのTLSおよび送信クライアント接続 |
| `${CLUSTER_NAME}-keeper-cert-secret` | `ca.crt`, `keeper.crt`, `keeper.key`                             | Keeper のTLS           |

<div id="18-bind-workload-identity-to-helm-sa">
  ## 18. Workload Identity を Helm の SA にバインドする
</div>

**ファイル: `18-bind-helm-workload-identity.sh`**

Helm チャートは独自のサービスアカウント (`ch-${CLUSTER_NAME}-sa`) を作成します。GCS にアクセスするには、この SA に Workload Identity をバインドする必要があります。

**重要:** 手順 17 で作成された keeper と server のポッドは、この Workload Identity のバインドがまだ存在しない段階で起動するため、GCS 403 Access Denied エラーで失敗します。このスクリプトは、バインド後にポッドを自動的に再起動し、新しい認証情報を反映させます。

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "18. Helm SAへのWorkload Identityのバインド"
echo "=========================================="

# Helm SAが作成されるまで待機
echo "Helmサービスアカウントが作成されるまで待機中..."
timeout=300
elapsed=0
while ! kubectl get serviceaccount ch-${CLUSTER_NAME}-sa -n ${NAMESPACE} &>/dev/null; do
  if [ $elapsed -ge $timeout ]; then
    echo "ERROR: Helmサービスアカウントの待機がタイムアウトしました"
    exit 1
  fi
  sleep 5
  elapsed=$((elapsed + 5))
  echo "  待機中... (${elapsed}s)"
done
echo "   ✓ Helmサービスアカウントが見つかりました"

# helmが作成したSAにアノテーションを付与
echo ""
echo "Helmサービスアカウントにアノテーションを付与中..."
kubectl annotate serviceaccount ch-${CLUSTER_NAME}-sa \
  -n ${NAMESPACE} \
  iam.gke.io/gcp-service-account=${GSA_EMAIL} \
  --overwrite
echo "   ✓ サービスアカウントにアノテーションを付与しました"

# Workload Identityをバインド
echo ""
echo "Workload Identityをバインド中..."
gcloud iam service-accounts add-iam-policy-binding ${GSA_EMAIL} \
  --project=${GCP_PROJECT} \
  --role=roles/iam.workloadIdentityUser \
  --member="serviceAccount:${GCP_PROJECT}.svc.id.goog[${NAMESPACE}/ch-${CLUSTER_NAME}-sa]" \
  --quiet
echo "   ✓ Workload Identityをバインドしました"

echo ""
echo "アノテーションを確認中..."
kubectl get sa ch-${CLUSTER_NAME}-sa -n ${NAMESPACE} -o yaml | grep -A3 annotations

# 新しいWorkload Identityのcredentialsを取得するためにポッドを再起動する。
# ステップ17で作成されたポッドはバインドが存在する前に起動しているため、
# GCPのcredentialsを持たず、GCSで403エラーが発生する。
echo ""
echo "Workload Identityを取得するためにkeeperおよびサーバーポッドを再起動中..."
kubectl delete pods -n ${NAMESPACE} -l clickhouseGroup=keeper --wait=false 2>/dev/null || true
kubectl delete pods -n ${NAMESPACE} -l clickhouseGroup=server --wait=false 2>/dev/null || true
echo "   ✓ ポッドを再起動しています"

echo ""
echo "keeperポッドの準備が整うまで待機中..."
kubectl wait --for=condition=ready pod \
  -l clickhouseGroup=keeper \
  -n ${NAMESPACE} \
  --timeout=600s
echo "   ✓ keeperポッドの準備が整いました"

echo ""
echo "サーバーポッドが作成されるまで待機中..."
echo "   (operatorはkeeperが正常になった後にサーバーを作成します)"
timeout=600
elapsed=0
while ! kubectl get pods -n ${NAMESPACE} -l clickhouseGroup=server -o name 2>/dev/null | grep -q .; do
  if [ $elapsed -ge $timeout ]; then
    echo "ERROR: サーバーポッドの作成待機がタイムアウトしました"
    echo "  kubectl get pods -n ${NAMESPACE}"
    exit 1
  fi
  sleep 10
  elapsed=$((elapsed + 10))
  echo "  サーバーポッドを待機中... (${elapsed}s)"
done

echo "サーバーポッドの準備が整うまで待機中..."
kubectl wait --for=condition=ready pod \
  -l clickhouseGroup=server \
  -n ${NAMESPACE} \
  --timeout=600s
echo "   ✓ サーバーポッドの準備が整いました"

echo ""
echo "=========================================="
echo "✅ Workload IdentityをHelm SAにバインドしました！"
echo "=========================================="
echo ""
kubectl get pods -n ${NAMESPACE}
```

<div id="19-verify-installation">
  ## 19. インストールを確認
</div>

**標準モード** (TLS なし) :

```bash
# ClickHouseのネイティブポートをポートフォワード
kubectl port-forward svc/c-${CLUSTER_NAME}-server-any 9000:9000 -n ${NAMESPACE} &

# clickhouse-clientで接続
clickhouse client --host localhost --port 9000 --password "${CLICKHOUSE_PASSWORD}"
```

**(FIPS) TLS モード** — `openSSL.required=true` を指定すると、ClickHouse はセキュアなポートでの接続のみを受け付けます。9000 ではなく、ポート **9440** (ネイティブ TLS) を使用してください。

```bash
# ClickHouseのセキュアなネイティブポートをポートフォワードする
kubectl port-forward svc/c-${CLUSTER_NAME}-server-any 9440:9440 -n ${NAMESPACE} &

# 自己署名証明書で接続する
clickhouse client --host localhost --port 9440 \
  --password "${CLICKHOUSE_PASSWORD}" \
  --secure \
  --accept-invalid-certificate
```

自己署名証明書を使用しているため、`--accept-invalid-certificate` フラグが必要です。適切な CA 署名済み証明書を使用する本番環境では、CA 証明書を明示的に指定してください:

```bash
clickhouse client --host localhost --port 9440 \
  --password "${CLICKHOUSE_PASSWORD}" \
  --secure \
  --config-file <(cat <<'EOF'
<config>
    <openSSL>
        <client>
            <caConfig>./certs/ca/ca.crt</caConfig>
        </client>
    </openSSL>
</config>
EOF
)
```

**テストクエリを実行する:**

```sql
SELECT 1;
```

想定される出力:

```
   ┌─1─┐
1. │ 1 │
   └───┘
1 row in set. Elapsed: 0.001 sec.
```

**重要 (FIPS) :** `openSSL.required=true` の場合、ポート9000 (平文のネイティブプロトコル) および8123 (平文HTTP) への接続は拒否されます。代わりに、ポート9440 (ネイティブTLS) または8443 (HTTPS) を使用してください。

<div id="appendix-fips-specific-considerations">
  ## 付録: FIPS 固有の考慮事項
</div>

> **注:** このセクションは、`00-env.sh` で `ENABLE_FIPS=true` を設定している場合にのみ適用されます。

<div id="certificate-requirements">
  ### 証明書の要件
</div>

FIPS 準拠には、以下が必要です。

* RSA 3072ビット以上の鍵
* FIPS で承認された署名アルゴリズム (SHA-256 以上) 
* FIPS 対応環境 (Red Hat UBI8) で生成された証明書
* 証明書チェーンの適切な検証

<div id="openssl-configuration">
  ### OpenSSL の設定
</div>

server と keeper の両方で、次の設定が必要です。

* `openSSL.enabled=true` - TLS を有効にする
* `openSSL.required=true` - TLS を必須にする (TLS 以外の接続を拒否) 
* `openSSL.selfSigned=true` - 自己署名証明書を使用する場合 (適切な CA を使用する場合は `false` に設定)

<div id="key-differences-from-standard-gcp-installation">
  ### 標準的な GCP インストールとの主な違い
</div>

| 設定                     | 標準              | FIPS                           |
| ---------------------- | --------------- | ------------------------------ |
| サーバーイメージタグ             | `25.8.1.9104`   | `25.8.1.9104-fips`             |
| Keeper イメージタグ          | `25.10.1.6624`  | `26.1.1.1493`                  |
| OpenSSL の有効化           | 未設定             | `true`                         |
| OpenSSL の必須化           | 未設定             | `true`                         |
| TLS 証明書                | 不要              | 必須 (RSA 3072 ビット)              |
| クライアント接続ポート            | `9000` (ネイティブ) | `9440` (ネイティブ TLS)            |
| HTTP ポート               | `8123`          | `8443` (HTTPS)                 |
| クライアントの `--secure` フラグ | 不要              | 必須                             |
| 自己署名証明書のフラグ            | 該当なし            | `--accept-invalid-certificate` |

<div id="certificate-verification-failures-fips">
  ### 証明書の検証失敗 (FIPS)
</div>

&quot;certificate verify failed&quot; のようなエラーが表示される場合:

1. CA証明書が正しいことを確認します:

```bash
openssl x509 -in ${CERT_DIR}/ca/ca.crt -text -noout
```

2. サーバー証明書のSANを確認します:

```bash
openssl x509 -in ${CERT_DIR}/server/server.crt -text -noout | grep -A5 "Subject Alternative Name"
```

3. シークレットの内容を確認します。

```bash
kubectl get secret ${CLUSTER_NAME}-server-cert-secret -n ${NAMESPACE} -o yaml
```

<div id="fips-mode-verification">
  ### FIPS モードの確認
</div>

生成された証明書が FIPS に準拠していることを確認します。

```bash
# 秘密鍵のサイズを確認する
openssl rsa -in ${CERT_DIR}/server/server.key -text -noout | grep "Private-Key"

# 署名アルゴリズムを確認する
openssl x509 -in ${CERT_DIR}/server/server.crt -text -noout | grep "Signature Algorithm"
```

次のように表示されるはずです。

* 秘密鍵: 3072ビット
* 署名アルゴリズム: sha256WithRSAEncryption (以上)

<div id="pods-stuck-in-pending-node-selector-issues">
  ### Pending のままのポッド - ノードセレクターの問題
</div>

```bash
kubectl get nodes --show-labels | grep clickhouseGroup

# 不足しているラベルを追加する
kubectl label node <node-name> clickhouseGroup=keeper
kubectl label node <node-name> topologyZone=c-${CLUSTER_NAME}-keeper
```

<div id="private-nodes-cannot-pull-images">
  ### プライベートノードでイメージをプルできない
</div>

Cloud NAT が構成されていることを確認します。

```bash
gcloud compute routers nats list \
```

<div id="gcs-access-denied-errors-403">
  ### GCS アクセス拒否エラー (403)
</div>

最も一般的な原因は、**Workload Identity の競合状態**です。Helm のインストール中 (ステップ 17) に、Helm が作成した SA (`ch-${CLUSTER_NAME}-sa`) への Workload Identity バインディングがステップ 18 で適用される前に、ポッドが起動してしまうことがあります。現在は、ステップ 18 でバインディング適用後にポッドを再起動するため、この問題は自動的に処理されます。

それでも 403 エラーが表示される場合:

```bash
# 1. Helmが作成したSAのWorkload Identityアノテーションを確認する
kubectl get sa ch-${CLUSTER_NAME}-sa -n ${NAMESPACE} -o yaml | grep -A5 annotations

# 2. IAMバインディングを確認する
gcloud iam service-accounts get-iam-policy ${GSA_EMAIL}

# 3. GSAのGCSバケット権限を確認する
gcloud storage buckets get-iam-policy gs://${BUCKET_NAME} | grep ${GSA_EMAIL}

# 4. ポッド内部からテストする（GSAのメールアドレスが返されるはず）
kubectl exec -it <pod-name> -n ${NAMESPACE} -- curl -s -H "Metadata-Flavor: Google" \
  http://169.254.169.254/computeMetadata/v1/instance/service-accounts/default/email

# 5. 認証情報を反映させるためポッドを再起動する（ポッド起動後にステップ18を実行した場合）
kubectl delete pods -n ${NAMESPACE} -l clickhouseGroup=keeper
kubectl delete pods -n ${NAMESPACE} -l clickhouseGroup=server
```

<div id="cannot-access-cluster-from-bastion">
  ### bastion ホスト からクラスターにアクセスできない
</div>

bastion ホスト のサブネットが許可済みネットワークに含まれていることを確認します:

```bash
gcloud container clusters describe ${GKE_CLUSTER_NAME} \
  --region=${GCP_REGION} \
  --project=${GCP_PROJECT} \
  --format="yaml(masterAuthorizedNetworksConfig)"

# bastion ホストサブネットが存在しない場合は追加する
gcloud container clusters update ${GKE_CLUSTER_NAME} \
  --region=${GCP_REGION} \
  --enable-master-authorized-networks \
  --master-authorized-networks=${SUBNET_RANGE},${BASTION_SUBNET_RANGE} \
  --project=${GCP_PROJECT}
```

<div id="connection-refused-on-port-9000-fips">
  ### ポート 9000 で接続が拒否される (FIPS)
</div>

FIPS TLS が有効な場合 (`openSSL.required=true`) 、ClickHouse は平文接続を受け付けません。ポート 9000 (Native) と 8123 (HTTP) では接続が拒否されるため、代わりにセキュアポートを使用してください。

| プロトコル  | 平文ポート | TLS ポート  |
| ------ | ----- | -------- |
| Native | 9000  | **9440** |
| HTTP   | 8123  | **8443** |

```bash
# 誤り - 接続拒否
kubectl port-forward svc/c-${CLUSTER_NAME}-server-any 9000:9000 -n ${NAMESPACE}
clickhouse client --host localhost --port 9000

# 正しい
kubectl port-forward svc/c-${CLUSTER_NAME}-server-any 9440:9440 -n ${NAMESPACE}
clickhouse client --host localhost --port 9440 --secure --accept-invalid-certificate
```

<div id="validate-ssd-cache-script">
  ### SSD Cache スクリプトの検証
</div>

`validate-ssd-cache.sh`

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "17. Validating SSD Cache Configuration"
echo "=========================================="

echo ""
echo "1. Checking DaemonSet status..."
DS_READY=$(kubectl get ds local-ssd-setup -n kube-system -o jsonpath='{.status.numberReady}')
DS_DESIRED=$(kubectl get ds local-ssd-setup -n kube-system -o jsonpath='{.status.desiredNumberScheduled}')

if [ "$DS_READY" = "$DS_DESIRED" ]; then
  echo "✅ DaemonSet ready: $DS_READY/$DS_DESIRED pods"
else
  echo "❌ DaemonSet not ready: $DS_READY/$DS_DESIRED pods"
  exit 1
fi

echo ""
echo "2. Checking ClickHouseCluster SSD configuration..."
SSD_CONFIG=$(kubectl get clickhousecluster c-${CLUSTER_NAME} -n ${NAMESPACE} -o jsonpath='{.spec.ssdCacheConfiguration}')

if echo "$SSD_CONFIG" | jq -e '.hostPathBaseDirectory == "/mnt/disks/ssd0/"' > /dev/null; then
  echo "✅ SSD cache configured in CRD:"
  echo "$SSD_CONFIG" | jq .
else
  echo "❌ SSD cache not properly configured"
  exit 1
fi

echo ""
echo "3. Waiting for server pods to be ready..."
kubectl wait --for=condition=ready pod \
  -l clickhouseGroup=server \
  -n ${NAMESPACE} \
  --timeout=300s

echo ""
echo "4. Checking pod volume mounts..."
SERVER_POD=$(kubectl get pods -n ${NAMESPACE} -l clickhouseGroup=server -o name | head -1)
echo "Checking pod: $SERVER_POD"

CACHE_MOUNT=$(kubectl get $SERVER_POD -n ${NAMESPACE} -o jsonpath='{.spec.containers[0].volumeMounts}' | jq '.[] | select(.name == "ch-cache-volume")')

if [ -n "$CACHE_MOUNT" ]; then
  echo "✅ Cache volume mounted:"
  echo "$CACHE_MOUNT" | jq .
else
  echo "❌ Cache volume not found in pod"
  exit 1
fi

echo ""
echo "5. Checking pod volume definition..."
CACHE_VOL=$(kubectl get $SERVER_POD -n ${NAMESPACE} -o jsonpath='{.spec.volumes}' | jq '.[] | select(.name == "ch-cache-volume")')

if [ -n "$CACHE_VOL" ]; then
  echo "✅ Cache volume defined:"
  echo "$CACHE_VOL" | jq .
else
  echo "❌ Cache volume not found in pod spec"
  exit 1
fi

echo ""
echo "6. Verifying cache is accessible inside container..."
if kubectl exec -n ${NAMESPACE} $SERVER_POD -- df -h /mnt/clickhouse-cache 2>/dev/null; then
  echo "✅ Cache directory accessible and mounted"
else
  echo "❌ Cache directory not accessible"
  exit 1
fi

echo ""
echo "7. Checking cache usage in ClickHouse..."
echo "Connecting to ClickHouse to verify cache configuration..."

# クライアント接続フラグを構築する
CLIENT_FLAGS=(--password="${CLICKHOUSE_PASSWORD}")
if [ "$ENABLE_FIPS" = "true" ]; then
  # FIPSモードではOpenSSLが必要 — CA証明書を検索してTLSを設定する
  CA_CERT_PATH=$(kubectl exec -n ${NAMESPACE} $SERVER_POD -- \
    find /etc -name "ca.crt" -type f 2>/dev/null | head -1)
  if [ -z "$CA_CERT_PATH" ]; then
    echo "❌ Could not find CA cert inside container"
    exit 1
  fi
  echo "Using CA cert: $CA_CERT_PATH"

  CLIENT_FLAGS+=(--secure --config-file=/tmp/ch-client-ssl.xml)
  kubectl exec -n ${NAMESPACE} $SERVER_POD -- bash -c "cat > /tmp/ch-client-ssl.xml << EOF
<clickhouse>
  <openSSL>
    <client>
      <caConfig>${CA_CERT_PATH}</caConfig>
    </client>
  </openSSL>
</clickhouse>
EOF"
fi

# ファイルシステムキャッシュの設定をクエリする（SSDキャッシュはObjectStorageディスク上の
# ファイルシステムキャッシュ層であるため、system.disksのスタンドアロンディスクとしてではなく、
# system.filesystem_cache_settingsに表示される）
CACHE_INFO=$(kubectl exec -n ${NAMESPACE} $SERVER_POD -- clickhouse-client "${CLIENT_FLAGS[@]}" -q "
SELECT
    cache_name,
    path,
    formatReadableSize(max_size) as max_size,
    formatReadableSize(current_size) as current_size,
    current_elements_num,
    is_initialized
FROM system.filesystem_cache_settings
FORMAT Vertical
" 2>/dev/null) || true

if [ -n "$CACHE_INFO" ]; then
  echo "✅ Filesystem cache active in ClickHouse:"
  echo "$CACHE_INFO"
else
  echo "⚠️  Could not query ClickHouse cache info (cluster may still be initializing)"
fi

echo ""
echo "=========================================="
echo "✅ SSD Cache Validation Complete!"
echo "=========================================="
echo ""
echo "Summary:"
echo "  • DaemonSet mounted SSD at: /mnt/disks/ssd0 (on host)"
echo "  • Operator created volume:  ch-cache-volume"
echo "  • Container mount point:    /mnt/clickhouse-cache"
echo "  • Cache size configured:    ${CACHE_BYTES_PER_GI_RAM} per GiB RAM"
echo ""
echo "The SSD cache is fully configured and operational!"
```

<div id="security-best-practices">
  ## セキュリティのベストプラクティス
</div>

1. **証明書管理** (FIPS)
   * 証明書は有効期限が切れる前にローテーションする (デフォルト: 365日) 
   * 秘密鍵は安全に保管する (シークレット管理を使用) 
   * 証明書をバージョン管理にコミットしない
   * 本番環境では適切なCA署名済み証明書を使用する

2. **ネットワークセキュリティ**
   * パブリックエンドポイントのないプライベートGKEクラスターを使用する
   * master-authorized-networks を踏み台ホストとGKEサブネットのみに制限する
   * VPCフローログを有効にする
   * 制御されたアウトバウンドアクセスのために Cloud NAT を使用する

3. **アクセス制御**
   * 静的な認証情報ではなく Workload Identity を使用する
   * Kubernetes RBAC を有効にする
   * アクセスログを定期的に監査する
   * デプロイメントにはサービスアカウントのなりすましを使用する

4. **監視**
   * 証明書の有効期限を監視する (FIPS) 
   * TLS 接続の失敗に対するアラートを設定する (FIPS) 
   * GCS のアクセスパターンを監視する
   * Cloud Audit Logging を有効にする
