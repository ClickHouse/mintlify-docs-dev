<div id="zone-details-couldnt-be-found-for-any-pv">
  ### どの PV でも zone 情報が見つからない場合
</div>

このエラーが ClickHouse Operator のログに表示される場合、PersistentVolume にトポロジー対応のノードアフィニティが自動的に設定されていることを前提としているため、operator が ClickHouse クラスターのリコンシリエーションを完了できないことを意味します。具体的には、operator は `topology.kubernetes.io/zone` ラベルに基づくノードアフィニティを探します。通常、これはトポロジー対応のボリュームプロビジョナー (たとえば AWS EBS ボリュームプロビジョナーを使用している場合) によって処理されます。

ただし、一部の Cloud プロバイダー (例: IBM) やオンプレミス環境では、これが自動的に設定されなかったり、標準以外のラベルが使われたりします。そうした場合でも operator が処理を継続できるよう、たとえば次のように storage class にノードアフィニティを追加することを推奨します。

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-nvme-sc
allowVolumeExpansion: true
parameters:
  path: /nvme/disk
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowedTopologies:
  - matchLabelExpressions:
      - key: topology.kubernetes.io/zone
        values:
          - <your_cluster_name>-keeper
          - <your_host_1>
          - <your_host_2>
          - <your_host_3>
          - <your_host_4>
          - <your_host_5>
          - <your_host_6>
      - key: directpv.min.io/zone
        values:
          - default
```

これにより、ストレージボリュームは適切なノードアフィニティで作成されます。例えば:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  ...
spec:
  accessModes:
    - ReadWriteOnce
  ...
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: directpv.min.io/zone
              operator: In
              values:
                - default
  ...
```

トポロジーの処理に標準以外のラベルを使用する場合、operator では `additionalZoneLabelRegexes` プロパティを利用できます。たとえば、operator のインストールに Helm チャートを使用している場合は、上記の PersistentVolume に一致するように `operator.additionalZoneLabelRegexes` の helm 値を `directpv.*zone` に設定できます。

<div id="what-does-the-loadbalancertype-field-on-the-clickhousecluster-crd-do">
  ### ClickHouseCluster CRD の `loadBalancerType` フィールドは何をするものですか？
</div>

`loadBalancerType` は、実際には ClickHouse クラスターの Service にロードバランサー用の annotations を追加しません。現時点では、ClickHouse Operator は ClickHouse クラスター向けのロードバランサー作成をサポートしていません。このフィールドに意味があるのは ClickHouse Cloud のみで、Cloud SQL Console 用のユーザー作成を支援するために使われます。

<div id="do-i-have-to-use-a-nvme-attached-instance-what-purpose-does-the-nvme-disk-serve">
  ### NVMe がアタッチされたインスタンスを使用する必要がありますか？NVMe ディスクは何のために使われますか？
</div>

NVMe ディスクは、ClickHouse Operator が ClickHouse server のポッドに cache ボリュームをマウントするために使用されます。この cache ボリュームは、S3 (または同等のオブジェクトストレージ) から取得されるデータの cache として使われます。ClickHouse Operator は、ClickHouse server の設定でディスクを自動的に構成します：

```yaml
s3diskWithCache:
    type: cache
    disk: s3disk
    path: /mnt/ClickHouse-cache/sharedS3DiskCache
    max_size:
    '@from_env': CONFIG_DISK_CACHE_SIZE
    cache_on_write_operations: 1
```

SharedMergeTree を使用する場合、ClickHouse が実際にデータをローカルに保存するわけではない点に注意してください。これは、SharedMergeTree に対して実行されるクエリのパフォーマンスを最適化するためだけのものです。

EC2 インスタンスを使用する場合は、たとえば AWS EBS など、ほかのストレージデバイスを使うこともできます。この場合、オンボーディングガイドのいくつかの手順が変わります。

* ClickHouse サーバーの Kubernetes ポッドをスケジュールするインスタンスに、ディスクがアタッチされていることを確認する必要があります
* ディスク構成の変更を反映するように、launch template を変更する必要があります。RAID ディスクを作成し、ディスクを ext4 または xfs でフォーマットすることは引き続き可能ですが、当然ながらデバイスの一覧表示には別のツール (例: lsblk) を使用する必要があります。
* ディスクが launch template の例のように `/nvme/disk` にマウントされていない場合は、ClickHouseCluster Helm チャートの `hostPathBaseDirectory` を実際のマウントポイントに設定する必要があります。

選択内容によっては、クエリのパフォーマンスに影響する可能性がある点に注意してください。
