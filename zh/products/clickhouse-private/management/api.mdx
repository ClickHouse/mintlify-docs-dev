<div id="introduction">
  ### 简介
</div>

<div id="starting-with-the-clickhouse-private-api">
  #### 先从 ClickHouse Private API 说起
</div>

ClickHouse Private API 支持管理 ClickHouse 集群的常见操作，例如创建备份和进行垂直扩缩容。

它是一个可独立部署的可选组件，可添加到您的环境中以简化管理。

<div id="installation">
  #### 安装
</div>

ClickHouse Private API 已打包为 Docker 镜像和 Helm 图表，必须先复制到你的私有 ECR 仓库中，再安装到你的 EKS 集群中。

<div id="prerequisites">
  ##### 前置条件
</div>

* 必须先安装 ClickHouse Operator (请参见 [通过 Helm 安装 Operator](/zh/products/clickhouse-private/deployment/aws#install-operator-via-helm))
* 至少已部署一个 ClickHouse 集群 (请参见 [ClickHouseCluster CR](/zh/products/clickhouse-private/deployment/aws#clickhousecluster-cr))
* 具有访问 ClickHouse 私有 ECR 仓库的权限
* 已在您的 AWS 账户中创建目标 ECR 仓库：
  * `airgap-management`
  * `helm/airgap-management`

<div id="copy-ecr-artifacts-for-private-api">
  ##### 为 Private API 复制 ECR 制品
</div>

**我们强烈建议使用 [skopeo](https://github.com/containers/skopeo) 复制这些镜像**，因为它会保留 Docker 镜像中的所有架构。请务必将下方的 `TARGET_REGION` 和 `TARGET_ECR_REPO` 设置为你的 ECR 区域和仓库主机。

```bash
SOURCE_REGION=us-east-1
SOURCE_ECR_REPO=349290138304.dkr.ecr.$SOURCE_REGION.amazonaws.com

TARGET_REGION=us-west-2
TARGET_ECR_REPO=0000000000.dkr.ecr.$TARGET_REGION.amazonaws.com

# 登录源 ECR
aws ecr get-login-password --region $SOURCE_REGION | skopeo login --username AWS --password-stdin $SOURCE_ECR_REPO

# 登录目标 AWS 仓库
aws ecr get-login-password --region $TARGET_REGION | skopeo login --username AWS --password-stdin $TARGET_ECR_REPO

# 将每个镜像复制到目标 ECR，请务必加上 --all 标志
skopeo copy --all docker://$SOURCE_ECR_REPO/airgap-management:<<API_TAG>> docker://$TARGET_ECR_REPO/airgap-management:<<API_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/airgap-management:<<API_HELM_TAG>> docker://$TARGET_ECR_REPO/helm/airgap-management:<<API_HELM_TAG>>
```

<div id="install-private-api-via-helm">
  ##### 通过 Helm 安装 Private API
</div>

Private API 应安装在独立的命名空间中。请根据需要更新 ECR 主机、版本标签和身份验证设置。

```bash
# 根据需要更新 ECR_HOST
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com

# 应使用 API 的 Helm 图表版本
API_HELM_VERSION=<<API_HELM_TAG>>

# 设置 API 镜像标签
API_IMAGE_TAG=<<API_TAG>>

helm install clickhouse-private-api \
   oci://$ECR_HOST/helm/airgap-management \
   --version=$API_HELM_VERSION \
   --create-namespace \
   -n clickhouse-private-api \
   --set-json="image.repository=\"$ECR_HOST/airgap-management\"" \
   --set-json="image.tag=\"$API_IMAGE_TAG\""
```

**关于身份验证的说明：**

* 默认情况下，基本身份验证处于禁用状态。在生产环境中，可以通过设置 `api.basicAuth.enabled=true` 并提供安全的凭据来启用基本身份验证。
* 用户名和密码应妥善安全存储，并根据您所在组织的安全策略定期更换。

<div id="verify-installation">
  ##### 验证安装
</div>

检查 Private API pod (容器组) 是否已运行：

```bash
kubectl get pods -n clickhouse-private-api
```

你应该会看到类似下面的输出：

```
NAME                                    READY   STATUS    RESTARTS   AGE
clickhouse-private-api-xxxxxxxxxx-xxxxx   1/1     Running   0          1m
```

通过对该服务执行端口转发，验证 API 是否可访问：

```bash
kubectl port-forward svc/clickhouse-private-api-airgap-management 8080:8080 -n clickhouse-private-api
```

测试 API 健康检查端点：

```bash
curl http://localhost:8080/readiness
```

如果启用了身份验证，请提供凭据：

```bash
curl -u admin:YOUR_SECURE_PASSWORD_HERE http://localhost:8080/readiness
```

<div id="configuration-options">
  ##### 配置选项
</div>

以下是可通过 Helm values 设置的关键配置选项：

* `image.repository`：Private API 镜像的 ECR 仓库
* `image.tag`：要部署的镜像标签
* `api.port`：API 监听的端口 (默认值：8080)
* `api.basicAuth.enabled`：启用 HTTP 基本身份验证 (默认值：false)
* `api.basicAuth.username`：基本身份验证的用户名 (默认值：&quot;admin&quot;)
* `api.basicAuth.password`：基本身份验证的密码 (默认值：&quot;changeme&quot;)
* `serviceAccount.enabled`：为 API 创建服务账号 (默认值：true)
* `serviceAccount.annotations`：服务账号的注解 (例如用于 IRSA)

有关完整的配置选项列表，请参阅 Helm 图表的 `README.md`。

<div id="tutorial-managing-backups-through-the-api">
  #### 教程：通过 API 管理备份
</div>

ClickHouse Private API 提供了相应支持，可简化备份管理。你可以使用 `api/v1/backups` REST 资源，与已部署的 ClickHouse 集群的备份进行交互。

在本指南中，我们假设你可以通过 `http://localhost:8080/` 访问该 API，例如通过对 Kubernetes pod (容器组) 进行端口转发。我们将使用 [curl](https://curl.se/) 与 API 交互并发起 HTTP 请求。我们还假设已部署了一个名为 default-xx-01 的 ClickHouse 集群 (有关如何部署 ClickHouse 集群的更多信息，请参阅[设置指南](/zh/products/clickhouse-private/deployment/aws)) 。

让我们先创建一个备份。按如下方式创建一个全量备份：

backup.json

```json
{
    "incremental": false
}
```

curl 命令

```sh
curl -X POST "http://localhost:8080/api/v1/backups?instance_id=default-xx-01" \
    -H "Content-Type: application/json" \
    --data-binary "@backup.json"
```

要指定在哪个 ClickHouse 集群上创建备份，需要使用 `instance_id` 查询参数。这里应填写部署时使用的 ClickHouse 集群名称。

这将创建全量备份，而不是增量备份，具体由请求体中的 `incremental` 字段指定。此外，还可以使用 `backupObject` 来指定要备份的表或数据库。本例中，我们使用 `type` Common，表示所有表和数据库。

响应将包含已创建备份的相关信息，其中包括一个可用于引用该备份的 UUID。

在底层，API 会在 ClickHouse 集群的命名空间内创建一个 `Backup` 对象。
ClickHouse Operator 会监视 ClickHouse 集群命名空间中的 `Backup` 对象；如果创建了新的 `Backup` 对象，operator 就会在该集群上执行相应的 Backup SQL 语句，并使用系统表监控其状态。

该备份的 UUID 可用于通过 API 监控备份状态：

```sh
curl "http://localhost:8080/api/v1/backups/{uuid}?instance_id=default-xx-01
```

这将返回备份对象，并且可以使用 `status` 字段获取有关备份的信息。如果备份已成功完成，`state` 字段将返回 `Ready`。

此外，你还可以按如下方式查看所有已创建的备份：

```sh
curl "http://localhost:8080/api/v1/backups?instance_id=default-xx-01"
```

<div id="tutorial-vertically-scaling-clickhouse-clusters-through-the-api">
  #### 教程：通过 API 对 ClickHouse 集群进行纵向扩缩容
</div>

ClickHouse Private API 支持通过调整 CPU 和内存资源，对 ClickHouse 集群进行纵向扩缩容。可通过 `api/v1/instances/{instance_id}/scale` 这一 REST 资源修改已部署 ClickHouse 集群的资源分配。

在本指南中，我们假设你可以通过 `http://localhost:8080/` 访问 API，例如通过对 Kubernetes pod (容器组) 进行端口转发。我们将使用 [curl](https://curl.se/) 与 API 交互并发起 HTTP 请求。我们还假设已经部署了一个名为 default-xx-01 的 ClickHouse 集群 (有关如何部署 ClickHouse 集群的更多信息，请参见[设置指南](/zh/products/clickhouse-private/deployment/aws)) 。

下面通过调整资源对集群进行扩缩容。按如下方式创建扩缩容请求：

scale.json

```json
{
  "vertical": {
    "resources": {
        "cpu": "4",
        "memory": "16Gi"
    }
  }
}
```

cURL 命令

```sh
curl -X POST "http://localhost:8080/api/v1/instances/default-xx-01/scale" \
    -H "Content-Type: application/json" \
    --data-binary "@scale.json"
```

要指定要扩缩容的 ClickHouse 集群，需要使用 `instance_id` 路径参数。这里使用的是部署时使用的 ClickHouse 集群名称。

`resources` 字段用于指定集群的 CPU 和内存分配。CPU 和内存都使用 Kubernetes 资源数量格式指定 (例如，&quot;4&quot; 表示 4 个 CPU 核心，&quot;16Gi&quot; 表示 16 GiB 内存) 。

**重要**：API 强制要求 CPU 与内存的比例为 1:4 (每 4 GiB 内存对应 1 个 CPU 核心) ，并允许 5% 的误差范围。如果你只提供其中一种资源类型，API 会自动推导出另一种资源，以维持该比例。例如，仅指定 `"memory": "16Gi"` 时，CPU 会自动设置为 4 个核心。

ClickHouse 在增加资源后通常能够获得很好的扩展效果，因此一般建议在考虑横向扩缩容 (Horizontal Scaling) 之前，先对 ClickHouse 进行垂直扩缩容。ClickHouse 会利用所有可用核心来提升查询性能。

在底层，API 会更新 Kubernetes 中 `ClickHouseCluster` 自定义资源的 `ServerPodPolicy`。ClickHouse Operator 会检测到这一变更，并触发对管理 ClickHouse server 的 StatefulSets 的滚动重启，以应用新的资源分配。

**重要**：与 ClickHouse Cloud 不同，在 ClickHouse Private 中，垂直扩缩容功能不使用 [Make Before Break (MBB) scaling](/zh/products/cloud/features/autoscaling/overview#how-scaling-works-in-clickhouse-cloud)。这意味着，由于会对管理 ClickHouse server 的 StatefulSets 执行滚动重启，垂直扩缩容可能会导致服务中断。

<div id="tutorial-resetting-the-main-clickhouse-user-password">
  #### 教程：重置主 ClickHouse 用户密码。
</div>

ClickHouse Private API 支持重置 ClickHouse 集群用户的密码。`api/v1/instances/{instance_id}/reset-user-password` 端点可用于更新已部署的 ClickHouse 集群上的用户凭据。

在本指南中，我们假设您可以通过 `http://localhost:8080/` 访问该 API，例如通过对 Kubernetes pod (容器组) 执行端口转发。我们将使用 [curl](https://curl.se/) 与 API 交互并发送 HTTP 请求。我们还假设已部署了一个名为 default-xx-01 的 ClickHouse 集群 (有关如何部署 ClickHouse 集群的更多详细信息，请参阅[安装指南](/zh/products/clickhouse-private/deployment/aws)) 。

**重要**：无法在 Hydra 子实例上执行密码重置。如果您需要重置 Hydra 子实例的密码，则必须改为在父实例上进行重置。

在重置密码之前，您需要先生成密码的哈希值。API 要求使用 SHA-256 (或其他受支持的哈希函数) 对密码进行哈希处理，然后再进行 base64 编码。请按如下方式生成密码哈希值：

```sh
# 这将是该用户的新密码
PASSWORD='My super secret p@$$w0rd'
HASHED_PASSWORD=$(echo -n $PASSWORD | shasum -a 256 | awk '{printf $1}' | base64)
```

现在创建一个密码重置请求。请求体中应包含密码的哈希值：

password&#95;reset.json

```json
{
  "user_hashed_password": "<base64-encoded-sha256-hash>",
  "hashing_function": "sha256",
  "username": "default"
}
```

字段如下：

* `user_hashed_password` (必填) ：新密码经 base64 编码后的哈希值
* `hashing_function` (可选) ：所使用的哈希算法。如未提供，默认为 `"sha256"`
* `username` (可选) ：要重置密码的用户名。如未提供，默认为 `"default"`

CURL 命令：

```sh
curl -X POST "http://localhost:8080/api/v1/instances/default-xx-01/reset-user-password" \
    -H "Content-Type: application/json" \
    --data-binary "@password_reset.json"
```

要指定要重置密码的 ClickHouse 集群，请使用路径参数 `instance_id`。该参数使用部署期间所用的 ClickHouse 集群名称。

如果请求成功，您将收到如下响应：

```json
{
  "message": "User password reset successfully"
}
```

实际上，API 会更新 Kubernetes 中 `ClickhouseCluster` 自定义资源里的 `CustomerAccount` 字段。ClickHouse Operator 会检测到这一变更，并相应更新 ClickHouse 集群中的用户凭证。

**注意**：密码重置会在 Operator 处理完这一变更后生效。你可以尝试使用新密码连接到集群，确认密码是否已更新。

<div id="how-to-check-the-current-state-of-a-clickhouse-cluster-and-monitor-state-transitions">
  #### 操作指南：检查 ClickHouse 集群的当前状态并监控状态转换。
</div>

ClickHouse Private API 提供了一个端点：`http://{api_base_url}/api/v1/instances/{instance_id}/status`，用于验证指定 ClickHouse 集群的当前状态。

该状态端点会返回一个包含以下字段的 JSON：

* `state`：ClickHouse 集群的当前状态。
* `previousState`：ClickHouse 集群转换前的状态。
* `message`：与状态转换相关的消息。其中包含集群为何发生上述状态转换的详细信息。
* `stateProvidedBy`：导致此次状态转换的是哪个进程。

在以下几种情况下，这个端点会很有用。例如：

* 你通过 API 触发了一次垂直扩缩容操作，并希望确认 operator 是否已完成该扩缩容操作。
* 你重置了用户密码，并希望确认 API 是否已将更改应用到整个集群。

<div id="how-to-incremental-backups">
  #### 操作指南：增量备份
</div>

增量备份可用于仅备份自上次备份以来新增的数据。这可以减少所需的总存储量

增量备份始终以备份链的形式创建，其中每个备份都引用前一个备份，并以全量备份作为起点。

可以按如下方式创建，前提是您已经创建了先前的备份：

```json
{
    "incremental": true,
    "baseBackupUuid": <uuid of previous backup>
}
```

```sh
curl -X POST "http://localhost:8080/api/v1/backups?instance_id=default-xx-01" \
    -H "Content-Type: application/json" \
    --data-binary "@backup.json"
```

要查找最近一次成功的备份并获取其 UUID，可使用 List backups API (`http://localhost:8080/api/v1/backups`)；该 API 支持通过查询参数查找最近一次成功的备份：`http://localhost:8080/api/v1/backups?instance_id=default-xx-01&status__state__eq=Ready&sort=status__effictiveFinishTime&limit=1 | jq -r '.[].id'`。

<div id="how-to-scheduling-backups">
  #### 操作指南：设置定时备份
</div>

使用 Kubernetes CronJob 即可轻松设置定时备份：

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: clickhouse-daily-backup
  namespace: clickhouse-private-api
spec:
  schedule: "0 2 * * *"  # 每天凌晨 2 点运行
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: curlimages/curl:latest
            command:
            - /bin/sh
            - -c
            - |
              curl -X POST "http://clickhouse-private-api-airgap-management:8080/api/v1/backups?instance_id=default-xx-01" \
                -H "Content-Type: application/json" \
                -d '{
                  "incremental": false
                }'
          restartPolicy: OnFailure
```

上述 CronJob 会将全量备份安排在每天凌晨 2 点执行。这里假设可通过 `http://clickhouse-private-api-airgap-management:8080` 访问 Private API。

```json
    "databases": ["mydb"],
    "tables": ["mydb2.table"]
}
```

```sh
curl -X POST "http://localhost:8080/api/v1/backups?instance_id=default-xx-01" \
    -H "Content-Type: application/json" \

```

<div id="how-to-restoring-backups">
  #### 操作指南：恢复备份
</div>

恢复 Backup 时，建议先启动一个新的 ClickHouse 集群 (按照[创建 ClickhouseCluster 资源](/zh/products/clickhouse-private/deployment/aws#clickhousecluster-cr)中的步骤操作) ，并将备份恢复到新集群中，以避免原集群过载。

API 提供了一个端点 `api/v1/backups/<uuid>/restore?instance_id=default-xx-01&target_instance_id=default-xx-02`，用于在目标实例上触发对指定备份的恢复操作。这会在目标实例上对该备份执行 `RESTORE ALL`。

出于安全考虑，此 API 不允许在同一实例上执行恢复操作。

或者，您也可以手动恢复备份，这样可以更细粒度地控制要恢复的内容。例如，对于数据库 `example`，您可以运行以下 SQL 语句：

```sql
RESTORE DATABASE example
AS example_restored
FROM S3('https://<bucket_name>.s3.amazonaws.com/backups/<uuid>')
```

这会从具有给定 uuid 的备份中恢复数据库 `example`，并将其恢复为一个名为 `example_restored` 的新数据库。

<div id="how-to-manage-the-lifecycle-of-backups-on-s3">
  #### 操作指南：管理 S3 上备份的生命周期
</div>

要管理备份的生命周期，需要考虑以下几点：

* 你希望将备份保留多长时间？例如，是否出于合规要求需要保留历史备份？你愿意为存储支付多少费用？
* 如果你创建了增量备份，就需要确保整条全量/增量备份链都可用。

一般来说，在 S3 上管理生命周期主要有两种方式：

* 使用 S3 生命周期
* 手动删除备份，例如使用 cronjob。

下面是一个 S3 生命周期策略示例：

```json
{
  "Rules": [
    {
      "ID": "ClickHouseBackupLifecycle",
      "Prefix": "backups/",
      "Status": "Enabled",
      "Transitions": [
        { "Days": 7, "StorageClass": "STANDARD_IA" },
        { "Days": 30, "StorageClass": "GLACIER_IR" }
      ],
      "Expiration": { "Days": 90 }
    }
  ]
}
```

此备份策略会在 7 天后将所有备份转移到较低的 S3 存储层级 (Intelligent Archive) ，并在 30 天后转移到 Glacier。90 天后，这些备份将被删除。

S3 生命周期策略无法监控属于备份链一部分的备份。例如，如果在上述示例中我们在 7 天后删除备份，而只每 14 天执行一次完整
备份，那么就会破坏备份链，导致备份失效。

因此，我们建议谨慎规划备份的生命周期管理方式，并且始终最好定期测试是否能够恢复这些备份。

<div id="how-to-understanding-resource-quantity-formats">
  #### 操作指南：理解资源数量格式
</div>

API 接受 Kubernetes 的 CPU 和内存资源数量格式：

**CPU 数量：**

* 整数值：`"4"` (4 个 CPU 核心)
* 小数值：`"2.5"` (2.5 个 CPU 核心)
* 毫核：`"500m"` (0.5 个 CPU 核心)

**内存数量：**

* 二进制单位：`"16Gi"` (16 GiB) 、`"4096Mi"` (4096 MiB)
* 十进制单位：`"16G"` (16 GB) 、`"16000M"` (16000 MB)

请注意，为了符合 Kubernetes 的惯例，内存建议使用二进制单位 (Ki、Mi、Gi) 。
