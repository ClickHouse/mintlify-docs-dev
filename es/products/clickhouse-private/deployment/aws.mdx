* Cree repositorios de ECR para alojar copias de nuestros artefactos en su propia instancia de ECR; esta guía asume que utilizará los nombres siguientes como nombres de sus repositorios de ECR. Utilice el tag especificado para cada artefacto.
* [Copiar artefactos de nuestro ECR a tu repositorio de ECR](#copy-ecr-artifacts)
* [Crear una VPC](#example-vpc-configuration)
* [Crear un clúster de EKS](#creating-eks-cluster)
  * Requiere los siguientes componentes:
    * Un CNI de su elección (debe usar ipv4), p. ej., [Amazon VPC CNI](https://github.com/aws/amazon-vpc-cni-k8s)
      * Si usa Amazon VPC CNI, recomendamos usar IRSA; puede seguir esta guía con las instrucciones para ipv4: [https://docs.aws.amazon.com/eks/latest/userguide/cni-iam-role.html](https://docs.aws.amazon.com/eks/latest/userguide/cni-iam-role.html)
    * Controlador CSI de EBS, p. ej., [aws-ebs-csi-driver](#install-aws-ebs-csi-driver)
    * DNS, p. ej., CoreDNS
    * Recomendado: escalado automático; puede requerir componentes como [cluster autoscaler](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/cloudprovider/aws/README.md)
  * Asociar con la VPC creada previamente
  * Grupos de nodos
    * **Todos los nodos requieren [IMDS](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instancedata-data-retrieval.html) para la autenticación**
    * Para los grupos de nodos de Keeper y de servidor, **cree un grupo de nodos por cada AZ si desea admitir cluster autoscaler** entre AZ, como se recomienda [aquí](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/FAQ.md#i-have-a-couple-of-pending-pods-but-there-was-no-scale-up); de lo contrario, pueden crearse como grupos de nodos únicos con las subredes de AZ correspondientes
    * Grupo de nodos de Keeper
      * Imagen AMI:
        * x86: AL2023&#95;x86&#95;64
        * arm64: AL2023&#95;ARM&#95;64
      * Tamaño del disco: 20gb
      * Si no usa escalado automático, el mínimo y la cantidad deseada de nodos deben ser 3 por clúster de ClickHouse
      * Tipo de instancia recomendado: `m7g.2xlarge`
      * Etiquetas de Kubernetes
        * x86: `clickhouseGroup: keeper`
        * arm64: `clickhouseGroup: keeper-arm64`
      * Taints de Kubernetes
        * `clickhouse.com/do-not-schedule: true, NoSchedule`
        * arm64: [`clickhouse.com/arch`](http://clickhouse.com/arch)`: arm64, NoSchedule`
      * Tags
        * Puede que los requiera cluster-autoscaler, si se está usando
          * Ejemplo:
            * `k8s.io/cluster-autoscaler/enabled: true`
            * `k8s.io/cluster-autoscaler/$CLUSTER_NAME: owned`
    * Grupo de nodos de servidor
      * Imagen AMI
        * x86: AL2023&#95;x86&#95;64
        * arm64: AL2023&#95;ARM&#95;64
      * Tamaño del disco: 20gb
      * [Plantilla de lanzamiento de EC2 para el grupo de nodos](#ec2-launch-template-for-node-group-server))
      * Si no usa escalado automático, el mínimo y la cantidad deseada de nodos deben ser iguales al número deseado de réplicas de ClickHouse
      * Tipo de instancia recomendado: `m7gd.16xlarge`
        * **Se recomienda encarecidamente usar una instancia de la serie &quot;d&quot;** (p. ej., `m7gd.*`), que incluye NVME SSD que ClickHouse usará como caché
          * Para las instancias con NVME SSD, use una [plantilla de lanzamiento personalizada](#ec2-launch-template-for-node-group-server) para montar automáticamente el NVME SSD
      * Etiquetas de Kubernetes
        * x86: `clickhouseGroup: server`
        * arm64: `clickhouseGroup: server-arm64`
      * Taints de Kubernetes
        * `clickhouse.com/do-not-schedule: true, NoSchedule`
        * arm64: [`clickhouse.com/arch`](http://clickhouse.com/arch)`: arm64, NoSchedule`
      * Tags
        * Puede que los requiera cluster-autoscaler, si se está usando
          * Ejemplo:
            * `k8s.io/cluster-autoscaler/enabled: true`
            * `k8s.io/cluster-autoscaler/$CLUSTER_NAME: owned`
    * Grupo de nodos x86 para ejecutar otros procesos x86 (operator, ...)
      * Puede ser un grupo de nodos existente si el clúster de EKS ya existe, siempre que sea compatible con x86 y tenga un tamaño mínimo de nodos xlarge
      * Para un grupo de nodos nuevo
        * Imagen AMI: AL2023&#95;x86&#95;64
        * Tamaño del disco: 20gb
        * Tamaño de la instancia: mínimo xlarge
        * Tipo de instancia: cualquier tipo compatible con x86
* Crear un proveedor de OIDC para el clúster de EKS
* Crear bucket de S3 (clase estándar de S3) con cifrado habilitado
  * El bucket debe estar en la misma región que el clúster de EKS
  * Puedes crear un bucket por cada clúster de ClickHouse aprovisionado, o usar un único bucket, pero en ese caso necesitas un prefijo único para cada clúster de ClickHouse (definido en el CR de ClickHouse/gráfico de Helm)
* Crear NLB, obligatorio si se requiere un Ingreso fuera del clúster de Kubernetes
  * Si se necesita un NLB**, debe aprovisionarse para cada clúster de ClickHouse**, a menos que algo como [istio](https://istio.io/) enrute las solicitudes al clúster correcto
  * Crear entradas en Route 53; esto puede hacerse de forma automatizada con algo como [external-dns](https://github.com/kubernetes-sigs/external-dns) (las instrucciones de configuración no se incluyen en este documento) mediante anotaciones de Kubernetes
* Cree roles de IAM:
  * **Los roles indicados a continuación deben usar [una política de confianza similar a esta](#example-trust-policy) (es decir, deben usar IRSA), a menos que se especifique lo contrario**
  * rol de clickhouse-server/keeper
    * **Este rol es necesario para cada clúster de ClickHouse aprovisionado**
    * La convención de nomenclatura debe ser `CH-S3-$NAME-$REGION-$ORDINAL-Role`
      * `$NAME`, nombre del clúster, por ejemplo `default-xx-01`
      * `$REGION`, identifica la región del clúster para evitar conflictos de nombres entre regiones si se usa el mismo nombre de clúster.
        * No hace falta el nombre completo de la región y podría dar como resultado un nombre de rol que supere los límites permitidos. Puedes usar un nombre abreviado como `uw2` para `us-west-2`
      * `$ORDINAL`, reservado, establecido en `00`
      * Nombre de rol de ejemplo para el servicio llamado `default-xx-01` en us-west-2: `CH-S3-default-xx-01-uw2-00-Role`
    * Permisos del bucket
      * Los permisos mínimos son: `s3:*`, `s3:ListBucket` en el recurso del bucket

  * Habilitar resolución DNS: true

<div id="copy-ecr-artifacts">
  ### Copiar artefactos de ECR
</div>

**Recomendamos encarecidamente usar [skopeo](https://github.com/containers/skopeo) para copiar las imágenes**, ya que conservará todas las arquitecturas de las imágenes de Docker. Asegúrese de configurar `TARGET_REGION` y `TARGET_ECR_REPO` que aparecen a continuación con su región y host de ECR.

```bash
SOURCE_REGION=us-east-1
SOURCE_ECR_REPO=349290138304.dkr.ecr.$SOURCE_REGION.amazonaws.com

TARGET_REGION=us-west-2
TARGET_ECR_REPO=0000000000.dkr.ecr.$TARGET_REGION.amazonaws.com

# iniciar sesión en nuestro repositorio (el proceso de autenticación puede variar según el cliente)
aws ecr get-login-password --region $SOURCE_REGION | skopeo login --username AWS --password-stdin $SOURCE_ECR_REPO

# iniciar sesión en el repositorio AWS de destino (el proceso de autenticación puede variar según el cliente)
aws ecr get-login-password --region $TARGET_REGION | skopeo login --username AWS --password-stdin $TARGET_ECR_REPO

# copiar cada imagen al ECR de destino; asegúrese de incluir el indicador --all
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-server:<<SERVER_TAG>> docker://$TARGET_ECR_REPO/clickhouse-server:<<SERVER_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-keeper:<<KEEPER_TAG>> docker://$TARGET_ECR_REPO/clickhouse-keeper:<<KEEPER_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-operator:main-<<OPERATOR_TAG>> docker://$TARGET_ECR_REPO/clickhouse-operator:<<OPERATOR_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/clickhouse-operator-helm:<<OPERATOR_TAG>> docker://$TARGET_ECR_REPO/helm/clickhouse-operator-helm:<<OPERATOR_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/onprem-clickhouse-cluster:<<CR_HELM_TAG>> docker://$TARGET_ECR_REPO/helm/onprem-clickhouse-cluster:<<CR_HELM_TAG>>
```

</div>

Requiere el rol de IAM del clúster y los roles de IAM de los nodos. Los roles creados con el botón &quot;Create recommended role&quot;, usando los permissions predeterminados en la UI de la consola de AWS, son suficientes.

<div id="cloud-formation-to-create-iam-role-to-pull-images">
  ### CloudFormation para crear un rol de IAM para extraer imágenes
</div>

Se requiere un rol de IAM para extraer imágenes de un ECR privado de ClickHouse. El rol se crea con la plantilla de CloudFormation. Una vez creado el ARN del rol, **debe proporcionar el ARN (consulte la salida) al equipo de ClickHouse**.

**CloudFormation**

```yaml expandable
AWSTemplateFormatVersion: 2010-09-09
Description: This CloudFormation template creates the ClickHouseAirgapECRPullRole.

Resources:
  ClickHouseAirgapECRPullRole:
    Type: AWS::IAM::Role
    Properties:
      RoleName: ClickHouseAirgapECRPullRole
      AssumeRolePolicyDocument:
        Version: 2012-10-17
        Statement:
          - Effect: Allow
            Principal:
              AWS: !Sub "arn:aws:iam::${AWS::AccountId}:root"
            Action:
              - sts:AssumeRole
          - Effect: Allow
            Principal:
              Service:
                - ec2.amazonaws.com
            Action:
              - sts:AssumeRole
      Policies:
        - PolicyName: ClickHouseAirgapECRPullPolicy
          PolicyDocument:
            Version: 2012-10-17
            Statement:
              - Effect: Allow
                Action:
                  - ecr:GetDownloadUrlForLayer
                  - ecr:BatchGetImage
                  - ecr:BatchCheckLayerAvailability
                  - ecr:DescribeImages
                  - ecr:ListImages
                Resource:
                  - arn:aws:ecr:us-east-1:349290138304:repository/*
              - Effect: Allow
                Action:
                  - ecr:GetAuthorizationToken
                Resource:
                  - "*"

Outputs:
  RoleArn:
    Description: IAM Role ARN for pulling images from all ECR repositories
    Value: !GetAtt ClickHouseAirgapECRPullRole.Arn

```

<div id="ec2-launch-template-for-node-group-server">
  ### Plantilla de lanzamiento de EC2 para el grupo de nodos del servidor
</div>

Antes de crear un grupo de nodos del servidor, se recomienda crear una plantilla de lanzamiento de EC2 para aprovisionar el nodo con un disco SSD para la caché de consultas de ClickHouse.

La plantilla debe contener el script que aparece a continuación. **Ten en cuenta que puede haber contenido existente en la plantilla de lanzamiento, si ya se creó previamente, que debe conservarse**. En ese caso, asegúrate de que los distintos archivos estén separados por el delimitador especificado.

**Detalles avanzados  (Datos de usuario**):

```bash expandable
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="==MYBOUNDARY=="

--==MYBOUNDARY==
Content-Type: text/x-shellscript; charset="us-ascii"

#!/bin/bash
sudo sysctl net.ipv4.tcp_fin_timeout=15
sudo sysctl net.ipv4.tcp_keepalive_time=15

function build_raid() {
set -x
mapfile -t SSD_NVME_DEVICE_LIST < <(nvme list | grep "Amazon EC2 NVMe Instance Storage" | cut -d " " -f 1 || true)
SSD_NVME_DEVICE_COUNT=${#SSD_NVME_DEVICE_LIST[@]}
RAID_DEVICE=${RAID_DEVICE:-/dev/md0}
RAID_CHUNK_SIZE=${RAID_CHUNK_SIZE:-512}              # Kilobytes
FILESYSTEM_BLOCK_SIZE=${FILESYSTEM_BLOCK_SIZE:-4096} # Bytes
STRIDE=$((RAID_CHUNK_SIZE * 1024 / FILESYSTEM_BLOCK_SIZE))
STRIPE_WIDTH=$((SSD_NVME_DEVICE_COUNT * STRIDE))
BLK_LABEL=ssdcache
MD_DEV_LABEL=dpssdcache

# Si el punto de montaje está presente en fstab - salir
grep "${BLK_LABEL}" /etc/fstab && return 0

nvme list
echo "${SSD_NVME_DEVICE_COUNT}" "${SSD_NVME_DEVICE_LIST[*]}"

# Realizar el aprovisionamiento según el número de dispositivos nvme
case  "${SSD_NVME_DEVICE_COUNT}" in
"0")
  echo 'No devices found of type "Amazon EC2 NVMe Instance Storage"'
  echo "Maybe your node selectors are not set correct"
  return 0
  ;;
"1")
  mkfs.ext4 -L "${BLK_LABEL}" -m 0 -b "${FILESYSTEM_BLOCK_SIZE}" "${SSD_NVME_DEVICE_LIST[0]}"
  ;;
*)
  mdadm --create --verbose "${RAID_DEVICE}" --name="${MD_DEV_LABEL}" --level=0 -c "${RAID_CHUNK_SIZE}" \
    --raid-devices="${#SSD_NVME_DEVICE_LIST[@]}" "${SSD_NVME_DEVICE_LIST[@]}"

  while mdadm --detail "${RAID_DEVICE}" | grep -q -ioE 'State :.*resyncing'
  do
    echo "Raid is resyncing.."
    sleep 1
  done
  echo "Raid0 device  ${RAID_DEVICE} has been created with disks  ${SSD_NVME_DEVICE_LIST[*]}"
  mkfs.ext4 -L "${BLK_LABEL}" -m 0 -b "${FILESYSTEM_BLOCK_SIZE}" -E "stride=${STRIDE},stripe-width=${STRIPE_WIDTH}" "${RAID_DEVICE}"
  ;;
esac

# Montarlo y añadir a fstab
# Se usa UUID para ser compatible con la herramienta de aprovisionamiento EKS NVME
DEV_NAME=$(blkid -s UUID -o value -L "${BLK_LABEL}")
UUID=$(blkid -s UUID -o value "${DEV_NAME}")
# Verificar que UUID está definido
test -z ${UUID} && return 1
mkdir -p /pv-disks/"${UUID}" /nvme/
test -h /nvme/disk || ln -fs /pv-disks/"${UUID}" /nvme/disk

cat<<EOF | tee -a /etc/fstab

LABEL=${BLK_LABEL} /pv-disks/${UUID} ext4 defaults,noatime,discard,nobarrier  0 0
EOF
mount -a
set +x
}

yum install -y nvme-cli mdadm
build_raid
mountpoint /nvme/disk/ || systemctl stop kubelet

--==MYBOUNDARY==--
```

<div id="install-storageclass-via-helm">
  ### Instalar StorageClass mediante Helm
</div>

Si se necesita una StorageClass, se recomienda instalar estas dependencias de clickhouse-operator por separado de la creación del CR real de clickhousecluster, mediante el gráfico de Helm proporcionado, para que, si se crean varios CR, las dependencias no queden vinculadas a ningún clúster y no se eliminen si ese clúster se borra. **Este paso solo es necesario si no dispone de un CR de StorageClass personalizado o existente** que tenga previsto usar para clickhouser-server y clickhouse-keeper.

```bash
# actualizar ECR_HOST según sea necesario
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
CHART_VERSION=<<CR_HELM_TAG>>

helm install clickhouse-prerequisites \
    oci://$ECR_HOST/helm/onprem-clickhouse-cluster \
    --version=$CHART_VERSION \
    -n default \
    --set-json="storageClass.create=true" \
    --set-json="createCluster=false" \
    --set-json="serviceAccount.create=false"
```

<div id="install-operator-via-helm">
  ### Instale el operador con Helm
</div>

Actualice la versión, el host de ECR y las zonas de disponibilidad (según la VPC creada) según corresponda.

```bash expandable
# actualizar ECR_HOST según sea necesario
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com

# se debe usar la versión del gráfico de Helm del operador, no la del operador en sí (p. ej. <<OPERATOR_TAG>>, no main.<<OPERATOR_TAG>>)
OPERATOR_VERSION=<<OPERATOR_TAG>>

# establecer las AZs según las subredes de la VPC
AZ_LIST='["us-west-2a","us-west-2b","us-west-2c"]'

helm install clickhouse-operator \
   oci://$ECR_HOST/helm/clickhouse-operator-helm \
   --version=$OPERATOR_VERSION \
   --create-namespace \
   -n clickhouse-operator-system \
   --set-json="image.repository=\"$ECR_HOST/clickhouse-operator\"" \
   --set-json='cilium.enabled=false' \
   --set-json='idleScalerEnabled=false' \
   --set-json='webhooks.enabled=false' \
   --set-json='operator.debug=true' \
   --set-json='operator.metricsScraper.enabled=false' \
   --set-json="operator.availabilityZones=$AZ_LIST" \
   --set-json='operator.featureFlags.backupOnASeparatePod=true' \
   --set-json='operator.featureFlags.serverCMEKEnabled=true'
```

<div id="install-aws-ebs-csi-driver">
  ### Instalar aws-ebs-csi-driver
</div>

Requiere un rol de IAM con lo siguiente:

* Use la política administrada `arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy`
* Para la política de confianza, se recomienda usar sts:AssumeRoleWithWebIdentity con el proveedor OIDC del cluster de EKS ([ejemplo](#example-trust-policy))
* El nombre del rol seleccionado debe coincidir con la anotación de la cuenta de servicio que ejecuta aws-ebs-csi-driver
  * Nombre de ejemplo: `ClickHouse_EksEbsCsiDriverRole`

Siga la guía de [instalación con helm](https://github.com/kubernetes-sigs/aws-ebs-csi-driver/blob/master/docs/install.md#helm) con valores adicionales para adjuntar el rol de IAM a la cuenta de servicio:

```bash
# actualizar el nombre del rol según sea necesario
AWS_EBS_CSI_DRIVER_IAM_ROLE_ARN=arn:aws:iam::0000000000:role/ClickHouse_EksEbsCsiDriverRole

helm upgrade --install aws-ebs-csi-driver \
--namespace kube-system \
aws-ebs-csi-driver/aws-ebs-csi-driver \
--set-json="controller.serviceAccount.annotations={\"eks.amazonaws.com/role-arn\":\"$AWS_EBS_CSI_DRIVER_IAM_ROLE_ARN\"}"
```

<div id="naming-your-clickhouse-cluster">
  ### Cómo nombrar su clúster de ClickHouse
</div>

Para cada clúster de ClickHouse que se vaya a aprovisionar, seleccione un **nombre de clúster único** dentro del clúster de EKS de destino. Este nombre se utilizará en varios recursos de AWS y Kubernetes, y servirá para identificar de forma única el clúster.

1. La convención de nomenclatura debe ser `$DESCRIPTOR-$LETTERS-$ORDINAL`
   1. $DESCRIPTOR - algún nombre descriptivo del clúster compuesto únicamente por letras
   2. $LETTERS - reservado; seleccione dos letras cualesquiera; por simplicidad, `xx` funciona
   3. $ORDINAL - ordinal incremental para clústeres con el mismo descriptor, comenzando por `01`
2. Nombre de ejemplo: `default-xx-01`

<div id="clickhousecluster-cr">
  ### CR de ClickHouseCluster
</div>

Ten en cuenta que los valores siguientes deben revisarse y actualizarse para un entorno de producción (p. ej., recursos, feature flags, configuraciones del servidor, ...). Consulta la [sección sobre la nomenclatura](#naming-your-clickhouse-cluster) antes de establecer `CLUSTER_NAME`.
Genera el hash de la contraseña correspondiente a `$PASSWORD` con el siguiente comando (OS X) y luego pásalo al valor `account.hashedPassword` del gráfico de Helm:

```bash expandable
# esta será la contraseña del usuario `default`
PASSWORD='My super secret p@$$w0rd'
HASHED_PASSWORD=`echo -n $PASSWORD | shasum -a 256 | awk '{printf $1}' | base64`

# actualice los valores a continuación según sea necesario,
# el host de ecr debe ser el de su cuenta
# el bucket de s3 debe ser el creado anteriormente
CLUSTER_NAME=default-xx-01
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
SA_IAM_ROLE_ARN=arn:aws:iam::0000000000:role/CH-S3-${CLUSTER_NAME}-uw2-00-Role
S3_BUCKET_NAME=my-clickhouse-data

# el prefijo de clave de s3 puede usar cualquier valor UUID, pero debe ser único para todos los clústeres que almacenen datos en el bucket especificado anteriormente
S3_KEY_PREFIX=ch-s3-$(uuidgen | tr '[:upper:]' '[:lower:]')

# estos deben coincidir con el valor de la etiqueta clickhouseGroup añadida al grupo de nodos
SERVER_NG_GROUP=server-arm64
KEEPER_NG_GROUP=keeper-arm64

# estos valores deben ajustarse según los tamaños de instancia seleccionados
# asegúrese de tener en cuenta los requisitos del daemon set al configurar los valores de CPU y MEMORY
SERVER_CPU=64
SERVER_MEMORY=256Gi
KEEPER_CPU=4
KEEPER_MEMORY=16Gi

CHART_VERSION=<<CR_HELM_TAG>>

# bytesPerGiRAM es un factor de escala utilizado para calcular automáticamente el tamaño de la caché en disco.
# Como regla general, establezca el tamaño de la caché en el 80-90% del tamaño disponible del disco de caché SSD.
# Cuando establece bytesPerGiRAM en el gráfico de Helm, se utiliza la siguiente fórmula durante el inicio del pod:
#
# CONFIG_DISK_CACHE_SIZE = bytesPerGiRAM * pod_memory_limit
#
# Por ejemplo:
# bytesPerGiRAM = 11.3Gi
# pod_memory_limit = 250Gi
# CONFIG_DISK_CACHE_SIZE = 11.3 * 250 = 2825Gi
CACHE_BYTES_PER_GI_RAM=11Gi

helm install $CLUSTER_NAME \    oci://$ECR_HOST/helm/onprem-clickhouse-cluster \
    --version=$CHART_VERSION \
    -n ns-$CLUSTER_NAME \
    --create-namespace \
    --set-json="account.hashedPassword=\"$HASHED_PASSWORD\"" \
    --set-json="server.image.repository=\"$ECR_HOST/clickhouse-server\"" \
    --set-json="server.storage.s3.bucketName=\"$S3_BUCKET_NAME\"" \
    --set-json="server.storage.s3.keyPrefix=\"$S3_KEY_PREFIX\"" \
    --set-json='server.arm64=true' \
    --set-json="server.image.tag=\"<<SERVER_TAG>>\"" \
    --set-json="server.podPolicy.nodeSelector.clickhouseGroup=\"$SERVER_NG_GROUP\"" \
    --set-json="keeper.image.repository=\"$ECR_HOST/clickhouse-keeper\"" \
    --set-json='keeper.arm64=true' \
    --set-json="keeper.image.tag=\"<<KEEPER_TAG>>\"" \
    --set-json="keeper.podPolicy.nodeSelector.clickhouseGroup=\"$KEEPER_NG_GROUP\"" \
    --set-json="serviceAccount.annotations={\"eks.amazonaws.com/role-arn\":\"$SA_IAM_ROLE_ARN\"}" \
    --set-json='server.tolerations=[{"effect":"NoSchedule","key":"clickhouse.com/do-not-schedule","operator":"Exists"}]' \
    --set-json='keeper.tolerations=[{"effect":"NoSchedule","key":"clickhouse.com/do-not-schedule","operator":"Exists"}]' \
    --set-json="server.ssdCacheConfiguration.bytesPerGiRAM=\"$CACHE_BYTES_PER_GI_RAM\"" \
    --set-json="server.podPolicy.resources.limits.cpu=\"$SERVER_CPU\"" \
    --set-json="server.podPolicy.resources.limits.memory=\"$SERVER_MEMORY\"" \
    --set-json="server.podPolicy.resources.requests.cpu=\"$SERVER_CPU\"" \
    --set-json="server.podPolicy.resources.requests.memory=\"$SERVER_MEMORY\"" \
    --set-json="keeper.podPolicy.resources.limits.cpu=\"$KEEPER_CPU\"" \
    --set-json="keeper.podPolicy.resources.limits.memory=\"$KEEPER_MEMORY\"" \
    --set-json="keeper.podPolicy.resources.requests.cpu=\"$KEEPER_CPU\"" \
    --set-json="keeper.podPolicy.resources.requests.memory=\"$KEEPER_MEMORY\""
```

<div id="hydra-setup">
  ## Configuración de Hydra
</div>

La idea es crear varios grupos de nodos dentro de un clúster de ClickHouse. Cada uno de esos grupos de nodos tendrá un número diferente de nodos (con distintas cantidades de memoria) y un endpoint independiente. Estos grupos de nodos tendrán una única instancia de Keeper y un único conjunto de datos / carpeta en el bucket compartido de S3.

<div id="provisioning-hydra-children-instances">
  ### Aprovisionar instancias secundarias de Hydra
</div>

<div id="prerequisites">
  ##### Requisitos previos
</div>

El operador debe estar [instalado](#install-operator-via-helm) con la función Hydra habilitada mediante la siguiente configuración (el valor predeterminado es false):

```bash
--set operator.featureFlags.privateHydraEnabled="true"
```

<div id="setup">
  ##### Configuración
</div>

*Antes de crear instancias secundarias, debes elegir un clúster principal de ClickHouse existente o crear uno nuevo, por lo que debes conocer de antemano el **nombre** y el **espacio de nombres** del clúster principal que usarán las secundarias.*

Para crear un nuevo servicio secundario, sigue las [mismas instrucciones](#clickhousecluster-cr) para crear un servicio y simplemente agrega nuevos valores de Helm al crear el recurso personalizado (CR) `ClickHouseCluster`:

```bash
--set-json='parentCluster.name="c-${PARENT_NAME}'"'
--set-json='parentCluster.namespace="ns-'${PARENT_NAME}'"'
```

**PARENT&#95;NAME** - nombre del clúster padre de ClickHouse, existente o nuevo.

Opcionalmente, si quieres que el nuevo secundario sea de solo lectura (por defecto, `false`), puedes añadir:

```bash
--set-json='isReadonly=true'
```

<div id="limitations">
  ### Limitaciones
</div>

1. No puedes aprovisionar instancias secundarias si la instancia principal está detenida, terminada o inactiva.
2. Si quieres eliminar el clúster principal, primero debes eliminar las instancias secundarias.

<div id="install-validation">
  ## Verificación de la instalación
</div>

<div id="preflight-checks">
  ### Comprobaciones previas
</div>

Hay una comprobación previa opcional mediante [Troubleshoot](https://troubleshoot.sh/), un complemento de Kubernetes para diagnosticar clústeres.

Para instalar los complementos necesarios, puedes usar Krew:

```console
kubectl krew install preflight
```

o consulta la [documentación](https://troubleshoot.sh/docs/) de Troubleshoot para ver otras opciones de instalación.

ClickHouse ofrece un gráfico de Helm (`helm/preflight-check`) que puede copiarse a tu ECR y renderizarse localmente para generar la especificación de preflight, que luego se pasa a `kubectl preflight`.

<div id="copying-the-preflight-check-helm-chart">
  ##### Copiar el gráfico de Helm de comprobación previa
</div>

Añade el gráfico de comprobación previa al [paso de copia en ECR](#copy-ecr-artifacts):

```bash
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/preflight-check:<<PREFLIGHT_CHART_TAG>> docker://$TARGET_ECR_REPO/helm/preflight-check:<<PREFLIGHT_CHART_TAG>>
```

<div id="running-the-preflight-checks">
  ##### Ejecutar las comprobaciones previas
</div>

Usa `helm template` para generar la especificación de preflight y luego pásala directamente a `kubectl preflight`. Establece `CLUSTER_NAME` con el nombre del clúster de ClickHouse que quieras validar (consulta [Naming Your ClickHouse Cluster](#naming-your-clickhouse-cluster)):

```bash
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
CHART_VERSION=<<PREFLIGHT_CHART_TAG>>
CLUSTER_NAME=default-xx-01

helm template clickhouse-preflight \
    oci://$ECR_HOST/helm/preflight-check \
    --version=$CHART_VERSION \
    --set preflight.clickhouseClusterName=$CLUSTER_NAME | \
kubectl preflight -
```

Esto valida los requisitos para ejecutar ClickHouse Operator y desplegar un clúster de ClickHouse. Comprueba si las etiquetas de nodo necesarias están
presentes, si la Storage Class está configurada correctamente, etc.

La salida muestra las distintas comprobaciones previas y su estado:
![Ejemplo de comprobación previa](/products/clickhouse-private/images/preflight-example.png)

Puede revisar la salida y comprobar que cada verificación se haya completado correctamente. Si una verificación falla, indica un problema (potencial) en la configuración que puede causar
problemas al ejecutar correctamente un clúster de ClickHouse. Las comprobaciones incluyen recomendaciones sobre qué hacer para solucionar el problema.

Para validar con una Storage Class distinta de la predeterminada (`gp3-encrypted`), sustitúyala con una marca `--set` adicional:

```bash
    --set preflight.checks.prerequisites.storageClassName=<your-storage-class>
```

<div id="required-permissions">
  ##### Permisos requeridos
</div>

El usuario o la cuenta de servicio que ejecuta `kubectl preflight` debe poder leer recursos de nivel de clúster y de nivel de espacio de nombres. Como mínimo, se requiere el siguiente acceso:

| Alcance                                                        | Recursos                                                                                  |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| En todo el clúster                                             | `nodes`, `namespaces`, `persistentvolumes`, `storageclasses`, `customresourcedefinitions` |
| Espacio de nombres del operador (`clickhouse-operator-system`) | `deployments`, `replicasets`, `pods`, `services`, `configmaps`, `events`                  |
| Espacio de nombres del clúster (`ns-<cluster-name>`)           | `statefulsets`, `pods`, `persistentvolumeclaims`, `services`, `configmaps`, `events`      |

En la práctica, basta con una identidad que tenga el Rol de clúster integrado `view` y acceso `view` a los espacios de nombres pertinentes. Una vinculación `cluster-admin` también funcionará y es más sencilla de configurar para ejecuciones puntuales de validación.

<div id="port-forward-the-clickhouse-service-to-your-local-machine">
  ### Reenvía los puertos del servicio ClickHouse a tu máquina local
</div>

Para reenviar el tráfico desde tu máquina local al servicio c-default-xx-01-server-any, ejecuta:

```bash
kubectl port-forward svc/c-default-xx-01-server-any 9000:9000 -n ns-default-xx-01
```

Esto redirigirá el puerto `9000` del servicio al puerto `9000` de tu equipo local. Ahora puedes acceder a la interfaz HTTP de ClickHouse en `http://localhost:9000`.

<div id="access-clickhouse-and-run-query">
  ### Acceda a ClickHouse y ejecute una consulta
</div>

Una vez redirigido el puerto, puede conectarse a ClickHouse localmente con una herramienta como clickhouse-client.

```bash
clickhouse client --host localhost --port 9000 --password $PASSWORD
```

y ejecute una consulta sencilla:

```sql
clickhouse-cloud :) select 1;
```

Deberías ver una salida como esta:

```text

1. │ 1  │
   └───┘
1 row in set. Elapsed: 0.001 sec.
```
