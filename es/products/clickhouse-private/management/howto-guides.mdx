Esta sección contiene guías para las configuraciones más comunes de ClickHouse en entornos privados.

<div id="how-to-configure-cert-manager-to-generate-the-certificates-for-clickhouse-server-keeper">
  ### Guía práctica: Configurar Cert Manager para generar los certificados de ClickHouse Server y Keeper
</div>

Esta guía da por hecho que [Cert Manager](https://cert-manager.io/) ya está instalado en el clúster. Además, asume que el clúster de ClickHouse se llama `default-xx-01`.

Primero necesitamos una autoridad de certificación (CA) para firmar los certificados:

```yaml
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: selfsigned-issuer
spec:
  selfSigned: {}
```

Para simplificar, usamos un `Issuer` autofirmado, ya que esto generará una CA válida. Esto es solo para pruebas; para un `Issuer` de nivel de producción, recomendamos consultar la [lista de opciones](https://cert-manager.io/docs/configuration/issuers/).

Después, podemos crear un certificado con el recurso `Certificate`:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: clickhouse-server-tls
  namespace: ns-default-xx-01
spec:
  secretName: default-xx-01-server-cert-secret
  dnsNames:
    - "*.default-xx-01.ns-default-xx-01.svc.cluster.local"
  issuerRef:
    name: selfsigned-issuer
    kind: Issuer
```

Esto creará un secreto con el nombre `default-xx-01-server-cert-secret` y con las claves `ca.crt`, `tls.crt` y `tls.key`.

Ten en cuenta que `ca.crt` solo se agrega si está disponible a través del emisor. Por ejemplo, con ACME no se agrega ningún `ca.crt` al secreto. En este caso, la raíz pública debe añadirse al valor de la clave `ca.crt` (por ejemplo, usando [trust-manager](https://cert-manager.io/docs/trust/trust-manager/) para generar el bundle de la CA y apuntar al secreto correcto).

De forma predeterminada, el gráfico de Helm onprem-ClickHouse-cluster espera un secreto con el nombre `<cluster_name>-server-cert-secret` con las claves `ca.crt`, `server.crt` y `server.key`.

Se pueden usar los siguientes valores para garantizar que el clúster de ClickHouse cargue los certificados desde las claves correctas del secreto:

```yaml
# Usar el nombre de secreto predeterminado (default-xx-01-server-cert-secret) - no es necesario especificarlo
server:
  openSSL:
    enabled: true
    secret:
      caKey: ca.crt
      certKey: tls.crt
      keyKey: tls.key
```

Los certificados se montan en los pods en `/etc/ClickHouse-server/certs/` para ClickHouse Server o en `/etc/clickhouse-keeper/certs/` para ClickHouse Keeper.
El gráfico de Helm genera la configuración correcta de OpenSSL para ClickHouse.

<div id="how-to-configure-remote_servers-with-secretkeyref-and-from_env">
  ### Guía práctica: configurar remote_servers con secretKeyRef y @from_env
</div>

> Necesitarás al menos la versión `1.1.151` del gráfico de Helm `onprem-clickHouse-cluster` para configurar la opción `remote_servers` de ClickHouse Server

Esta guía muestra cómo configurar [`remote_servers`](/es/reference/settings/server-settings/settings#remote_servers) para usarlo con tablas distribuidas y la función cluster(). Esta guía asume que el clúster de ClickHouse se llama `default-xx-01` y que existe un [secreto](https://kubernetes.io/docs/concepts/configuration/secret/) llamado `default-xx-01-password` en el espacio de nombres del clúster.

> Nota: Si integra almacenes de secretos externos, puede seguir un enfoque similar con [Kubernetes Secrets Store CSI Driver](https://github.com/kubernetes-sigs/secrets-store-csi-driver) para montarlo y [cargar el secreto como variable de entorno](https://secrets-store-csi-driver.sigs.k8s.io/topics/set-as-env-var).

El enfoque recomendado utiliza [secretos de Kubernetes con `secretKeyRef`](https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/#define-container-environment-variables-using-secret-data) para inyectar datos confidenciales como variables de entorno y, después, hace referencia a esas variables en la configuración de ClickHouse mediante [`@from_env`](/es/concepts/features/configuration/server-config/configuration-files#from_env_zk).

Ejemplo:

```yaml
server:
  additionalEnvVars:
    - name: DEFAULT_XX_01_PASSWORD
      valueFrom:
        secretKeyRef:
          name: default-xx-01-password
          key: password
  config:
    remote_servers:
      default-xx-01:
        shard:
          - replica:
              user: default
              password:
                "@from_env": DEFAULT_XX_01_PASSWORD
              host: c-default-xx-01-server-0r280c0-0.c-default-xx-01-server-headless.ns-default-xx-01.svc.cluster.local
              port: 9000
          - replica:
              user: default
              password:
                "@from_env": DEFAULT_XX_01_PASSWORD
              host: c-default-xx-01-server-f9cshqb-0.c-default-xx-01-server-headless.ns-default-xx-01.svc.cluster.local
              port: 9000
          - replica:
              user: default
              password:
                "@from_env": DEFAULT_XX_01_PASSWORD
              host: c-default-xx-01-server-gsip6lp-0.c-default-xx-01-server-headless.ns-default-xx-01.svc.cluster.local
              port: 9000
```

Este patrón garantiza que los datos sensibles no se incluyan directamente en plantillas dentro de los manifiestos. El campo `additionalEnvVars` define variables de entorno a partir de secretos de Kubernetes mediante `secretKeyRef`, y la directiva `@from_env` en la configuración de ClickHouse carga esos valores en tiempo de ejecución.

Ten en cuenta que el formato FQDN de los hosts de las réplicas sigue el patrón de Kubernetes: `<pod-name>.<headless-service-name>.<namespace>.svc.cluster.local`.
