<div id="zone-details-couldnt-be-found-for-any-pv">
  ### ¿No se pudo encontrar información de zona para ningún PV?
</div>

Si este error aparece en los logs del ClickHouse Operator, significa que no puede completar la reconciliación del clúster de ClickHouse porque espera que las afinidades de nodo con reconocimiento de topología se rellenen automáticamente en los PersistentVolumes. En concreto, el operador busca afinidades de nodo basadas en la etiqueta `topology.kubernetes.io/zone`. Normalmente, esto lo gestionan los aprovisionadores de volúmenes con reconocimiento de topología (por ejemplo, al usar el aprovisionador de volúmenes de AWS EBS).

Sin embargo, en algunos proveedores de nube (p. ej., IBM) o en entornos on-premise, esto no se rellena automáticamente o se usan etiquetas no estándar. Para garantizar que el operador pueda seguir funcionando, se recomienda añadir las afinidades de nodo en la clase de almacenamiento, por ejemplo:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-nvme-sc
allowVolumeExpansion: true
parameters:
  path: /nvme/disk
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowedTopologies:
  - matchLabelExpressions:
      - key: topology.kubernetes.io/zone
        values:
          - <your_cluster_name>-keeper
          - <your_host_1>
          - <your_host_2>
          - <your_host_3>
          - <your_host_4>
          - <your_host_5>
          - <your_host_6>
      - key: directpv.min.io/zone
        values:
          - default
```

Esto garantizará que los volúmenes de almacenamiento se creen con las afinidades de nodo adecuadas. Por ejemplo:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  ...
spec:
  accessModes:
    - ReadWriteOnce
  ...
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: directpv.min.io/zone
              operator: In
              values:
                - default
  ...
```

Si se usan etiquetas no estándar para gestionar la topología, el operador expone una propiedad `additionalZoneLabelRegexes`. Por ejemplo, si está usando el gráfico de Helm para instalar el operador, puede establecer el valor de helm `operator.additionalZoneLabelRegexes` en `directpv.*zone` para que coincida con el PersistentVolume anterior.

<div id="what-does-the-loadbalancertype-field-on-the-clickhousecluster-crd-do">
  ### ¿Qué hace el campo `loadBalancerType` en el CRD de ClickHouseCluster?
</div>

En realidad, `loadBalancerType` no agrega annotations de balanceador de carga al Service del clúster de ClickHouse. Actualmente, ClickHouse Operator no admite crear un balanceador de carga para el clúster de ClickHouse. Este campo solo tiene utilidad en ClickHouse Cloud, donde se usa para facilitar la creación de usuarios para la SQL Console de Cloud.

<div id="do-i-have-to-use-a-nvme-attached-instance-what-purpose-does-the-nvme-disk-serve">
  ### ¿Tengo que usar una instancia con NVMe adjunto? ¿Para qué sirve el disco NVMe?
</div>

El disco NVMe lo utiliza el ClickHouse Operator para montar un volumen de caché en los pods del servidor ClickHouse. Este volumen de caché se utiliza para almacenar en caché los datos procedentes de S3 (u otros almacenamientos de objetos equivalentes). El operador configura automáticamente los discos en la configuración del servidor ClickHouse:

```yaml
s3diskWithCache:
    type: cache
    disk: s3disk
    path: /mnt/ClickHouse-cache/sharedS3DiskCache
    max_size:
    '@from_env': CONFIG_DISK_CACHE_SIZE
    cache_on_write_operations: 1
```

Ten en cuenta que, si usas SharedMergeTree, ClickHouse en realidad no almacena datos localmente. Su única finalidad es optimizar el rendimiento de las consultas que se ejecutan sobre SharedMergeTree.

Es posible usar otros dispositivos de almacenamiento, como por ejemplo AWS EBS al usar instancias de EC2. Esto cambia algunos pasos de la guía de incorporación:

* Debes asegurarte de que los discos estén conectados a las instancias utilizadas para programar los pods de Kubernetes del servidor ClickHouse
* La plantilla de lanzamiento debe modificarse para reflejar los cambios en la arquitectura de disco. Sigue siendo posible crear un disco RAID y formatearlo como ext4 o xfs, pero, obviamente, los dispositivos deben enumerarse con otra herramienta (por ejemplo, lsblk).
* Si los discos no están montados en `/nvme/disk`, como en la plantilla de lanzamiento de ejemplo, `hostPathBaseDirectory` en el gráfico de Helm de ClickHouseCluster debe establecerse en el punto de montaje real.

Ten en cuenta que, según las opciones que elijas, puedes afectar al rendimiento de las consultas.
