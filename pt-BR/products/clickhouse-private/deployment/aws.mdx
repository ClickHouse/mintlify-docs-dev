  ### Recursos da AWS
</div>

* [Criar função do IAM para baixar imagens de um ECR privado do ClickHouse](#cloud-formation-to-create-iam-role-to-pull-images)
* Crie repositórios no ECR para hospedar cópias dos nossos artefatos no seu próprio ECR; este guia pressupõe que você usará os nomes abaixo como nomes dos seus repositórios no ECR. Use a tag especificada para cada artefato.
* [Copie os artefatos do nosso ECR para o seu repositório no ECR](#copy-ecr-artifacts)
* [Criar uma VPC](#example-vpc-configuration)
* [Criar cluster do EKS](#creating-eks-cluster)
  * Requer os seguintes componentes:
    * CNI de sua escolha (deve usar ipv4), por exemplo [Amazon VPC CNI](https://github.com/aws/amazon-vpc-cni-k8s)
      * Se estiver usando Amazon VPC CNI, recomendamos usar IRSA; você pode seguir este guia usando as instruções de ipv4: [https://docs.aws.amazon.com/eks/latest/userguide/cni-iam-role.html](https://docs.aws.amazon.com/eks/latest/userguide/cni-iam-role.html)
    * Driver CSI do EBS, por exemplo [aws-ebs-csi-driver](#install-aws-ebs-csi-driver)
    * DNS, por exemplo CoreDNS
    * Recomendado: escalonamento automático, que pode exigir componentes como [cluster autoscaler](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/cloudprovider/aws/README.md)
  * Associe à VPC criada anteriormente
  * Grupos de nós
    * **Todos os nós exigem [IMDS](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instancedata-data-retrieval.html) para autenticação**
    * Para os grupos de nós keeper e server, **crie um grupo de nós por AZ se quiser dar suporte ao cluster autoscaler** entre AZs, conforme recomendado [aqui](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/FAQ.md#i-have-a-couple-of-pending-pods-but-there-was-no-scale-up); caso contrário, eles podem ser criados como um único grupo de nós com as sub-redes de AZ apropriadas
    * Grupo de nós Keeper
      * Imagem AMI:
        * x86: AL2023&#95;x86&#95;64
        * arm64: AL2023&#95;ARM&#95;64
      * Tamanho do disco: 20gb
      * Se não estiver usando escalonamento automático, as quantidades mínima e desejada de nós devem ser 3 por cluster do ClickHouse
      * Tipo de instância recomendado: `m7g.2xlarge`
      * Labels do Kubernetes
        * x86: `clickhouseGroup: keeper`
        * arm64: `clickhouseGroup: keeper-arm64`
      * Taints do Kubernetes
        * `clickhouse.com/do-not-schedule: true, NoSchedule`
        * arm64: [`clickhouse.com/arch`](http://clickhouse.com/arch)`: arm64, NoSchedule`
      * Tags
        * Podem ser necessárias para o cluster-autoscaler, se estiver sendo usado
          * Exemplo:
            * `k8s.io/cluster-autoscaler/enabled: true`
            * `k8s.io/cluster-autoscaler/$CLUSTER_NAME: owned`
    * Grupo de nós server
      * Imagem AMI
        * x86: AL2023&#95;x86&#95;64
        * arm64: AL2023&#95;ARM&#95;64
      * Tamanho do disco: 20gb
      * [Template de inicialização do EC2 para grupo de nós](#ec2-launch-template-for-node-group-server))
      * Se não estiver usando escalonamento automático, as quantidades mínima e desejada de nós devem ser iguais ao número desejado de réplicas do ClickHouse
      * Tipo de instância recomendado: `m7gd.16xlarge`
        * **Recomendamos fortemente usar uma instância da série &quot;d&quot;** (por exemplo `m7gd.*`), que inclui SSD NVME e será usado pelo ClickHouse como cache
          * Para instâncias com NVME SSD, use um [template de inicialização personalizado](#ec2-launch-template-for-node-group-server) para montar automaticamente o NVME SSD
      * Labels do Kubernetes
        * x86: `clickhouseGroup: server`
        * arm64: `clickhouseGroup: server-arm64`
      * Taints do Kubernetes
        * `clickhouse.com/do-not-schedule: true, NoSchedule`
        * arm64: [`clickhouse.com/arch`](http://clickhouse.com/arch)`: arm64, NoSchedule`
      * Tags
        * Podem ser necessárias para o cluster-autoscaler, se estiver sendo usado
          * Exemplo:
            * `k8s.io/cluster-autoscaler/enabled: true`
            * `k8s.io/cluster-autoscaler/$CLUSTER_NAME: owned`
    * Grupo de nós x86 para executar outros processos em x86 (operator, ...)
      * Pode ser um grupo de nós existente se o cluster EKS já existir, desde que seja compatível com x86 e tenha nós de tamanho mínimo xlarge
      * Para novo grupo de nós
        * Imagem AMI: AL2023&#95;x86&#95;64
        * Tamanho do disco: 20gb
        * Tamanho da instância: mínimo xlarge
        * Tipo de instância: qualquer tipo compatível com x86
* Criar provedor OIDC para o cluster do EKS
* Crie um bucket do S3 (classe padrão do S3) com a criptografia ativada
  * O bucket deve estar na mesma região que o cluster do EKS
  * Você pode criar um bucket para cada cluster do ClickHouse provisionado ou usar um único bucket, mas isso exige um prefixo exclusivo para cada cluster do ClickHouse (definido no CR do ClickHouse/Chart do Helm)
* Crie o NLB, necessário se for preciso Entrada externa ao cluster do Kubernetes
  * Se um NLB for necessário**, ele deverá ser provisionado para cada cluster do ClickHouse**, a menos que algo como [istio](https://istio.io/) encaminhe as solicitações para o cluster correto
  * Crie entradas no Route 53; isso pode ser feito de forma automatizada com algo como [external-dns](https://github.com/kubernetes-sigs/external-dns) (as instruções de configuração não estão incluídas neste documento) usando anotações do Kubernetes
* Crie funções do IAM:
  * **As funções abaixo devem usar [uma política de confiança semelhante a esta](#example-trust-policy) (ou seja, devem usar IRSA), salvo indicação em contrário**
  * função do clickhouse-server/keeper
    * **Essa função é necessária para cada cluster do ClickHouse provisionado**
    * A convenção de nomenclatura deve ser `CH-S3-$NAME-$REGION-$ORDINAL-Role`
      * `$NAME`, nome do cluster, por exemplo `default-xx-01`
      * `$REGION`, identifica a região do cluster para evitar conflitos de nomenclatura entre regiões caso o mesmo nome de cluster seja usado.
        * O nome completo da região não é necessário e pode resultar em um nome de função que exceda os limites permitidos. Você pode usar um nome abreviado, como `uw2` para `us-west-2`
      * `$ORDINAL`, reservado, defina como `00`
      * Nome de função de exemplo para o serviço chamado `default-xx-01` em `us-west-2`: `CH-S3-default-xx-01-uw2-00-Role`
    * Permissões do bucket
      * As permissões mínimas são: `s3:*`, `s3:ListBucket` no recurso do bucket

  * Habilitar nomes de host DNS: true

<div id="copy-ecr-artifacts">
  ### Copiar artefatos do ECR
</div>

**Recomendamos fortemente o uso do [skopeo](https://github.com/containers/skopeo) para copiar as imagens**, pois ele preserva todas as arquiteturas das imagens Docker. Defina `TARGET_REGION` e `TARGET_ECR_REPO` abaixo de acordo com sua região e seu host do ECR.

```bash
SOURCE_REGION=us-east-1
SOURCE_ECR_REPO=349290138304.dkr.ecr.$SOURCE_REGION.amazonaws.com

TARGET_REGION=us-west-2
TARGET_ECR_REPO=0000000000.dkr.ecr.$TARGET_REGION.amazonaws.com

# faça login no nosso repositório (o processo de autenticação pode variar para o cliente)
aws ecr get-login-password --region $SOURCE_REGION | skopeo login --username AWS --password-stdin $SOURCE_ECR_REPO

# faça login no repositório AWS de destino (o processo de autenticação pode variar para o cliente)
aws ecr get-login-password --region $TARGET_REGION | skopeo login --username AWS --password-stdin $TARGET_ECR_REPO

# copie cada imagem para o ECR de destino, certifique-se de incluir a flag --all
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-server:<<SERVER_TAG>> docker://$TARGET_ECR_REPO/clickhouse-server:<<SERVER_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-keeper:<<KEEPER_TAG>> docker://$TARGET_ECR_REPO/clickhouse-keeper:<<KEEPER_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-operator:main-<<OPERATOR_TAG>> docker://$TARGET_ECR_REPO/clickhouse-operator:<<OPERATOR_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/clickhouse-operator-helm:<<OPERATOR_TAG>> docker://$TARGET_ECR_REPO/helm/clickhouse-operator-helm:<<OPERATOR_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/onprem-clickhouse-cluster:<<CR_HELM_TAG>> docker://$TARGET_ECR_REPO/helm/onprem-clickhouse-cluster:<<CR_HELM_TAG>>
```

<div id="creating-eks-cluster">
  ### Criando cluster EKS
</div>

São necessárias a IAM role do cluster e as IAM roles dos nós. As roles criadas com o botão &quot;Create recommended role&quot;, usando as permissões padrão na interface do console da AWS, são suficientes.

Execute o seguinte para adicionar um novo cluster EKS ao kubeconfig:

```bash
REGION=us-west-2
EKS_CLUSTER_NAME=eks-clickhouse

aws eks update-kubeconfig --region $REGION --name=$EKS_CLUSTER_NAME
```

<div id="cloud-formation-to-create-iam-role-to-pull-images">
  ### CloudFormation para criar IAM role para baixar imagens
</div>

É necessária uma IAM role para baixar imagens de um ECR privado da ClickHouse. A role é criada usando o template do CloudFormation. Depois que o ARN da role for criado, **você precisa fornecer o ARN (consulte a saída) à equipe da ClickHouse**.

**CloudFormation**

```yaml expandable
AWSTemplateFormatVersion: 2010-09-09
Description: This CloudFormation template creates the ClickHouseAirgapECRPullRole.

Resources:
  ClickHouseAirgapECRPullRole:
    Type: AWS::IAM::Role
    Properties:
      RoleName: ClickHouseAirgapECRPullRole
      AssumeRolePolicyDocument:
        Version: 2012-10-17
        Statement:
          - Effect: Allow
            Principal:
              AWS: !Sub "arn:aws:iam::${AWS::AccountId}:root"
            Action:
              - sts:AssumeRole
          - Effect: Allow
            Principal:
              Service:
                - ec2.amazonaws.com
            Action:
              - sts:AssumeRole
      Policies:
        - PolicyName: ClickHouseAirgapECRPullPolicy
          PolicyDocument:
            Version: 2012-10-17
            Statement:
              - Effect: Allow
                Action:
                  - ecr:GetDownloadUrlForLayer
                  - ecr:BatchGetImage
                  - ecr:BatchCheckLayerAvailability
                  - ecr:DescribeImages
                  - ecr:ListImages
                Resource:
                  - arn:aws:ecr:us-east-1:349290138304:repository/*
              - Effect: Allow
                Action:
                  - ecr:GetAuthorizationToken
                Resource:
                  - "*"

Outputs:
  RoleArn:
    Description: IAM Role ARN for pulling images from all ECR repositories
    Value: !GetAtt ClickHouseAirgapECRPullRole.Arn

```

<div id="ec2-launch-template-for-node-group-server">
  ### Modelo de execução do EC2 para o servidor do grupo de nós
</div>

Antes de criar um grupo de nós de servidores, é recomendável criar um modelo de execução do EC2 para provisionar o nó com um disco SSD para cache de consultas do ClickHouse.

O modelo deve conter o script abaixo. **Observe que pode haver dados já existentes no modelo de execução, caso ele tenha sido criado anteriormente, e eles devem ser mantidos**. Nesse caso, certifique-se de que os diferentes arquivos estejam separados pelo delimitador especificado.

**Detalhes avançados  (Dados do usuário**):

```bash expandable
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="==MYBOUNDARY=="

--==MYBOUNDARY==
Content-Type: text/x-shellscript; charset="us-ascii"

#!/bin/bash
sudo sysctl net.ipv4.tcp_fin_timeout=15
sudo sysctl net.ipv4.tcp_keepalive_time=15

function build_raid() {
set -x
mapfile -t SSD_NVME_DEVICE_LIST < <(nvme list | grep "Amazon EC2 NVMe Instance Storage" | cut -d " " -f 1 || true)
SSD_NVME_DEVICE_COUNT=${#SSD_NVME_DEVICE_LIST[@]}
RAID_DEVICE=${RAID_DEVICE:-/dev/md0}
RAID_CHUNK_SIZE=${RAID_CHUNK_SIZE:-512}              # Kilo Bytes
FILESYSTEM_BLOCK_SIZE=${FILESYSTEM_BLOCK_SIZE:-4096} # Bytes
STRIDE=$((RAID_CHUNK_SIZE * 1024 / FILESYSTEM_BLOCK_SIZE))
STRIPE_WIDTH=$((SSD_NVME_DEVICE_COUNT * STRIDE))
BLK_LABEL=ssdcache
MD_DEV_LABEL=dpssdcache

# Se o ponto de montagem estiver presente no fstab - sair
grep "${BLK_LABEL}" /etc/fstab && return 0

nvme list
echo "${SSD_NVME_DEVICE_COUNT}" "${SSD_NVME_DEVICE_LIST[*]}"

# Realizar provisionamento com base na contagem de dispositivos nvme
case  "${SSD_NVME_DEVICE_COUNT}" in
"0")
  echo 'No devices found of type "Amazon EC2 NVMe Instance Storage"'
  echo "Maybe your node selectors are not set correct"
  return 0
  ;;
"1")
  mkfs.ext4 -L "${BLK_LABEL}" -m 0 -b "${FILESYSTEM_BLOCK_SIZE}" "${SSD_NVME_DEVICE_LIST[0]}"
  ;;
*)
  mdadm --create --verbose "${RAID_DEVICE}" --name="${MD_DEV_LABEL}" --level=0 -c "${RAID_CHUNK_SIZE}" \
    --raid-devices="${#SSD_NVME_DEVICE_LIST[@]}" "${SSD_NVME_DEVICE_LIST[@]}"

  while mdadm --detail "${RAID_DEVICE}" | grep -q -ioE 'State :.*resyncing'
  do
    echo "Raid is resyncing.."
    sleep 1
  done
  echo "Raid0 device  ${RAID_DEVICE} has been created with disks  ${SSD_NVME_DEVICE_LIST[*]}"
  mkfs.ext4 -L "${BLK_LABEL}" -m 0 -b "${FILESYSTEM_BLOCK_SIZE}" -E "stride=${STRIDE},stripe-width=${STRIPE_WIDTH}" "${RAID_DEVICE}"
  ;;
esac

# Montar e adicionar ao fstab
# UUID é usado para compatibilidade com a ferramenta de provisionamento NVME do EKS
DEV_NAME=$(blkid -s UUID -o value -L "${BLK_LABEL}")
UUID=$(blkid -s UUID -o value "${DEV_NAME}")
# Verificar se o UUID está definido
test -z ${UUID} && return 1
mkdir -p /pv-disks/"${UUID}" /nvme/
test -h /nvme/disk || ln -fs /pv-disks/"${UUID}" /nvme/disk

cat<<EOF | tee -a /etc/fstab

LABEL=${BLK_LABEL} /pv-disks/${UUID} ext4 defaults,noatime,discard,nobarrier  0 0
EOF
mount -a
set +x
}

yum install -y nvme-cli mdadm
build_raid
mountpoint /nvme/disk/ || systemctl stop kubelet

--==MYBOUNDARY==--
```

<div id="install-storageclass-via-helm">
  ### Instalar StorageClass via Helm
</div>

Se uma StorageClass for necessária, recomenda-se instalar essas dependências do clickhouse-operator separadamente da criação propriamente dita do CR do clickhousecluster, usando o Chart do Helm fornecido, para que, se vários CRs forem criados, as dependências não fiquem vinculadas a nenhum cluster e não sejam removidas caso esse cluster seja excluído. **Esta etapa só precisa ser realizada se você não tiver um CR de StorageClass personalizado ou já existente** que pretende usar para clickhouser-server e clickhouse-keeper.

```bash
# atualize ECR_HOST conforme necessário
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
CHART_VERSION=<<CR_HELM_TAG>>

helm install clickhouse-prerequisites \
    oci://$ECR_HOST/helm/onprem-clickhouse-cluster \
    --version=$CHART_VERSION \
    -n default \
    --set-json="storageClass.create=true" \
    --set-json="createCluster=false" \
    --set-json="serviceAccount.create=false"
```

<div id="install-operator-via-helm">
  ### Instale o Operator com Helm
</div>

Atualize a versão, o host do ECR e as zonas de disponibilidade (conforme definido pela VPC criada), conforme necessário.

```bash expandable
# atualize ECR_HOST conforme necessário
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com

# deve usar a versão do chart do Helm do operator, não do próprio operator (ex: <<OPERATOR_TAG>>, não main.<<OPERATOR_TAG>>)
OPERATOR_VERSION=<<OPERATOR_TAG>>

# defina as AZs conforme determinado pelas sub-redes da VPC
AZ_LIST='["us-west-2a","us-west-2b","us-west-2c"]'

helm install clickhouse-operator \
   oci://$ECR_HOST/helm/clickhouse-operator-helm \
   --version=$OPERATOR_VERSION \
   --create-namespace \
   -n clickhouse-operator-system \
   --set-json="image.repository=\"$ECR_HOST/clickhouse-operator\"" \
   --set-json='cilium.enabled=false' \
   --set-json='idleScalerEnabled=false' \
   --set-json='webhooks.enabled=false' \
   --set-json='operator.debug=true' \
   --set-json='operator.metricsScraper.enabled=false' \
   --set-json="operator.availabilityZones=$AZ_LIST" \
   --set-json='operator.featureFlags.backupOnASeparatePod=true' \
   --set-json='operator.featureFlags.serverCMEKEnabled=true'
```

<div id="install-aws-ebs-csi-driver">
  ### Instale o aws-ebs-csi-driver
</div>

Requer um IAM role com o seguinte:

* Use a política gerenciada `arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy`
* Para a política de confiança, recomenda-se usar sts:AssumeRoleWithWebIdentity com o provedor OIDC do cluster EKS ([exemplo](#example-trust-policy))
* O nome do role selecionado deve corresponder à anotação na conta de serviço que executa o aws-ebs-csi-driver
  * Nome de exemplo: `ClickHouse_EksEbsCsiDriverRole`

Siga o guia de [instalação com helm](https://github.com/kubernetes-sigs/aws-ebs-csi-driver/blob/master/docs/install.md#helm) com valores adicionais para associar o IAM role à conta de serviço:

```bash
# atualize o nome da role conforme necessário
AWS_EBS_CSI_DRIVER_IAM_ROLE_ARN=arn:aws:iam::0000000000:role/ClickHouse_EksEbsCsiDriverRole

helm upgrade --install aws-ebs-csi-driver \
--namespace kube-system \
aws-ebs-csi-driver/aws-ebs-csi-driver \
--set-json="controller.serviceAccount.annotations={\"eks.amazonaws.com/role-arn\":\"$AWS_EBS_CSI_DRIVER_IAM_ROLE_ARN\"}"
```

<div id="naming-your-clickhouse-cluster">
  ### Nomeando seu cluster do ClickHouse
</div>

Para cada cluster do ClickHouse que estiver sendo provisionado, selecione um **nome de cluster exclusivo** dentro do cluster EKS de destino. Esse nome será usado em vários recursos da AWS e do Kubernetes e servirá para identificar exclusivamente o cluster.

1. A convenção de nomenclatura deve ser `$DESCRIPTOR-$LETTERS-$ORDINAL`
   1. $DESCRIPTOR - um nome descritivo do cluster, composto apenas por letras
   2. $LETTERS - reservado; selecione quaisquer duas letras. Para simplificar, `xx` funciona
   3. $ORDINAL - número ordinal incremental para clusters com o mesmo descritor, começando em `01`
2. Nome de exemplo: `default-xx-01`

<div id="clickhousecluster-cr">
  ### CR do Clickhousecluster
</div>

Observe que os valores abaixo devem ser revisados e atualizados para um ambiente de produção (por exemplo, recursos, flags de recursos, configurações do servidor, ...). Consulte a [seção sobre nomenclatura](#naming-your-clickhouse-cluster) antes de definir `CLUSTER_NAME`.
Gere o hash da senha para o `$PASSWORD` informado usando o comando a seguir (OS X) e depois informe-o no valor `account.hashedPassword` do Chart do Helm:

```bash expandable
# esta será a senha do usuário `default`
PASSWORD='My super secret p@$$w0rd'
HASHED_PASSWORD=`echo -n $PASSWORD | shasum -a 256 | awk '{printf $1}' | base64`

# atualize os valores abaixo conforme necessário,
# o host do ecr deve ser o da sua conta
# o bucket do S3 deve ser o criado anteriormente
CLUSTER_NAME=default-xx-01
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
SA_IAM_ROLE_ARN=arn:aws:iam::0000000000:role/CH-S3-${CLUSTER_NAME}-uw2-00-Role
S3_BUCKET_NAME=my-clickhouse-data

# o prefixo de chave do s3 pode usar qualquer valor UUID, mas deve ser único para todos os clusters que armazenam dados no bucket especificado acima
S3_KEY_PREFIX=ch-s3-$(uuidgen | tr '[:upper:]' '[:lower:]')

# estes devem corresponder ao valor do label clickhouseGroup adicionado ao grupo de nós
SERVER_NG_GROUP=server-arm64
KEEPER_NG_GROUP=keeper-arm64

# estes valores devem ser ajustados conforme os tamanhos de instância selecionados
# certifique-se de considerar os requisitos do daemon set ao definir os valores de CPU e MEMORY
SERVER_CPU=64
SERVER_MEMORY=256Gi
KEEPER_CPU=4
KEEPER_MEMORY=16Gi

CHART_VERSION=<<CR_HELM_TAG>>

# bytesPerGiRAM é um fator de escalonamento usado para calcular automaticamente o tamanho do cache em disco.
# Como regra geral, defina o tamanho do cache como 80-90% do tamanho disponível do disco de cache SSD.
# Ao definir bytesPerGiRAM no chart do Helm, a seguinte fórmula é aplicada durante a inicialização do pod:
#
# CONFIG_DISK_CACHE_SIZE = bytesPerGiRAM * pod_memory_limit
#
# Por exemplo:
# bytesPerGiRAM = 11.3Gi
# pod_memory_limit = 250Gi
# CONFIG_DISK_CACHE_SIZE = 11.3 * 250 = 2825Gi
CACHE_BYTES_PER_GI_RAM=11Gi

helm install $CLUSTER_NAME \    oci://$ECR_HOST/helm/onprem-clickhouse-cluster \
    --version=$CHART_VERSION \
    -n ns-$CLUSTER_NAME \
    --create-namespace \
    --set-json="account.hashedPassword=\"$HASHED_PASSWORD\"" \
    --set-json="server.image.repository=\"$ECR_HOST/clickhouse-server\"" \
    --set-json="server.storage.s3.bucketName=\"$S3_BUCKET_NAME\"" \
    --set-json="server.storage.s3.keyPrefix=\"$S3_KEY_PREFIX\"" \
    --set-json='server.arm64=true' \
    --set-json="server.image.tag=\"<<SERVER_TAG>>\"" \
    --set-json="server.podPolicy.nodeSelector.clickhouseGroup=\"$SERVER_NG_GROUP\"" \
    --set-json="keeper.image.repository=\"$ECR_HOST/clickhouse-keeper\"" \
    --set-json='keeper.arm64=true' \
    --set-json="keeper.image.tag=\"<<KEEPER_TAG>>\"" \
    --set-json="keeper.podPolicy.nodeSelector.clickhouseGroup=\"$KEEPER_NG_GROUP\"" \
    --set-json="serviceAccount.annotations={\"eks.amazonaws.com/role-arn\":\"$SA_IAM_ROLE_ARN\"}" \
    --set-json='server.tolerations=[{"effect":"NoSchedule","key":"clickhouse.com/do-not-schedule","operator":"Exists"}]' \
    --set-json='keeper.tolerations=[{"effect":"NoSchedule","key":"clickhouse.com/do-not-schedule","operator":"Exists"}]' \
    --set-json="server.ssdCacheConfiguration.bytesPerGiRAM=\"$CACHE_BYTES_PER_GI_RAM\"" \
    --set-json="server.podPolicy.resources.limits.cpu=\"$SERVER_CPU\"" \
    --set-json="server.podPolicy.resources.limits.memory=\"$SERVER_MEMORY\"" \
    --set-json="server.podPolicy.resources.requests.cpu=\"$SERVER_CPU\"" \
    --set-json="server.podPolicy.resources.requests.memory=\"$SERVER_MEMORY\"" \
    --set-json="keeper.podPolicy.resources.limits.cpu=\"$KEEPER_CPU\"" \
    --set-json="keeper.podPolicy.resources.limits.memory=\"$KEEPER_MEMORY\"" \
    --set-json="keeper.podPolicy.resources.requests.cpu=\"$KEEPER_CPU\"" \
    --set-json="keeper.podPolicy.resources.requests.memory=\"$KEEPER_MEMORY\""
```

<div id="hydra-setup">
  ## Configuração do Hydra
</div>

A ideia é criar vários grupos de nós dentro de um cluster do ClickHouse. Cada grupo terá um número diferente de nós (com diferentes quantidades de memória) e um endpoint separado. Esses grupos terão uma única instância do Keeper e um único conjunto de dados/pasta no bucket do S3 compartilhado.

<div id="provisioning-hydra-children-instances">
  ### Provisionamento das instâncias filhas do Hydra
</div>

<div id="prerequisites">
  ##### Pré-requisitos
</div>

O operador deve ser [instalado](#install-operator-via-helm) com o recurso Hydra habilitado, definindo-o como (o padrão é false):

```bash
--set operator.featureFlags.privateHydraEnabled="true"
```

<div id="setup">
  ##### Configuração
</div>

*Antes de criar instâncias filhas, você precisa escolher um cluster ClickHouse pai existente e/ou criar um novo. Portanto, deve saber com antecedência o **nome** e o **espaço de nomes** do pai para as filhas.*

Para criar um novo serviço filho, siga as [mesmas instruções](#clickhousecluster-cr) para criar um serviço e apenas adicione novos valores do Helm ao criar o recurso personalizado `ClickHouseCluster` (CR):

```bash
--set-json='parentCluster.name="c-${PARENT_NAME}'"'
--set-json='parentCluster.namespace="ns-'${PARENT_NAME}'"'
```

**PARENT&#95;NAME** - nome do cluster ClickHouse pai, existente ou novo.

Opcionalmente, se quiser que o novo cluster filho seja somente leitura (o padrão é false), pode adicionar:

```bash
--set-json='isReadonly=true'
```

<div id="limitations">
  ### Limitações
</div>

1. Você não pode provisionar instâncias filhas se a instância pai estiver parada, encerrada ou inativa.
2. Se quiser excluir o cluster pai, primeiro deverá excluir as instâncias filhas.

<div id="install-validation">
  ## Verificação da instalação
</div>

<div id="preflight-checks">
  ### Verificações preliminares
</div>

Há uma verificação preflight opcional com o [Troubleshoot](https://troubleshoot.sh/), um plugin do Kubernetes para diagnóstico de cluster.

Para instalar os plugins necessários, você pode usar o Krew:

```console
kubectl krew install preflight
```

ou consulte a [documentação](https://troubleshoot.sh/docs/) do Troubleshoot para ver outras opções de instalação.

O ClickHouse disponibiliza um Chart do Helm (`helm/preflight-check`) que pode ser copiado para o seu ECR e renderizado localmente para gerar a especificação de preflight, que depois é passada ao `kubectl preflight`.

<div id="copying-the-preflight-check-helm-chart">
  ##### Copiando o Chart do Helm de verificações preflight
</div>

Adicione o chart de verificações preflight à [etapa de cópia do ECR](#copy-ecr-artifacts):

```bash
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/preflight-check:<<PREFLIGHT_CHART_TAG>> docker://$TARGET_ECR_REPO/helm/preflight-check:<<PREFLIGHT_CHART_TAG>>
```

<div id="running-the-preflight-checks">
  ##### Executando as verificações de preflight
</div>

Use `helm template` para renderizar a especificação de preflight e, em seguida, envie a saída diretamente para `kubectl preflight`. Defina `CLUSTER_NAME` como o nome do cluster ClickHouse que você quer validar (consulte [Naming Your ClickHouse Cluster](#naming-your-clickhouse-cluster)):

```bash
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
CHART_VERSION=<<PREFLIGHT_CHART_TAG>>
CLUSTER_NAME=default-xx-01

helm template clickhouse-preflight \
    oci://$ECR_HOST/helm/preflight-check \
    --version=$CHART_VERSION \
    --set preflight.clickhouseClusterName=$CLUSTER_NAME | \
kubectl preflight -
```

Isso valida os requisitos para executar o ClickHouse Operator e implantar um cluster do ClickHouse. Valida se os labels de nó obrigatórios estão
presentes, se a Storage Class está configurada corretamente etc.

A saída mostra as diferentes verificações de preflight e seus status:
![Exemplo de preflight](/products/clickhouse-private/images/preflight-example.png)

Você pode percorrer a saída e verificar se cada checagem foi aprovada. Se uma checagem falhar, isso indica um problema (potencial) na configuração que pode causar
problemas para executar um cluster do ClickHouse com sucesso. As checagens incluem recomendações sobre o que fazer para corrigir o problema.

Para validar usando uma storage class diferente da padrão (`gp3-encrypted`), substitua-a com uma flag `--set` adicional:

```bash
    --set preflight.checks.prerequisites.storageClassName=<your-storage-class>
```

<div id="required-permissions">
  ##### Permissões necessárias
</div>

O usuário ou a conta de serviço que executa `kubectl preflight` deve conseguir ler recursos no nível do cluster e do espaço de nomes. No mínimo, é necessário o seguinte acesso:

| Escopo                                                     | Recursos                                                                                  |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Em todo o cluster                                          | `nodes`, `namespaces`, `persistentvolumes`, `storageclasses`, `customresourcedefinitions` |
| Espaço de nomes do operador (`clickhouse-operator-system`) | `deployments`, `replicasets`, `pods`, `services`, `configmaps`, `events`                  |
| Espaço de nomes do cluster (`ns-<cluster-name>`)           | `statefulsets`, `pods`, `persistentvolumeclaims`, `services`, `configmaps`, `events`      |

Na prática, uma identidade com a Função de cluster `view` interna, além de acesso `view` aos espaços de nomes relevantes, é suficiente. Uma vinculação a `cluster-admin` também funciona e é mais simples de configurar para execuções pontuais de validação.

<div id="port-forward-the-clickhouse-service-to-your-local-machine">
  ### Faça o redirecionamento de porta do serviço ClickHouse para sua máquina local
</div>

Para redirecionar o tráfego da sua máquina local para o serviço c-default-xx-01-server-any, execute:

```bash
kubectl port-forward svc/c-default-xx-01-server-any 9000:9000 -n ns-default-xx-01
```

Isso redirecionará a porta `9000` do serviço para a porta `9000` na sua máquina local. Agora você pode acessar a interface HTTP do ClickHouse em `http://localhost:9000`.

<div id="access-clickhouse-and-run-query">
  ### Acesse o ClickHouse e execute uma consulta
</div>

Após encaminhar a porta, você pode se conectar ao ClickHouse localmente usando uma ferramenta como `clickhouse-client`.

```bash
clickhouse client --host localhost --port 9000 --password $PASSWORD
```

e execute uma consulta simples:

```sql
clickhouse-cloud :) select 1;
```

Você verá uma saída como esta:

