<div id="overview">
  ## Обзор
</div>

В этом руководстве описано развертывание ClickHouse Private в Google Cloud Platform (GCP) с использованием Google Kubernetes Engine (GKE). В нем стандартный процесс развертывания для AWS адаптирован для сервисов GCP, включая Artifact Registry, GCS с S3-совместимым API и Workload Identity.

Это руководство поддерживает как **стандартные развертывания**, так и развертывания с **соответствием FIPS 140-2**. Шаги и параметры конфигурации, относящиеся к FIPS, по всему тексту помечены как **(FIPS)**. Чтобы включить режим FIPS, задайте `ENABLE_FIPS=true` в `00-env.sh`.

<div id="prerequisites">
  ## Предварительные требования
</div>

* Проект GCP с включенным биллингом
* Установленные и настроенные `gcloud` CLI
* Установленный `kubectl`
* Установленный `helm` v3.x
* Установленный `skopeo` (для копирования образов контейнеров)
* Учетные данные AWS с правом чтения из ClickHouse ECR (для копирования образов)
* **Bastion host** в VPC для доступа к приватному кластеру
* **Сервисный аккаунт для развертывания** с соответствующими разрешениями (см. ниже)
* **(FIPS)** Доступ к образу контейнера Red Hat UBI8 (загружается через GKE для генерации сертификатов)

<div id="creating-a-service-account-for-clickhouse-deployment">
  ## Создание сервисного аккаунта для развертывания ClickHouse
</div>

В средах FedRAMP, где прямая аутентификация пользователей ограничена, создайте сервисный аккаунт для имперсонации.

<div id="option-1-via-gcp-console">
  ### Вариант 1: Через консоль GCP
</div>

1. Перейдите в **IAM &amp; Admin** → **Service Accounts**
2. Нажмите **+ CREATE SERVICE ACCOUNT**
3. Укажите:
   * **Name:** `clickhouse-deployer`
   * **ID:** `clickhouse-deployer`
   * **Description:** `Сервисный аккаунт для развертывания инфраструктуры ClickHouse`
4. Нажмите **CREATE AND CONTINUE**
5. Добавьте следующие роли:

| Роль                                    | Назначение                                                   |
| --------------------------------------- | ------------------------------------------------------------ |
| `roles/compute.networkAdmin`            | Создание и управление VPC, подсетями, NAT и маршрутизаторами |
| `roles/container.admin`                 | Создание и управление кластерами GKE и пулами узлов          |
| `roles/storage.admin`                   | Создание и управление бакетами GCS                           |
| `roles/iam.serviceAccountAdmin`         | Создание и управление сервисными аккаунтами                  |
| `roles/iam.serviceAccountUser`          | Использование сервисных аккаунтов для Workload Identity      |
| `roles/iam.workloadIdentityUser`        | Настройка привязок Workload Identity                         |
| `roles/artifactregistry.admin`          | Создание и управление репозиториями Artifact Registry        |
| `roles/resourcemanager.projectIamAdmin` | Управление политиками IAM в проекте                          |

6. Нажмите **CONTINUE** → **DONE**

**Выдайте разрешение Token Creator:**

1. Нажмите на только что созданный сервисный аккаунт `clickhouse-deployer`
2. Перейдите на вкладку **PERMISSIONS**
3. Нажмите **GRANT ACCESS**
4. Добавьте субъект: `<COMPUTE_SERVICE_ACCOUNT>@developer.gserviceaccount.com` (сервисный аккаунт вашего bastion-хоста)
5. Назначьте роль: `roles/iam.serviceAccountTokenCreator`
6. Нажмите **SAVE**

<div id="option-2-via-cli-requires-iam-admin-access">
  ### Вариант 2: Через CLI (требуются права администратора IAM)
</div>

```bash expandable
PROJECT_ID=your-project-id
SA_EMAIL=clickhouse-deployer@${PROJECT_ID}.iam.gserviceaccount.com
COMPUTE_SA=<COMPUTE_PROJECT_NUMBER>-compute@developer.gserviceaccount.com

# Создать сервисный аккаунт
gcloud iam service-accounts create clickhouse-deployer \
  --display-name="ClickHouse Deployer" \
  --project=${PROJECT_ID}

# Назначить роли
for role in \
  roles/compute.networkAdmin \
  roles/container.admin \
  roles/storage.admin \
  roles/iam.serviceAccountAdmin \
  roles/iam.serviceAccountUser \
  roles/iam.workloadIdentityUser \
  roles/artifactregistry.admin \
  roles/resourcemanager.projectIamAdmin
do
  gcloud projects add-iam-policy-binding ${PROJECT_ID} \
    --member="serviceAccount:${SA_EMAIL}" \
    --role="${role}"
done

# Разрешить compute SA выполнять имперсонацию
gcloud iam service-accounts add-iam-policy-binding ${SA_EMAIL} \
  --member="serviceAccount:${COMPUTE_SA}" \
  --role="roles/iam.serviceAccountTokenCreator" \
  --project=${PROJECT_ID}
```

<div id="configure-impersonation-on-bastion">
  ### Настройте имперсонацию на bastion-хосте
</div>

Добавьте это в `00-env.sh` или выполните перед запуском скриптов:

```bash
# Настроить имперсонацию для сервисного аккаунта deployer
gcloud config set auth/impersonate_service_account clickhouse-deployer@${GCP_PROJECT}.iam.gserviceaccount.com

# Проверить работоспособность
gcloud compute networks list --project=${GCP_PROJECT}
```

Чтобы позже отключить имперсонацию:

```bash
gcloud config unset auth/impersonate_service_account
```

<div id="00-environment-variables">
  ## 00. Переменные окружения
</div>

**Файл: `00-env.sh`**

```bash expandable
#!/bin/bash
# ============================================
# ClickHouse Private GCP - Настройка окружения
# ============================================
# Обновите эти значения для вашего окружения

# Проект и регион GCP
export GCP_PROJECT=your-project-id
export GCP_REGION=us-central1
export GCP_ZONES="us-central1-a,us-central1-b,us-central1-c"

# Кластер GKE
export GKE_CLUSTER_NAME=clickhouse-cluster

# Кластер ClickHouse (на один кластер GKE может приходиться несколько)
export CLUSTER_NAME=default-xx-01
export NAMESPACE=ns-${CLUSTER_NAME}

# Сеть — используйте существующий VPC, в котором находится bastion-хост
export VPC_NAME=clickhouse-vpc
export SUBNET_NAME=gke-subnet
export SUBNET_RANGE=10.1.0.0/24
export POD_RANGE=10.244.0.0/14         # Должен быть выровнен по границе /14 (3-й октет кратен 4)
export SERVICE_RANGE=10.252.0.0/20     # Должен быть выровнен по границе /20
export MASTER_IPV4_CIDR=172.16.0.0/28  # Для управляющего уровня приватного кластера
export BASTION_SUBNET_RANGE=10.0.0.0/24  # Подсеть bastion-хоста (для master-authorized-networks)

# Хранилище
export BUCKET_NAME=clickhouse-data-${GCP_PROJECT}
export S3_KEY_PREFIX=ch-s3-$(uuidgen | tr '[:upper:]' '[:lower:]')

# Сервисные аккаунты
export GSA_NAME=clickhouse
export GSA_EMAIL=${GSA_NAME}@${GCP_PROJECT}.iam.gserviceaccount.com
export KSA_NAME=clickhouse

# Реестр артефактов
export GAR_REPO_NAME=clickhouse
export GAR_HOST=${GCP_REGION}-docker.pkg.dev/${GCP_PROJECT}/${GAR_REPO_NAME}

# Конфигурация FIPS (установите true для соответствия требованиям FIPS 140-2)
export ENABLE_FIPS=false

# Версии образов — в режиме FIPS используются сборки, соответствующие требованиям FIPS
if [ "$ENABLE_FIPS" = "true" ]; then
  export CLICKHOUSE_SERVER_VERSION=25.8.1.9104-fips
  export CLICKHOUSE_KEEPER_VERSION=26.1.1.1493
else
  export CLICKHOUSE_SERVER_VERSION=25.8.1.9104
  export CLICKHOUSE_KEEPER_VERSION=25.10.1.6624
fi
export CLICKHOUSE_OPERATOR_VERSION=main-1.16067.1
export OPERATOR_HELM_VERSION=1.16067.1
export CLUSTER_HELM_VERSION=1.1.155

# Источник AWS ECR (для копирования образов)
export SOURCE_ECR_REGION=us-east-1
export SOURCE_ECR_REPO=349290138304.dkr.ecr.${SOURCE_ECR_REGION}.amazonaws.com
export AWS_PROFILE=clickhouse-ecr

# Конфигурация пула узлов
export KEEPER_MACHINE_TYPE=n2-standard-4      # Для production рекомендуется n2-standard-8
export SERVER_MACHINE_TYPE=n2-standard-8      # Для production рекомендуется n2-standard-64
export DEFAULT_MACHINE_TYPE=n2-standard-4

# Ограничения ресурсов (скорректируйте в соответствии с типами инстансов)
export SERVER_CPU=4                           # Должно соответствовать типу машины
export SERVER_MEMORY=16Gi                     # Должно соответствовать типу машины
export KEEPER_CPU=2
export KEEPER_MEMORY=8Gi

# Конфигурация кэша
export CACHE_BYTES_PER_GI_RAM=11Gi

# Конфигурация сертификатов FIPS (используется только при ENABLE_FIPS=true)
if [ "$ENABLE_FIPS" = "true" ]; then
  export KUBERNETES_DOMAIN=cluster.local
  export CERT_DIR=./certs
  export SELF_SIGNED=true  # Установите false, если используется существующий CA
fi

# Пароль ClickHouse
# Для production/FIPS рекомендуется использовать Secret Manager:
#   export CLICKHOUSE_PASSWORD=$(gcloud secrets versions access latest --secret=clickhouse-password --project=${GCP_PROJECT})
export CLICKHOUSE_PASSWORD='change-me-not-for-production'

echo "=========================================="
echo "Environment Variables Set"
echo "=========================================="
echo "GCP Project:     ${GCP_PROJECT}"
echo "GCP Region:      ${GCP_REGION}"
echo "GKE Cluster:     ${GKE_CLUSTER_NAME}"
echo "CH Cluster:      ${CLUSTER_NAME}"
echo "Namespace:       ${NAMESPACE}"
echo "VPC:             ${VPC_NAME}"
echo "Subnet:          ${SUBNET_NAME}"
echo "Bucket:          ${BUCKET_NAME}"
echo "GAR Host:        ${GAR_HOST}"
echo "FIPS Mode:       ${ENABLE_FIPS}"
echo "=========================================="
```

**Важно:** Подключите этот файл командой `source` перед запуском других скриптов:

```bash
source ./00-env.sh
```

```bash expandable
#!/bin/bash
set -e

echo ""
echo "=========================================="
echo "✅ Artifact Registry Setup Complete!"
echo "=========================================="
echo ""
echo "Repository URL: ${GAR_HOST}"
```

<div id="02-copy-container-images">
  ## 02. Скопируйте образы контейнеров
</div>

**Файл: `02-copy-images.sh`**

Чтобы сохранить все архитектуры, требуется [skopeo](https://github.com/containers/skopeo).

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "02. Copying ClickHouse Images"
echo "=========================================="

# Проверка существования профиля AWS
if ! aws configure list --profile ${AWS_PROFILE} &>/dev/null; then
  echo "ERROR: AWS profile '${AWS_PROFILE}' not found"
  echo "To create the profile, run: aws configure --profile ${AWS_PROFILE}"
  exit 1
fi

# Аутентификация в исходном ECR
echo "Authenticating to AWS ECR..."
aws ecr get-login-password --region ${SOURCE_ECR_REGION} --profile ${AWS_PROFILE} | \
  skopeo login --username AWS --password-stdin ${SOURCE_ECR_REPO}
echo "✓ ECR authentication successful"

# Аутентификация в GCP Artifact Registry
echo "Authenticating to GCP Artifact Registry..."
gcloud auth configure-docker ${GCP_REGION}-docker.pkg.dev --quiet
echo "✓ GAR authentication successful"

echo ""
echo "Copying images..."

echo "1/5 Copying ClickHouse Server ${CLICKHOUSE_SERVER_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/clickhouse-server:${CLICKHOUSE_SERVER_VERSION} \
  docker://${GAR_HOST}/clickhouse-server:${CLICKHOUSE_SERVER_VERSION}
echo "✓ Server copied"

echo "2/5 Copying ClickHouse Keeper ${CLICKHOUSE_KEEPER_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/clickhouse-keeper:${CLICKHOUSE_KEEPER_VERSION} \
  docker://${GAR_HOST}/clickhouse-keeper:${CLICKHOUSE_KEEPER_VERSION}
echo "✓ Keeper copied"

echo "3/5 Copying ClickHouse Operator ${CLICKHOUSE_OPERATOR_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/clickhouse-operator:${CLICKHOUSE_OPERATOR_VERSION} \
  docker://${GAR_HOST}/clickhouse-operator:${CLICKHOUSE_OPERATOR_VERSION}
echo "✓ Operator copied"

echo "4/5 Copying Operator Helm Chart ${OPERATOR_HELM_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/helm/clickhouse-operator-helm:${OPERATOR_HELM_VERSION} \
  docker://${GAR_HOST}/helm/clickhouse-operator-helm:${OPERATOR_HELM_VERSION}
echo "✓ Operator Helm chart copied"

echo "5/5 Copying Cluster Helm Chart ${CLUSTER_HELM_VERSION}..."
skopeo copy --all \
  docker://${SOURCE_ECR_REPO}/helm/onprem-clickhouse-cluster:${CLUSTER_HELM_VERSION} \
  docker://${GAR_HOST}/helm/onprem-clickhouse-cluster:${CLUSTER_HELM_VERSION}
echo "✓ Cluster Helm chart copied"

echo ""
echo "=========================================="
echo "✅ All images copied successfully!"
echo "=========================================="

# Проверка
echo ""
echo "Verifying images in Artifact Registry..."
gcloud artifacts docker images list ${GAR_HOST} --format="table(package,version)"
```

<div id="03-configure-vpc-and-subnet">
  ## 03. Настройка VPC и подсети
</div>

**Файл: `03-vpc-subnet.sh`**

Этот скрипт предполагает, что у вас уже есть VPC с бастион-хостом. Он создает или обновляет подсеть GKE с необходимыми вторичными диапазонами.

**Важно: требования к границам CIDR**

* Блоки `/14`: третий октет должен делиться на 4 (например, `10.244.0.0`, НЕ `10.245.0.0`)
* Блоки `/20`: четвертый октет должен быть равен 0, а третий октет — кратен 16 (например, `10.252.0.0`)

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "03. Configuring VPC and GKE Subnet"
echo "=========================================="

# Проверка существования VPC
echo "Checking VPC: ${VPC_NAME}..."
if gcloud compute networks describe ${VPC_NAME} --project=${GCP_PROJECT} &>/dev/null; then
  echo "   ✓ VPC exists"
else
  echo "   Creating VPC..."
  gcloud compute networks create ${VPC_NAME} \
    --subnet-mode=custom \
    --project=${GCP_PROJECT}
  echo "   ✓ VPC created"
fi

# Проверка существования подсети GKE
echo ""
echo "Checking GKE subnet: ${SUBNET_NAME}..."
if gcloud compute networks subnets describe ${SUBNET_NAME} --region=${GCP_REGION} --project=${GCP_PROJECT} &>/dev/null; then
  # Подсеть существует — проверка вторичных диапазонов
  EXISTING_SECONDARY=$(gcloud compute networks subnets describe ${SUBNET_NAME} \
    --region=${GCP_REGION} \
    --project=${GCP_PROJECT} \
    --format="value(secondaryIpRanges.rangeName)" 2>/dev/null | grep -E "^pods$" || true)
  
  if [ -z "$EXISTING_SECONDARY" ]; then
    echo "   ⚠️ Subnet exists but missing secondary ranges"
    echo "   Adding secondary ranges for pods and services..."
    gcloud compute networks subnets update ${SUBNET_NAME} \
      --region=${GCP_REGION} \
      --add-secondary-ranges=pods=${POD_RANGE},services=${SERVICE_RANGE} \
      --project=${GCP_PROJECT}
    echo "   ✓ Secondary ranges added"
  else
    echo "   ✓ Subnet exists with secondary ranges"
  fi
else
  echo "   Creating GKE subnet..."
  gcloud compute networks subnets create ${SUBNET_NAME} \
    --network=${VPC_NAME} \
    --region=${GCP_REGION} \
    --range=${SUBNET_RANGE} \
    --secondary-range=pods=${POD_RANGE},services=${SERVICE_RANGE} \
    --enable-private-ip-google-access \
    --project=${GCP_PROJECT}
  echo "   ✓ Subnet created"
fi

# Включение Private Google Access
echo ""
echo "Ensuring Private Google Access is enabled..."
gcloud compute networks subnets update ${SUBNET_NAME} \
  --region=${GCP_REGION} \
  --enable-private-ip-google-access \
  --project=${GCP_PROJECT} 2>/dev/null || true
echo "   ✓ Private Google Access enabled"

echo ""
echo "=========================================="
echo "✅ VPC/Subnet Configuration Complete!"
echo "=========================================="
echo ""
echo "VPC:          ${VPC_NAME}"
echo "GKE Subnet:   ${SUBNET_NAME} (${SUBNET_RANGE})"
echo "Pods:         ${POD_RANGE}"
echo "Services:     ${SERVICE_RANGE}"
echo "Bastion:      ${BASTION_SUBNET_RANGE}"
```

<div id="04-create-cloud-nat">
  ## 04. Создайте Cloud NAT
</div>

**Файл: `04-cloud-nat.sh`**

Приватным узлам GKE требуется Cloud NAT для исходящего доступа к интернету (например, для загрузки образов).

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "04. Creating Cloud NAT for Private Nodes"
echo "=========================================="

# Создание Cloud Router
echo "Creating Cloud Router..."
if gcloud compute routers describe clickhouse-router --region=${GCP_REGION} --project=${GCP_PROJECT} &>/dev/null; then
  echo "   ✓ Router already exists"
else
  gcloud compute routers create clickhouse-router \
    --network=${VPC_NAME} \
    --region=${GCP_REGION} \
    --project=${GCP_PROJECT}
  echo "   ✓ Router created"
fi

# Создание Cloud NAT
echo ""
echo "Creating Cloud NAT..."
if gcloud compute routers nats describe clickhouse-nat --router=clickhouse-router --region=${GCP_REGION} --project=${GCP_PROJECT} &>/dev/null; then
  echo "   ✓ NAT already exists"
else
  gcloud compute routers nats create clickhouse-nat \
    --router=clickhouse-router \
    --region=${GCP_REGION} \
    --nat-all-subnet-ip-ranges \
    --auto-allocate-nat-external-ips \
    --enable-logging \
    --log-filter=ERRORS_ONLY \
    --project=${GCP_PROJECT}
  echo "   ✓ NAT created"
fi

echo ""
echo "=========================================="
echo "✅ Cloud NAT Setup Complete!"
echo "=========================================="
echo ""
echo "Router: clickhouse-router"
echo "NAT:    clickhouse-nat"
echo "Region: ${GCP_REGION}"
```

<div id="07-create-gke-cluster">

* Воркер-узлы имеют только внутренние IP-адреса
* У плоскости управления **только частная конечная точка**
* Весь доступ должен осуществляться только изнутри VPC (через bastion)

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "07. Creating Private GKE Cluster"
echo "=========================================="

echo "Creating cluster: ${GKE_CLUSTER_NAME}..."
if gcloud container clusters describe ${GKE_CLUSTER_NAME} --region=${GCP_REGION} --project=${GCP_PROJECT} &>/dev/null; then
  echo "   ✓ Cluster already exists"
else
  gcloud container clusters create ${GKE_CLUSTER_NAME} \
    --region=${GCP_REGION} \
    --node-locations=${GCP_ZONES} \
    --network=${VPC_NAME} \
    --subnetwork=${SUBNET_NAME} \
    --cluster-secondary-range-name=pods \
    --services-secondary-range-name=services \
    --enable-ip-alias \
    --enable-private-nodes \
    --enable-private-endpoint \
    --master-ipv4-cidr=${MASTER_IPV4_CIDR} \
    --enable-master-authorized-networks \
    --master-authorized-networks=${SUBNET_RANGE},${BASTION_SUBNET_RANGE} \
    --workload-pool=${GCP_PROJECT}.svc.id.goog \
    --num-nodes=1 \
    --machine-type=${DEFAULT_MACHINE_TYPE} \
    --disk-type=pd-standard \
    --disk-size=50 \
    --project=${GCP_PROJECT}
  echo "   ✓ Cluster created"
fi

# Получить учётные данные (необходимо запускать изнутри VPC / bastion)
echo ""
echo "Getting cluster credentials..."
gcloud container clusters get-credentials ${GKE_CLUSTER_NAME} \
  --region=${GCP_REGION} \
  --internal-ip \
  --project=${GCP_PROJECT}
echo "   ✓ Credentials configured"

# Проверить доступ

kubectl get nodes

echo ""
echo "=========================================="
echo "✅ Private GKE Cluster Ready!"
echo "=========================================="
echo ""
echo "Cluster:     ${GKE_CLUSTER_NAME}"
echo "Region:      ${GCP_REGION}"
echo "Master CIDR: ${MASTER_IPV4_CIDR}"
```

<div id="09-local-ssd-daemonset">
  ## 09. Локальный SSD в ДемонСете
</div>

**Файл: `09-local-ssd-daemonset.sh`**

В GKE Container-Optimized OS (COS) корневая файловая система доступна только для чтения, поэтому создать `/nvme` нельзя. Вместо этого мы монтируем локальный SSD в `/mnt/disks/ssd0` и настраиваем ClickHouse на использование этого пути.

**Примечание:** GKE не позволяет использовать `--metadata-from-file=startup-script` в пулах узлов (это зарезервированный ключ), поэтому для форматирования и монтирования локального SSD требуется ДемонСет.

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "09. Развёртывание ДемонСета для локального SSD"
echo "=========================================="

kubectl apply -f - <<'EOF'
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: local-ssd-setup
  namespace: kube-system
spec:
  selector:
    matchLabels:
      app: local-ssd-setup
  template:
    metadata:
      labels:
        app: local-ssd-setup
    spec:
      hostPID: true
      nodeSelector:
        clickhouseGroup: server
      tolerations:
      - key: "clickhouse.com/do-not-schedule"
        operator: "Exists"
        effect: "NoSchedule"
      initContainers:
      - name: setup-ssd
        image: busybox:1.36
        command:
        - /bin/sh
        - -c
        - |
          set -e
          
          # Используем nsenter для выполнения команд на хосте
          nsenter -t 1 -m -- /bin/sh -c '
            # Поиск устройства локального SSD
            if [ -b /dev/disk/by-id/google-local-nvme-ssd-0 ]; then
              DEV=/dev/disk/by-id/google-local-nvme-ssd-0
            elif [ -b /dev/disk/by-id/google-local-ssd-0 ]; then
              DEV=/dev/disk/by-id/google-local-ssd-0
            else
              echo "No local SSD found"
              exit 0
            fi
            
            mkdir -p /mnt/disks/ssd0
            
            # Форматирование при необходимости
            if ! blkid $DEV 2>/dev/null | grep -q ext4; then
              echo "Formatting $DEV..."
              mkfs.ext4 -F $DEV
            fi
            
            # Монтирование при необходимости
            if ! mountpoint -q /mnt/disks/ssd0; then
              echo "Mounting $DEV to /mnt/disks/ssd0..."
              mount $DEV /mnt/disks/ssd0
            fi
            chmod 755 /mnt/disks/ssd0
            
            echo "Local SSD ready at /mnt/disks/ssd0"
            df -h /mnt/disks/ssd0
          '
        securityContext:
          privileged: true
      containers:
      - name: pause
        image: gcr.io/google-containers/pause:3.2
EOF

echo ""
echo "Ожидание готовности ДемонСета..."
sleep 15
kubectl get ds -n kube-system local-ssd-setup
kubectl get pods -n kube-system -l app=local-ssd-setup
kubectl logs -n kube-system -l app=local-ssd-setup -c setup-ssd

echo ""
echo "=========================================="
echo "✓ ДемонСет для локального SSD развёрнут!"
echo "=========================================="
echo ""
echo "ВАЖНО: SSD смонтирован по пути /mnt/disks/ssd0"
echo "Необходимо настроить ClickHouse на использование этого пути"
echo "вместо /nvme/disk (корневая файловая система GKE COS доступна только для чтения)"
```

**Важные примечания:**

* В GKE Container-Optimized OS **корневая файловая система доступна только для чтения** — создать `/nvme` нельзя
* Локальный SSD монтируется в `/mnt/disks/ssd0`
* Используется образ `busybox:1.36` (интернет для `apt-get` не требуется)
* Для выполнения команд в файловой системе хоста используется `nsenter`
* ДемонСет должен быть развернут **до** кластера ClickHouse, чтобы избежать состояний гонки

<div id="14-create-fips-certificates-fips-only">
  ## 14. Создание FIPS-сертификатов (только для FIPS)
</div>

**Файл: `14-create-fips-certs.sh`** — Пропустите этот шаг, если `ENABLE_FIPS=false`.

Сертификаты, соответствующие требованиям FIPS, должны генерироваться с использованием одобренных FIPS алгоритмов в среде с включенным режимом FIPS. Этот скрипт запускает под Red Hat UBI8 в кластере GKE с включенной криптополитикой FIPS, а затем копирует сгенерированные сертификаты обратно на бастион с помощью `kubectl cp`.

**Требования:**

* Минимальный размер ключа RSA — 3072 бита
* Алгоритм подписи — SHA-256 или выше
* Альтернативные имена субъекта (SAN) должны включать DNS-имена кластера
* Доступ `kubectl` к кластеру GKE (`docker` не требуется)

**Типы сертификатов:**

| Сертификат | Файлы                                    | Назначение                       | Требуемые SAN                                                                     |
| ---------- | ---------------------------------------- | -------------------------------- | --------------------------------------------------------------------------------- |
| CA         | `ca/ca.crt`, `ca/ca.key`                 | Удостоверяющий центр             | Н/Д                                                                               |
| Server     | `server/server.crt`, `server/server.key` | Подключения к clickhouse-server  | `*.c-${CLUSTER_NAME}-server-headless.ns-${CLUSTER_NAME}.svc.${KUBERNETES_DOMAIN}` |
| Client     | `client/client.crt`, `client/client.key` | Подключения от clickhouse-server | Не требуются                                                                      |
| Keeper     | `keeper/keeper.crt`, `keeper/keeper.key` | Подключения к clickhouse-keeper  | `*.c-${CLUSTER_NAME}-keeper-headless.ns-${CLUSTER_NAME}.svc.${KUBERNETES_DOMAIN}` |

Скрипт выполняет следующие шаги:

1. Создает ConfigMap со скриптом генерации сертификатов
2. Запускает под UBI8 с `initContainer`, который устанавливает OpenSSL, задает криптополитику FIPS через `update-crypto-policies --set FIPS` и генерирует все сертификаты
3. Копирует сертификаты обратно на бастион с помощью `kubectl cp`
4. Удаляет под и ConfigMap

Полный текст скрипта см. в `fips/14-create-fips-certs.sh`.

**Важные примечания:**

* По умолчанию сертификаты действуют 365 дней — при необходимости скорректируйте `CERT_VALIDITY`
* CA‑сертификат действует 3650 дней (10 лет)
* Используются ключи RSA длиной 3072 бита (минимум, соответствующий требованиям FIPS)
* Храните закрытые ключи (файлы `*.key`) в безопасности и никогда не добавляйте их в систему контроля версий

<div id="15-create-certificate-secrets-fips-only">
  ## 15. Создайте секреты с сертификатами (только для FIPS)
</div>

**Файл: `15-create-cert-secrets.sh`** — Пропустите этот шаг, если `ENABLE_FIPS=false`.

Создайте секреты Kubernetes с сертификатами, соответствующими требованиям FIPS. Секреты должны находиться в том же пространстве имен, что и кластер ClickHouse.

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "15. Creating Certificate Secrets"
echo "=========================================="

# Создать пространство имен, если оно не существует
kubectl create namespace ${NAMESPACE} 2>/dev/null || echo "   Namespace exists"

# Создать секрет сертификата сервера
echo ""
echo "Creating server certificate secret..."
kubectl create secret generic -n ${NAMESPACE} ${CLUSTER_NAME}-server-cert-secret \
  --from-file=ca.crt="${CERT_DIR}/ca/ca.crt" \
  --from-file=server.crt="${CERT_DIR}/server/server.crt" \
  --from-file=server.key="${CERT_DIR}/server/server.key" \
  --from-file=client.crt="${CERT_DIR}/client/client.crt" \
  --from-file=client.key="${CERT_DIR}/client/client.key" \
  --dry-run=client -o yaml | kubectl apply -f -
echo "   ✓ Server certificate secret created"

# Создать секрет сертификата Keeper
echo ""
echo "Creating keeper certificate secret..."
kubectl create secret generic -n ${NAMESPACE} ${CLUSTER_NAME}-keeper-cert-secret \
  --from-file=ca.crt="${CERT_DIR}/ca/ca.crt" \
  --from-file=keeper.crt="${CERT_DIR}/keeper/keeper.crt" \
  --from-file=keeper.key="${CERT_DIR}/keeper/keeper.key" \
  --dry-run=client -o yaml | kubectl apply -f -
echo "   ✓ Keeper certificate secret created"

echo ""
echo "=========================================="
echo "✅ Certificate Secrets Created!"
echo "=========================================="
```

**Структура секрета:**

| Имя секрета                          | Ключи                                                            | Назначение                                     |
| ------------------------------------ | ---------------------------------------------------------------- | ---------------------------------------------- |
| `${CLUSTER_NAME}-server-cert-secret` | `ca.crt`, `server.crt`, `server.key`, `client.crt`, `client.key` | TLS сервера и исходящие клиентские подключения |

<div id="18-bind-workload-identity-to-helm-sa">
  ## 18. Привязка Workload Identity к Helm SA
</div>

**Файл: `18-bind-helm-workload-identity.sh`**

Helm-чарт создает собственный сервисный аккаунт (`ch-${CLUSTER_NAME}-sa`). Необходимо привязать Workload Identity к этой SA для доступа к GCS.

**Важно:** поды Keeper и сервера, созданные на шаге 17, запускаются *до* создания этой привязки Workload Identity, поэтому завершаются с ошибками GCS 403 Access Denied. Этот скрипт автоматически перезапускает поды после привязки, чтобы они получили новые учетные данные.

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "18. Привязка Workload Identity к Helm SA"
echo "=========================================="

# Ожидание создания Helm SA
echo "Ожидание создания сервисного аккаунта Helm..."
timeout=300
elapsed=0
while ! kubectl get serviceaccount ch-${CLUSTER_NAME}-sa -n ${NAMESPACE} &>/dev/null; do
  if [ $elapsed -ge $timeout ]; then
    echo "ОШИБКА: Тайм-аут ожидания сервисного аккаунта Helm"
    exit 1
  fi
  sleep 5
  elapsed=$((elapsed + 5))
  echo "  Ожидание... (${elapsed}s)"
done
echo "   ✓ Сервисный аккаунт Helm найден"

# Аннотирование SA, созданного helm
echo ""
echo "Аннотирование сервисного аккаунта Helm..."
kubectl annotate serviceaccount ch-${CLUSTER_NAME}-sa \
  -n ${NAMESPACE} \
  iam.gke.io/gcp-service-account=${GSA_EMAIL} \
  --overwrite
echo "   ✓ Сервисный аккаунт аннотирован"

# Привязка Workload Identity
echo ""
echo "Привязка Workload Identity..."
gcloud iam service-accounts add-iam-policy-binding ${GSA_EMAIL} \
  --project=${GCP_PROJECT} \
  --role=roles/iam.workloadIdentityUser \
  --member="serviceAccount:${GCP_PROJECT}.svc.id.goog[${NAMESPACE}/ch-${CLUSTER_NAME}-sa]" \
  --quiet
echo "   ✓ Workload Identity привязан"

echo ""
echo "Проверка аннотации..."
kubectl get sa ch-${CLUSTER_NAME}-sa -n ${NAMESPACE} -o yaml | grep -A3 annotations

# Перезапуск подов для получения новых учётных данных Workload Identity.
# Поды, созданные на шаге 17, были запущены до создания привязки, поэтому
# у них нет учётных данных GCP и они завершатся с ошибкой 403 при обращении к GCS.
echo ""
echo "Перезапуск подов Keeper и server для получения Workload Identity..."
kubectl delete pods -n ${NAMESPACE} -l clickhouseGroup=keeper --wait=false 2>/dev/null || true
kubectl delete pods -n ${NAMESPACE} -l clickhouseGroup=server --wait=false 2>/dev/null || true
echo "   ✓ Поды перезапускаются"

echo ""
echo "Ожидание готовности подов Keeper..."
kubectl wait --for=condition=ready pod \
  -l clickhouseGroup=keeper \
  -n ${NAMESPACE} \
  --timeout=600s
echo "   ✓ Поды Keeper готовы"

echo ""
echo "Ожидание создания подов server..."
echo "   (Оператор создаёт серверы после того, как Keeper'ы становятся работоспособными)"
timeout=600
elapsed=0
while ! kubectl get pods -n ${NAMESPACE} -l clickhouseGroup=server -o name 2>/dev/null | grep -q .; do
  if [ $elapsed -ge $timeout ]; then
    echo "ОШИБКА: Тайм-аут ожидания создания подов server"
    echo "  kubectl get pods -n ${NAMESPACE}"
    exit 1
  fi
  sleep 10
  elapsed=$((elapsed + 10))
  echo "  Ожидание подов server... (${elapsed}s)"
done

echo "Ожидание готовности подов server..."
kubectl wait --for=condition=ready pod \
  -l clickhouseGroup=server \
  -n ${NAMESPACE} \
  --timeout=600s
echo "   ✓ Поды server готовы"

echo ""
echo "=========================================="
echo "✅ Workload Identity привязан к Helm SA!"
echo "=========================================="
echo ""
kubectl get pods -n ${NAMESPACE}
```

<div id="19-verify-installation">
  ## 19. Проверьте установку
</div>

**Стандартный режим** (без TLS):

```bash
# Проброс порта для нативного порта ClickHouse
kubectl port-forward svc/c-${CLUSTER_NAME}-server-any 9000:9000 -n ${NAMESPACE} &

# Подключение с помощью clickhouse-client
clickhouse client --host localhost --port 9000 --password "${CLICKHOUSE_PASSWORD}"
```

**Режим TLS (FIPS)** — При `openSSL.required=true` ClickHouse принимает подключения только через защищённые порты. Используйте порт **9440** (TLS native-протокола) вместо 9000:

```bash
# Проброс порта для защищённого нативного порта ClickHouse
kubectl port-forward svc/c-${CLUSTER_NAME}-server-any 9440:9440 -n ${NAMESPACE} &

# Подключение с самоподписанными сертификатами
clickhouse client --host localhost --port 9440 \
  --password "${CLICKHOUSE_PASSWORD}" \
  --secure \
  --accept-invalid-certificate
```

Флаг `--accept-invalid-certificate` нужен, потому что мы используем самоподписанные сертификаты. В production при использовании корректных сертификатов, подписанных CA, явно укажите CA‑сертификат:

```bash
clickhouse client --host localhost --port 9440 \
  --password "${CLICKHOUSE_PASSWORD}" \
  --secure \
  --config-file <(cat <<'EOF'
<config>
    <openSSL>
        <client>
            <caConfig>./certs/ca/ca.crt</caConfig>
        </client>
    </openSSL>
</config>
EOF
)
```

**Выполните тестовый запрос:**

```sql
SELECT 1;
```

Ожидаемый вывод:

```
   ┌─1─┐
1. │ 1 │
   └───┘
1 row in set. Elapsed: 0.001 sec.
```

**Важно (FIPS):** Порты 9000 (незашифрованный нативный протокол) и 8123 (незашифрованный HTTP) не принимают подключения, если `openSSL.required=true`. Вместо них используйте порт 9440 (нативный TLS) или 8443 (HTTPS).

<div id="appendix-fips-specific-considerations">
  ## Приложение: Особенности FIPS
</div>

> **Примечание:** Этот раздел относится только к случаям, когда в `00-env.sh` установлено значение `ENABLE_FIPS=true`.

<div id="certificate-requirements">
  ### Требования к сертификатам
</div>

Для соответствия требованиям FIPS необходимо:

* Ключи RSA длиной не менее 3072 бит
* Одобренные FIPS алгоритмы подписи (SHA-256 или выше)
* Сертификаты, сгенерированные в среде с включенным FIPS (Red Hat UBI8)
* Корректная проверка цепочки сертификатов

<div id="openssl-configuration">
  ### Конфигурация OpenSSL
</div>

И для сервера, и для Keeper должно быть задано:

* `openSSL.enabled=true` - Включить TLS
* `openSSL.required=true` - Обязательно использовать TLS (отклонять соединения без TLS)
* `openSSL.selfSigned=true` - Для самоподписанных сертификатов (установите `false`, если используете доверенный CA)

<div id="key-differences-from-standard-gcp-installation">
  ### Ключевые отличия от стандартной установки в GCP
</div>

| Параметр                              | Стандартная     | FIPS                           |
| ------------------------------------- | --------------- | ------------------------------ |
| Тег образа сервера                    | `25.8.1.9104`   | `25.8.1.9104-fips`             |
| Тег образа Keeper                     | `25.10.1.6624`  | `26.1.1.1493`                  |
| OpenSSL включен                       | Не задано       | `true`                         |
| OpenSSL обязателен                    | Не задано       | `true`                         |
| TLS-сертификаты                       | Не требуются    | Обязательны (RSA 3072 бит)     |
| Порт клиентского подключения          | `9000` (native) | `9440` (native TLS)            |
| HTTP-порт                             | `8123`          | `8443` (HTTPS)                 |
| Флаг клиента `--secure`               | Не требуется    | Обязателен                     |
| Флаг для самоподписанного сертификата | Н/Д             | `--accept-invalid-certificate` |

<div id="appendix-troubleshooting">
  ## Приложение: Устранение неполадок
</div>

<div id="certificate-verification-failures-fips">
  ### Ошибки проверки сертификата (FIPS)
</div>

Если вы видите ошибки вроде &quot;certificate verify failed&quot;:

1. Убедитесь, что CA‑сертификат указан верно:

```bash
openssl x509 -in ${CERT_DIR}/ca/ca.crt -text -noout
```

2. Проверьте SAN-поля сертификата сервера:

```bash
openssl x509 -in ${CERT_DIR}/server/server.crt -text -noout | grep -A5 "Subject Alternative Name"
```

3. Проверьте содержимое секрета:

```bash
kubectl get secret ${CLUSTER_NAME}-server-cert-secret -n ${NAMESPACE} -o yaml
```

<div id="fips-mode-verification">
  ### Проверка режима FIPS
</div>

Проверьте, соответствуют ли созданные сертификаты требованиям FIPS:

```bash
# Проверить размер ключа
openssl rsa -in ${CERT_DIR}/server/server.key -text -noout | grep "Private-Key"

# Проверить алгоритм подписи
openssl x509 -in ${CERT_DIR}/server/server.crt -text -noout | grep "Signature Algorithm"
```

Должно быть:

* Закрытый ключ: 3072 бит
* Алгоритм подписи: sha256WithRSAEncryption (или выше)

<div id="gcs-access-denied-errors-403">
  ### Ошибки отказа в доступе к GCS (403)
</div>

Наиболее частая причина — **race condition в Workload Identity**: поды запускаются во время установки Helm (шаг 17) до того, как для SA (`ch-${CLUSTER_NAME}-sa`), созданной Helm, будет применена привязка Workload Identity на шаге 18. Теперь на шаге 18 это обрабатывается автоматически: после применения привязки поды перезапускаются.

Если вы по-прежнему видите ошибки 403:

```bash
# 1. Проверьте аннотацию Workload Identity на SA, созданном Helm
kubectl get sa ch-${CLUSTER_NAME}-sa -n ${NAMESPACE} -o yaml | grep -A5 annotations

# 2. Проверьте привязку IAM
gcloud iam service-accounts get-iam-policy ${GSA_EMAIL}

# 3. Проверьте разрешения бакета GCS для GSA
gcloud storage buckets get-iam-policy gs://${BUCKET_NAME} | grep ${GSA_EMAIL}

# 4. Выполните проверку изнутри пода (должен вернуть email GSA)
kubectl exec -it <pod-name> -n ${NAMESPACE} -- curl -s -H "Metadata-Flavor: Google" \
  http://169.254.169.254/computeMetadata/v1/instance/service-accounts/default/email

# 5. Перезапустите поды для применения учётных данных (если шаг 18 был выполнен после запуска подов)
kubectl delete pods -n ${NAMESPACE} -l clickhouseGroup=keeper
kubectl delete pods -n ${NAMESPACE} -l clickhouseGroup=server
```

<div id="connection-refused-on-port-9000-fips">
  ### Отказ в подключении к порту 9000 (FIPS)
</div>

При включенном FIPS для TLS (`openSSL.required=true`) ClickHouse не принимает незашифрованные соединения. Подключения к портам 9000 (Native) и 8123 (HTTP) будут отклоняться. Используйте защищенные порты:

| Протокол | Незашифрованный порт | TLS-порт |
| -------- | -------------------- | -------- |
| Native   | 9000                 | **9440** |
| HTTP     | 8123                 | **8443** |

```bash
# Неверно — соединение отклонено
kubectl port-forward svc/c-${CLUSTER_NAME}-server-any 9000:9000 -n ${NAMESPACE}
clickhouse client --host localhost --port 9000

# Верно
kubectl port-forward svc/c-${CLUSTER_NAME}-server-any 9440:9440 -n ${NAMESPACE}
clickhouse client --host localhost --port 9440 --secure --accept-invalid-certificate
```

<div id="helm-registry-login-fails">
  ### Не удается выполнить вход в реестр Helm

```bash
# Неверно — завершится ошибкой "invalid registry"

# Верно

  -u oauth2accesstoken --password-stdin \
  ${GCP_REGION}-docker.pkg.dev
```

<div id="validate-ssd-cache-script">
  ### Скрипт для проверки SSD-кэша
</div>

`validate-ssd-cache.sh`

```bash expandable
#!/bin/bash
set -e
source ./00-env.sh

echo "=========================================="
echo "17. Validating SSD Cache Configuration"
echo "=========================================="

echo ""
echo "1. Checking DaemonSet status..."
DS_READY=$(kubectl get ds local-ssd-setup -n kube-system -o jsonpath='{.status.numberReady}')
DS_DESIRED=$(kubectl get ds local-ssd-setup -n kube-system -o jsonpath='{.status.desiredNumberScheduled}')

if [ "$DS_READY" = "$DS_DESIRED" ]; then
  echo "✅ DaemonSet ready: $DS_READY/$DS_DESIRED pods"
else
  echo "❌ DaemonSet not ready: $DS_READY/$DS_DESIRED pods"
  exit 1
fi

echo ""
echo "2. Checking ClickHouseCluster SSD configuration..."
SSD_CONFIG=$(kubectl get clickhousecluster c-${CLUSTER_NAME} -n ${NAMESPACE} -o jsonpath='{.spec.ssdCacheConfiguration}')

if echo "$SSD_CONFIG" | jq -e '.hostPathBaseDirectory == "/mnt/disks/ssd0/"' > /dev/null; then
  echo "✅ SSD cache configured in CRD:"
  echo "$SSD_CONFIG" | jq .
else
  echo "❌ SSD cache not properly configured"
  exit 1
fi

echo ""
echo "3. Waiting for server pods to be ready..."
kubectl wait --for=condition=ready pod \
  -l clickhouseGroup=server \
  -n ${NAMESPACE} \
  --timeout=300s

echo ""
echo "4. Checking pod volume mounts..."
SERVER_POD=$(kubectl get pods -n ${NAMESPACE} -l clickhouseGroup=server -o name | head -1)
echo "Checking pod: $SERVER_POD"

CACHE_MOUNT=$(kubectl get $SERVER_POD -n ${NAMESPACE} -o jsonpath='{.spec.containers[0].volumeMounts}' | jq '.[] | select(.name == "ch-cache-volume")')

if [ -n "$CACHE_MOUNT" ]; then
  echo "✅ Cache volume mounted:"
  echo "$CACHE_MOUNT" | jq .
else
  echo "❌ Cache volume not found in pod"
  exit 1
fi

echo ""
echo "5. Checking pod volume definition..."
CACHE_VOL=$(kubectl get $SERVER_POD -n ${NAMESPACE} -o jsonpath='{.spec.volumes}' | jq '.[] | select(.name == "ch-cache-volume")')

if [ -n "$CACHE_VOL" ]; then
  echo "✅ Cache volume defined:"
  echo "$CACHE_VOL" | jq .
else
  echo "❌ Cache volume not found in pod spec"
  exit 1
fi

echo ""
echo "6. Verifying cache is accessible inside container..."
if kubectl exec -n ${NAMESPACE} $SERVER_POD -- df -h /mnt/clickhouse-cache 2>/dev/null; then
  echo "✅ Cache directory accessible and mounted"
else
  echo "❌ Cache directory not accessible"
  exit 1
fi

echo ""
echo "7. Checking cache usage in ClickHouse..."
echo "Connecting to ClickHouse to verify cache configuration..."

# Собрать флаги подключения клиента
CLIENT_FLAGS=(--password="${CLICKHOUSE_PASSWORD}")
if [ "$ENABLE_FIPS" = "true" ]; then
  # В режиме FIPS требуется OpenSSL — найдите сертификат CA и настройте TLS
  CA_CERT_PATH=$(kubectl exec -n ${NAMESPACE} $SERVER_POD -- \
    find /etc -name "ca.crt" -type f 2>/dev/null | head -1)
  if [ -z "$CA_CERT_PATH" ]; then
    echo "❌ Could not find CA cert inside container"
    exit 1
  fi
  echo "Using CA cert: $CA_CERT_PATH"

  CLIENT_FLAGS+=(--secure --config-file=/tmp/ch-client-ssl.xml)
  kubectl exec -n ${NAMESPACE} $SERVER_POD -- bash -c "cat > /tmp/ch-client-ssl.xml << EOF
<clickhouse>
  <openSSL>
    <client>
      <caConfig>${CA_CERT_PATH}</caConfig>
    </client>
  </openSSL>
</clickhouse>
EOF"
fi

# Получить настройки файлового кэша (SSD-кэш представляет собой слой файлового кэша
# поверх дисков ObjectStorage, поэтому он отображается в system.filesystem_cache_settings,
# а не как автономный диск в system.disks)
CACHE_INFO=$(kubectl exec -n ${NAMESPACE} $SERVER_POD -- clickhouse-client "${CLIENT_FLAGS[@]}" -q "
SELECT
    cache_name,
    path,
    formatReadableSize(max_size) as max_size,
    formatReadableSize(current_size) as current_size,
    current_elements_num,
    is_initialized
FROM system.filesystem_cache_settings
FORMAT Vertical
" 2>/dev/null) || true

if [ -n "$CACHE_INFO" ]; then
  echo "✅ Filesystem cache active in ClickHouse:"
  echo "$CACHE_INFO"
else
  echo "⚠️  Could not query ClickHouse cache info (cluster may still be initializing)"
fi

echo ""
echo "=========================================="
echo "✅ SSD Cache Validation Complete!"
echo "=========================================="
echo ""
echo "Summary:"
echo "  • DaemonSet mounted SSD at: /mnt/disks/ssd0 (on host)"
echo "  • Operator created volume:  ch-cache-volume"
echo "  • Container mount point:    /mnt/clickhouse-cache"
echo "  • Cache size configured:    ${CACHE_BYTES_PER_GI_RAM} per GiB RAM"
echo ""
echo "The SSD cache is fully configured and operational!"
```

<div id="security-best-practices">
  ## Рекомендации по обеспечению безопасности
</div>

1. **Управление сертификатами** (FIPS)
   * Обновляйте сертификаты до истечения срока их действия (по умолчанию: 365 дней)
   * Храните закрытые ключи в безопасном месте (используйте управление секретами)
   * Никогда не добавляйте сертификаты в систему контроля версий
   * В продакшене используйте корректные сертификаты, подписанные CA

2. **Сетевая безопасность**
   * Используйте приватный кластер GKE без публичной конечной точки
   * Ограничьте master-authorized-networks, разрешив доступ только с бастиона и из подсетей GKE
   * Включите журналы потоков VPC
   * Используйте Cloud NAT для контролируемого исходящего доступа

3. **Управление доступом**
   * Используйте Workload Identity вместо статических учетных данных
   * Включите Kubernetes RBAC
   * Регулярно проверяйте журналы доступа
   * Используйте имперсонацию сервисного аккаунта при развертывании

4. **Мониторинг**
   * Отслеживайте даты истечения срока действия сертификатов (FIPS)
   * Настройте оповещения о сбоях TLS‑соединений (FIPS)
   * Отслеживайте характер доступа к GCS
   * Включите Cloud Audit Logging
