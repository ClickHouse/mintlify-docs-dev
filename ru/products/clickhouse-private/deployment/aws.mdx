* [Создание VPC](#example-vpc-configuration)
* [Создание кластера EKS](#creating-eks-cluster)
  * Требуются следующие компоненты:
    * CNI на ваш выбор (должен использовать ipv4), например [Amazon VPC CNI](https://github.com/aws/amazon-vpc-cni-k8s)
      * Если используется Amazon VPC CNI, рекомендуем использовать IRSA; вы можете воспользоваться этим руководством, следуя инструкциям для ipv4: [https://docs.aws.amazon.com/eks/latest/userguide/cni-iam-role.html](https://docs.aws.amazon.com/eks/latest/userguide/cni-iam-role.html)
    * Драйвер EBS CSI, например [aws-ebs-csi-driver](#install-aws-ebs-csi-driver)
    * DNS, например CoreDNS
    * Рекомендуется: автомасштабирование; для него могут потребоваться такие компоненты, как [cluster autoscaler](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/cloudprovider/aws/README.md)
  * Свяжите с ранее созданной VPC
  * Группы узлов
    * **Для authentication всем узлам требуется [IMDS](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instancedata-data-retrieval.html)**
    * Для групп узлов keeper и server **создайте отдельную группу узлов для каждой AZ, если хотите поддерживать cluster autoscaler** между AZ, как рекомендовано [здесь](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/FAQ.md#i-have-a-couple-of-pending-pods-but-there-was-no-scale-up); в противном случае их можно создать как одиночные группы узлов с подсетями соответствующих AZ
    * Группа узлов Keeper
      * AMI-образ:
        * x86: AL2023&#95;x86&#95;64
        * arm64: AL2023&#95;ARM&#95;64
      * Размер диска: 20gb
      * Если автомасштабирование не используется, минимальное и желаемое количество узлов должно составлять 3 для каждого кластера ClickHouse
      * Рекомендуемый тип инстанса: `m7g.2xlarge`
      * Метки Kubernetes
        * x86: `clickhouseGroup: keeper`
        * arm64: `clickhouseGroup: keeper-arm64`
      * Taints Kubernetes
        * `clickhouse.com/do-not-schedule: true, NoSchedule`
        * arm64: [`clickhouse.com/arch`](http://clickhouse.com/arch)`: arm64, NoSchedule`
      * Теги
        * Могут потребоваться для cluster-autoscaler, если он используется
          * Пример:
            * `k8s.io/cluster-autoscaler/enabled: true`
            * `k8s.io/cluster-autoscaler/$CLUSTER_NAME: owned`
    * Группа узлов Server
      * AMI-образ
        * x86: AL2023&#95;x86&#95;64
        * arm64: AL2023&#95;ARM&#95;64
      * Размер диска: 20gb
      * [Шаблон запуска EC2 для группы узлов](#ec2-launch-template-for-node-group-server))
      * Если автомасштабирование не используется, минимальное и желаемое количество узлов должно быть равно требуемому числу реплик ClickHouse
      * Рекомендуемый тип инстанса: `m7gd.16xlarge`
        * **Настоятельно рекомендуется использовать инстанс серии &quot;d&quot;** (например, `m7gd.*`), который включает NVMe SSD и будет использоваться ClickHouse как кеш
          * Для инстансов с NVMe SSD используйте [пользовательский шаблон запуска](#ec2-launch-template-for-node-group-server), чтобы автоматически монтировать NVMe SSD
      * Метки Kubernetes
        * x86: `clickhouseGroup: server`
        * arm64: `clickhouseGroup: server-arm64`
      * Taints Kubernetes
        * `clickhouse.com/do-not-schedule: true, NoSchedule`
        * arm64: [`clickhouse.com/arch`](http://clickhouse.com/arch)`: arm64, NoSchedule`
      * Теги
        * Могут потребоваться для cluster-autoscaler, если он используется
          * Пример:
            * `k8s.io/cluster-autoscaler/enabled: true`
            * `k8s.io/cluster-autoscaler/$CLUSTER_NAME: owned`
    * Группа узлов x86 для запуска других процессов x86 (operator, ...)
      * Может быть существующей группой узлов, если кластер EKS уже существует, при условии, что она совместима с x86 и минимальный размер узлов — xlarge
      * Для новой группы узлов
        * AMI-образ: AL2023&#95;x86&#95;64
        * Размер диска: 20gb
        * Размер инстанса: не менее xlarge
        * Тип инстанса: любой тип, совместимый с x86
* Создайте OIDC-провайдер для кластера EKS
* Создайте S3 бакет (стандартный класс хранения S3) с включённым шифрованием
  * Бакет должен находиться в том же регионе, что и кластер EKS
  * Вы можете создать отдельный бакет для каждого развернутого кластера ClickHouse или использовать один общий бакет, но в этом случае для каждого кластера ClickHouse потребуется уникальный префикс (задается в clickhouse CR/helm-чарте)
* Создайте NLB — это необходимо, если нужен входной шлюз вне кластера Kubernetes
  * Если требуется NLB**, его следует выделять для каждого кластера ClickHouse**, если только запросы не будут направляться в нужный кластер с помощью чего-то вроде [istio](https://istio.io/)
  * Создайте записи в Route 53; это можно автоматизировать с помощью чего-то вроде [external-dns](https://github.com/kubernetes-sigs/external-dns) (инструкции по настройке в этом документе не приводятся), используя annotations Kubernetes
* Создайте роли IAM:
  * **Если не указано иное, для указанных ниже ролей должна использоваться [политика доверия, аналогичная этой](#example-trust-policy) (то есть они должны использовать IRSA)**
  * роль clickhouse-server/Keeper
    * **Эта роль требуется для каждого развернутого кластера ClickHouse**
    * Следует использовать следующую схему именования: `CH-S3-$NAME-$REGION-$ORDINAL-Role`
      * `$NAME` — имя кластера, например `default-xx-01`
      * `$REGION` указывает регион кластера, чтобы избежать конфликтов имён между регионами, если используется одно и то же имя кластера.
        * Полное имя региона не требуется и может привести к тому, что имя роли превысит допустимую длину. При желании можно использовать сокращённое имя, например `uw2` для `us-west-2`
      * `$ORDINAL` зарезервирован, установите значение `00`
      * Пример имени роли для сервиса с именем `default-xx-01` в us-west-2: `CH-S3-default-xx-01-uw2-00-Role`
    * Разрешения для бакета
      * Минимальные разрешения: `s3:*`, `s3:ListBucket` на ресурс бакета

<div id="copy-ecr-artifacts">
  ### Копирование артефактов ECR
</div>

**Мы настоятельно рекомендуем использовать [skopeo](https://github.com/containers/skopeo) для копирования образов**, так как это позволит сохранить все архитектуры в Docker-образах. Обязательно укажите ниже значения `TARGET_REGION` и `TARGET_ECR_REPO` в соответствии с вашим регионом и хостом ECR.

```bash
SOURCE_REGION=us-east-1
SOURCE_ECR_REPO=349290138304.dkr.ecr.$SOURCE_REGION.amazonaws.com

TARGET_REGION=us-west-2
TARGET_ECR_REPO=0000000000.dkr.ecr.$TARGET_REGION.amazonaws.com

# войти в наш репозиторий (процесс аутентификации может отличаться у клиента)
aws ecr get-login-password --region $SOURCE_REGION | skopeo login --username AWS --password-stdin $SOURCE_ECR_REPO

# войти в целевой репозиторий AWS (процесс аутентификации может отличаться у клиента)
aws ecr get-login-password --region $TARGET_REGION | skopeo login --username AWS --password-stdin $TARGET_ECR_REPO

# скопировать каждый образ в целевой ECR, обязательно укажите флаг --all
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-server:<<SERVER_TAG>> docker://$TARGET_ECR_REPO/clickhouse-server:<<SERVER_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-keeper:<<KEEPER_TAG>> docker://$TARGET_ECR_REPO/clickhouse-keeper:<<KEEPER_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/clickhouse-operator:main-<<OPERATOR_TAG>> docker://$TARGET_ECR_REPO/clickhouse-operator:<<OPERATOR_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/clickhouse-operator-helm:<<OPERATOR_TAG>> docker://$TARGET_ECR_REPO/helm/clickhouse-operator-helm:<<OPERATOR_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/onprem-clickhouse-cluster:<<CR_HELM_TAG>> docker://$TARGET_ECR_REPO/helm/onprem-clickhouse-cluster:<<CR_HELM_TAG>>
```

<div id="creating-eks-cluster">
  ### Создание кластера EKS
</div>

Требуются роль IAM для кластера и роли IAM для узлов. Ролей, созданных с помощью кнопки &quot;Create recommended role&quot; с разрешениями по умолчанию в интерфейсе консоли AWS, будет достаточно.

Выполните следующую команду, чтобы добавить новый кластер EKS в kubeconfig:

```bash
REGION=us-west-2
EKS_CLUSTER_NAME=eks-clickhouse

aws eks update-kubeconfig --region $REGION --name=$EKS_CLUSTER_NAME
```

<div id="cloud-formation-to-create-iam-role-to-pull-images">
  ### Cloud Formation для создания роли IAM для скачивания образов
</div>

Требуется роль IAM для скачивания образов из приватного ECR ClickHouse. Роль создаётся с помощью шаблона CloudFormation. После создания ARN роли **необходимо передать ARN (см. вывод) команде ClickHouse**.

**CloudFormation**

```yaml expandable
AWSTemplateFormatVersion: 2010-09-09
Description: This CloudFormation template creates the ClickHouseAirgapECRPullRole.

Resources:
  ClickHouseAirgapECRPullRole:
    Type: AWS::IAM::Role
    Properties:
      RoleName: ClickHouseAirgapECRPullRole
      AssumeRolePolicyDocument:
        Version: 2012-10-17
        Statement:
          - Effect: Allow
            Principal:
              AWS: !Sub "arn:aws:iam::${AWS::AccountId}:root"
            Action:
              - sts:AssumeRole
          - Effect: Allow
            Principal:
              Service:
                - ec2.amazonaws.com
            Action:
              - sts:AssumeRole
      Policies:
        - PolicyName: ClickHouseAirgapECRPullPolicy
          PolicyDocument:
            Version: 2012-10-17
            Statement:
              - Effect: Allow
                Action:
                  - ecr:GetDownloadUrlForLayer
                  - ecr:BatchGetImage
                  - ecr:BatchCheckLayerAvailability
                  - ecr:DescribeImages
                  - ecr:ListImages
                Resource:
                  - arn:aws:ecr:us-east-1:349290138304:repository/*
              - Effect: Allow
                Action:
                  - ecr:GetAuthorizationToken
                Resource:
                  - "*"

Outputs:
  RoleArn:
    Description: IAM Role ARN for pulling images from all ECR repositories
    Value: !GetAtt ClickHouseAirgapECRPullRole.Arn

```

<div id="ec2-launch-template-for-node-group-server">
  ### Шаблон запуска EC2 для группы серверных узлов
</div>

Перед созданием группы серверных узлов рекомендуется создать шаблон запуска EC2, чтобы развернуть узел с SSD-диском для кэширования запросов ClickHouse.

Шаблон должен содержать приведённый ниже скрипт. **Обратите внимание: если шаблон запуска был создан ранее, в нём уже могут быть данные, и их следует сохранить**. В этом случае обязательно убедитесь, что разные файлы разделены указанной границей.

**Дополнительные параметры  (Пользовательские данные**):

```bash expandable
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="==MYBOUNDARY=="

--==MYBOUNDARY==
Content-Type: text/x-shellscript; charset="us-ascii"

#!/bin/bash
sudo sysctl net.ipv4.tcp_fin_timeout=15
sudo sysctl net.ipv4.tcp_keepalive_time=15

function build_raid() {
set -x
mapfile -t SSD_NVME_DEVICE_LIST < <(nvme list | grep "Amazon EC2 NVMe Instance Storage" | cut -d " " -f 1 || true)
SSD_NVME_DEVICE_COUNT=${#SSD_NVME_DEVICE_LIST[@]}
RAID_DEVICE=${RAID_DEVICE:-/dev/md0}
RAID_CHUNK_SIZE=${RAID_CHUNK_SIZE:-512}              # Килобайты
FILESYSTEM_BLOCK_SIZE=${FILESYSTEM_BLOCK_SIZE:-4096} # Байты
STRIDE=$((RAID_CHUNK_SIZE * 1024 / FILESYSTEM_BLOCK_SIZE))
STRIPE_WIDTH=$((SSD_NVME_DEVICE_COUNT * STRIDE))
BLK_LABEL=ssdcache
MD_DEV_LABEL=dpssdcache

# If mount is present in fstab - exit
grep "${BLK_LABEL}" /etc/fstab && return 0

nvme list
echo "${SSD_NVME_DEVICE_COUNT}" "${SSD_NVME_DEVICE_LIST[*]}"

# Perform provisioning based on nvme device count
case  "${SSD_NVME_DEVICE_COUNT}" in
"0")
  echo 'No devices found of type "Amazon EC2 NVMe Instance Storage"'
  echo "Maybe your node selectors are not set correct"
  return 0
  ;;
"1")
  mkfs.ext4 -L "${BLK_LABEL}" -m 0 -b "${FILESYSTEM_BLOCK_SIZE}" "${SSD_NVME_DEVICE_LIST[0]}"
  ;;
*)
  mdadm --create --verbose "${RAID_DEVICE}" --name="${MD_DEV_LABEL}" --level=0 -c "${RAID_CHUNK_SIZE}" \
    --raid-devices="${#SSD_NVME_DEVICE_LIST[@]}" "${SSD_NVME_DEVICE_LIST[@]}"

  while mdadm --detail "${RAID_DEVICE}" | grep -q -ioE 'State :.*resyncing'
  do
    echo "Raid is resyncing.."
    sleep 1
  done
  echo "Raid0 device  ${RAID_DEVICE} has been created with disks  ${SSD_NVME_DEVICE_LIST[*]}"
  mkfs.ext4 -L "${BLK_LABEL}" -m 0 -b "${FILESYSTEM_BLOCK_SIZE}" -E "stride=${STRIDE},stripe-width=${STRIPE_WIDTH}" "${RAID_DEVICE}"
  ;;
esac

# Mount it & add to fstab
# UUID is used to be compatible with EKS NVME proviioner tool
DEV_NAME=$(blkid -s UUID -o value -L "${BLK_LABEL}")
UUID=$(blkid -s UUID -o value "${DEV_NAME}")
# Make sure UUID is defined
test -z ${UUID} && return 1
mkdir -p /pv-disks/"${UUID}" /nvme/
test -h /nvme/disk || ln -fs /pv-disks/"${UUID}" /nvme/disk

cat<<EOF | tee -a /etc/fstab

LABEL=${BLK_LABEL} /pv-disks/${UUID} ext4 defaults,noatime,discard,nobarrier  0 0
EOF
mount -a
set +x
}

yum install -y nvme-cli mdadm
build_raid
mountpoint /nvme/disk/ || systemctl stop kubelet

--==MYBOUNDARY==--
```

<div id="install-storageclass-via-helm">
  ### Установка StorageClass через Helm
</div>

Если требуется StorageClass, рекомендуется устанавливать эти зависимости clickhouse-operator через предоставленный Helm-чарт отдельно от фактического создания CR clickhousecluster, чтобы при создании нескольких CR зависимости не были привязаны к какому-либо кластеру и не удалялись при его удалении. **Этот шаг нужно выполнять только в том случае, если у вас нет пользовательского или уже существующего CR StorageClass**, который вы планируете использовать для clickhouser-server и clickhouse-keeper.

```bash
# обновите ECR_HOST при необходимости
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
CHART_VERSION=<<CR_HELM_TAG>>

helm install clickhouse-prerequisites \
    oci://$ECR_HOST/helm/onprem-clickhouse-cluster \
    --version=$CHART_VERSION \
    -n default \
    --set-json="storageClass.create=true" \
    --set-json="createCluster=false" \
    --set-json="serviceAccount.create=false"
```

<div id="install-operator-via-helm">
  ### Установка оператора с помощью Helm
</div>

При необходимости обновите версию, хост ECR и зоны доступности, определённые при создании VPC.

```bash expandable
# обновите ECR_HOST при необходимости
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com

# следует использовать версию Helm-чарта оператора, а не самого оператора (например, <<OPERATOR_TAG>>, а не main.<<OPERATOR_TAG>>)
OPERATOR_VERSION=<<OPERATOR_TAG>>

# укажите зоны доступности в соответствии с подсетями VPC
AZ_LIST='["us-west-2a","us-west-2b","us-west-2c"]'

helm install clickhouse-operator \
   oci://$ECR_HOST/helm/clickhouse-operator-helm \
   --version=$OPERATOR_VERSION \
   --create-namespace \
   -n clickhouse-operator-system \
   --set-json="image.repository=\"$ECR_HOST/clickhouse-operator\"" \
   --set-json='cilium.enabled=false' \
   --set-json='idleScalerEnabled=false' \
   --set-json='webhooks.enabled=false' \
   --set-json='operator.debug=true' \
   --set-json='operator.metricsScraper.enabled=false' \
   --set-json="operator.availabilityZones=$AZ_LIST" \
   --set-json='operator.featureFlags.backupOnASeparatePod=true' \
   --set-json='operator.featureFlags.serverCMEKEnabled=true'
```

<div id="install-aws-ebs-csi-driver">
  ### Установите aws-ebs-csi-driver
</div>

Требуется роль IAM со следующими параметрами:

* Используйте управляемую политику `arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy`
* Для политики доверия рекомендуется использовать sts:AssumeRoleWithWebIdentity с OIDC-провайдером кластера EKS ([пример](#example-trust-policy))
* Выбранное имя роли должно совпадать с аннотацией сервисной учётной записи, под которой запускается aws-ebs-csi-driver
  * Пример имени: `ClickHouse_EksEbsCsiDriverRole`

Следуйте руководству по [установке с помощью Helm](https://github.com/kubernetes-sigs/aws-ebs-csi-driver/blob/master/docs/install.md#helm), добавив дополнительные значения, чтобы привязать роль IAM к сервисной учётной записи:

```bash
# обновите имя роли при необходимости
AWS_EBS_CSI_DRIVER_IAM_ROLE_ARN=arn:aws:iam::0000000000:role/ClickHouse_EksEbsCsiDriverRole
```

<div id="naming-your-clickhouse-cluster">
  ### Именование кластера ClickHouse
</div>

Для каждого кластера ClickHouse, подготавливаемого к развертыванию, выберите **уникальное имя кластера** в пределах целевого кластера EKS. Это имя будет использоваться в различных ресурсах AWS и Kubernetes и служить для однозначной идентификации кластера.

1. Соглашение об именовании должно иметь вид `$DESCRIPTOR-$LETTERS-$ORDINAL`
   1. $DESCRIPTOR - некоторое описательное имя кластера, состоящее только из букв
   2. $LETTERS - зарезервировано; выберите любые две буквы, для простоты подойдет `xx`
   3. $ORDINAL - возрастающий порядковый номер для кластеров с одинаковым дескриптором, начиная с `01`
2. Пример имени: `default-xx-01`

<div id="clickhousecluster-cr">
  ### Clickhousecluster CR
</div>

Обратите внимание: значения ниже следует проверить и скорректировать для промышленной среды (например, ресурсы, флаги возможностей, конфигурации сервера, ...). Перед тем как задавать `CLUSTER_NAME`, см. [раздел об именовании](#naming-your-clickhouse-cluster).
Сгенерируйте хеш пароля для указанного `$PASSWORD` с помощью следующей команды (os x), затем передайте его в параметр `account.hashedPassword` Helm-чарта:

```bash expandable
# это будет пароль пользователя `default`
PASSWORD='My super secret p@$$w0rd'
HASHED_PASSWORD=`echo -n $PASSWORD | shasum -a 256 | awk '{printf $1}' | base64`

# при необходимости обновите значения ниже,
# ecr host должен соответствовать вашей учётной записи
# s3 bucket должен быть тем, что был создан ранее
CLUSTER_NAME=default-xx-01
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
SA_IAM_ROLE_ARN=arn:aws:iam::0000000000:role/CH-S3-${CLUSTER_NAME}-uw2-00-Role
S3_BUCKET_NAME=my-clickhouse-data

# s3 key prefix может принимать любое значение UUID, но должен быть уникальным для всех кластеров, хранящих данные в указанном выше бакете
S3_KEY_PREFIX=ch-s3-$(uuidgen | tr '[:upper:]' '[:lower:]')

# эти значения должны совпадать со значением метки clickhouseGroup, добавленной к группе узлов
SERVER_NG_GROUP=server-arm64
KEEPER_NG_GROUP=keeper-arm64

# эти значения зависят от выбранных размеров инстансов
# при задании значений CPU и MEMORY обязательно учитывайте требования daemon set
SERVER_CPU=64
SERVER_MEMORY=256Gi
KEEPER_CPU=4
KEEPER_MEMORY=16Gi

CHART_VERSION=<<CR_HELM_TAG>>

# bytesPerGiRAM — коэффициент масштабирования для автоматического вычисления размера дискового кэша.
# Как правило, размер кэша следует устанавливать равным 80–90% доступного объёма SSD-кэша.
# При задании bytesPerGiRAM в Helm-чарте во время запуска пода применяется следующая формула:
#
# CONFIG_DISK_CACHE_SIZE = bytesPerGiRAM * pod_memory_limit
#
# Например:
# bytesPerGiRAM = 11.3Gi
# pod_memory_limit = 250Gi
# CONFIG_DISK_CACHE_SIZE = 11.3 * 250 = 2825Gi
CACHE_BYTES_PER_GI_RAM=11Gi

helm install $CLUSTER_NAME \    oci://$ECR_HOST/helm/onprem-clickhouse-cluster \
    --version=$CHART_VERSION \
    -n ns-$CLUSTER_NAME \
    --create-namespace \
    --set-json="account.hashedPassword=\"$HASHED_PASSWORD\"" \
    --set-json="server.image.repository=\"$ECR_HOST/clickhouse-server\"" \
    --set-json="server.storage.s3.bucketName=\"$S3_BUCKET_NAME\"" \
    --set-json="server.storage.s3.keyPrefix=\"$S3_KEY_PREFIX\"" \
    --set-json='server.arm64=true' \
    --set-json="server.image.tag=\"<<SERVER_TAG>>\"" \
    --set-json="server.podPolicy.nodeSelector.clickhouseGroup=\"$SERVER_NG_GROUP\"" \
    --set-json="keeper.image.repository=\"$ECR_HOST/clickhouse-keeper\"" \
    --set-json='keeper.arm64=true' \
    --set-json="keeper.image.tag=\"<<KEEPER_TAG>>\"" \
    --set-json="keeper.podPolicy.nodeSelector.clickhouseGroup=\"$KEEPER_NG_GROUP\"" \
    --set-json="serviceAccount.annotations={\"eks.amazonaws.com/role-arn\":\"$SA_IAM_ROLE_ARN\"}" \
    --set-json='server.tolerations=[{"effect":"NoSchedule","key":"clickhouse.com/do-not-schedule","operator":"Exists"}]' \
    --set-json='keeper.tolerations=[{"effect":"NoSchedule","key":"clickhouse.com/do-not-schedule","operator":"Exists"}]' \
    --set-json="server.ssdCacheConfiguration.bytesPerGiRAM=\"$CACHE_BYTES_PER_GI_RAM\"" \
    --set-json="server.podPolicy.resources.limits.cpu=\"$SERVER_CPU\"" \
    --set-json="server.podPolicy.resources.limits.memory=\"$SERVER_MEMORY\"" \
    --set-json="server.podPolicy.resources.requests.cpu=\"$SERVER_CPU\"" \
    --set-json="server.podPolicy.resources.requests.memory=\"$SERVER_MEMORY\"" \
    --set-json="keeper.podPolicy.resources.limits.cpu=\"$KEEPER_CPU\"" \
    --set-json="keeper.podPolicy.resources.limits.memory=\"$KEEPER_MEMORY\"" \
    --set-json="keeper.podPolicy.resources.requests.cpu=\"$KEEPER_CPU\"" \
    --set-json="keeper.podPolicy.resources.requests.memory=\"$KEEPER_MEMORY\""
```

<div id="hydra-setup">
  ## Настройка Hydra
</div>

Суть в том, чтобы создать несколько групп узлов внутри одного кластера ClickHouse. У каждой такой группы будет своё количество узлов (с разным объёмом памяти) и отдельная конечная точка. При этом у каждой группы узлов будет один экземпляр Keeper и один набор данных / папка в общем S3 бакете.

<div id="provisioning-hydra-children-instances">
  ### Создание дочерних инстансов Hydra
</div>

<div id="prerequisites">
  ##### Необходимые условия
</div>

Оператор должен быть [установлен](#install-operator-via-helm) с включенной возможностью Hydra; для этого задайте (по умолчанию — false):

```bash
--set operator.featureFlags.privateHydraEnabled="true"
```

<div id="setup">
  ##### Настройка
</div>

*Прежде чем создавать дочерние инстансы, необходимо выбрать существующий и/или создать новый родительский кластер ClickHouse, поэтому для дочерних инстансов нужно заранее знать **имя** и **пространство имен** родителя.*

Чтобы создать новый дочерний сервис, следуйте [тем же инструкциям](#clickhousecluster-cr) по созданию сервиса и просто добавьте новые значения Helm при создании пользовательского ресурса (CR) `ClickHouseCluster`:

```bash
--set-json='parentCluster.name="c-${PARENT_NAME}'"'
--set-json='parentCluster.namespace="ns-'${PARENT_NAME}'"'
```

**PARENT&#95;NAME** — имя существующего или нового родительского кластера ClickHouse.

При необходимости, если вы хотите, чтобы новый дочерний кластер был только для чтения (по умолчанию false), можно добавить:

```bash
--set-json='isReadonly=true'
```

<div id="limitations">
  ### Ограничения
</div>

1. Нельзя создать дочерние инстансы, если родительский инстанс остановлен, завершён или переведён в режим простоя.
2. Если вы хотите удалить родительский кластер, сначала нужно удалить дочерние инстансы.

<div id="install-validation">
  ## Проверка установки
</div>

<div id="preflight-checks">
  ### Предварительные проверки
</div>

При желании можно выполнить предварительную проверку с помощью [Troubleshoot](https://troubleshoot.sh/) — плагина Kubernetes для диагностики кластера.

Чтобы установить необходимые плагины, можно использовать Krew:

```console
kubectl krew install preflight
```

или обратитесь к [документации](https://troubleshoot.sh/docs/) Troubleshoot, чтобы ознакомиться с другими вариантами установки.

ClickHouse предоставляет Helm-чарт (`helm/preflight-check`), который можно скопировать в ваш ECR и локально отрендерить, чтобы сгенерировать спецификацию preflight, которая затем передаётся в `kubectl preflight`.

<div id="copying-the-preflight-check-helm-chart">
  ##### Копирование Helm-чарта предварительной проверки
</div>

Добавьте чарт предварительной проверки на [этап копирования ECR](#copy-ecr-artifacts):

```bash
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/preflight-check:<<PREFLIGHT_CHART_TAG>> docker://$TARGET_ECR_REPO/helm/preflight-check:<<PREFLIGHT_CHART_TAG>>
```

<div id="running-the-preflight-checks">
  ##### Запуск предварительных проверок
</div>

Используйте `helm template`, чтобы сгенерировать спецификацию предварительных проверок, а затем сразу передайте вывод в `kubectl preflight`. Установите `CLUSTER_NAME` в имя кластера ClickHouse, который нужно проверить (см. [Именование кластера ClickHouse](#naming-your-clickhouse-cluster)):

```bash
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com
CHART_VERSION=<<PREFLIGHT_CHART_TAG>>
CLUSTER_NAME=default-xx-01

helm template clickhouse-preflight \
    oci://$ECR_HOST/helm/preflight-check \
    --version=$CHART_VERSION \
    --set preflight.clickhouseClusterName=$CLUSTER_NAME | \
kubectl preflight -
```

Это позволяет проверить, соблюдены ли требования для запуска ClickHouse Operator и развертывания кластера ClickHouse. Проверяется наличие
необходимых меток узлов, правильность настройки класса хранения и т. д.

В выводе отображаются различные предварительные проверки и их статус:
![Пример предварительных проверок](/products/clickhouse-private/images/preflight-example.png)

Вы можете прокрутить вывод и убедиться, что каждая проверка пройдена успешно. Если какая-либо проверка завершается ошибкой, это указывает на (потенциальную) проблему в конфигурации, которая может
помешать успешной работе кластера ClickHouse. Проверки также содержат рекомендации по устранению проблемы.

Чтобы выполнить проверку для класса хранения, отличного от используемого по умолчанию (`gp3-encrypted`), переопределите его с помощью дополнительного флага `--set`:

```bash
    --set preflight.checks.prerequisites.storageClassName=<your-storage-class>
```

<div id="required-permissions">
  ##### Требуемые разрешения
</div>

Пользователь или сервисная учетная запись, выполняющие `kubectl preflight`, должны иметь доступ на чтение ресурсов уровня кластера и уровня пространства имен. Как минимум требуются следующие права доступа:

| Область                                                    | Ресурсы                                                                                   |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| На уровне всего кластера                                   | `nodes`, `namespaces`, `persistentvolumes`, `storageclasses`, `customresourcedefinitions` |
| Пространство имен оператора (`clickhouse-operator-system`) | `deployments`, `replicasets`, `pods`, `services`, `configmaps`, `events`                  |
| Пространство имен кластера (`ns-<cluster-name>`)           | `statefulsets`, `pods`, `persistentvolumeclaims`, `services`, `configmaps`, `events`      |

На практике достаточно субъекта со встроенной РольКластера `view` и доступом `view` к соответствующим пространствам имен. Также подойдет привязка cluster-admin — ее проще настроить для разовых запусков проверки.

<div id="port-forward-the-clickhouse-service-to-your-local-machine">
  ### Выполните проброс порта сервиса ClickHouse на локальную машину
</div>

Чтобы перенаправить трафик с локальной машины на сервис c-default-xx-01-server-any, выполните:

```bash
kubectl port-forward svc/c-default-xx-01-server-any 9000:9000 -n ns-default-xx-01
```

Это перенаправит порт `9000` сервиса на порт `9000` вашего локального компьютера. Теперь вы можете получить доступ к HTTP-интерфейсу ClickHouse по адресу `http://localhost:9000`.

<div id="access-clickhouse-and-run-query">
  ### Доступ к ClickHouse и выполнение запроса
</div>

После перенаправления порта вы можете подключиться к ClickHouse локально с помощью такого инструмента, как clickhouse-client.

```bash
clickhouse client --host localhost --port 9000 --password $PASSWORD
```

и выполните простой запрос:

```sql
clickhouse-cloud :) select 1;
```

Вы должны увидеть примерно такой результат:

```text
SELECT 1
Query id: 825591bf-a8e5-4995-ac9f-afb864854ba2
   ┌─1─┐
1. │ 1  │
   └───┘
1 строка в Set. Затрачено: 0.001 сек.
```
