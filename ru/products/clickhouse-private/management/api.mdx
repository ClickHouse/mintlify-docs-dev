<div id="introduction">
  ### Введение
</div>

<div id="starting-with-the-clickhouse-private-api">
  #### Начало работы с ClickHouse Private API
</div>

ClickHouse Private API поддерживает типовые операции по управлению вашим кластером ClickHouse, такие как создание резервных копий и вертикальное масштабирование.

Это отдельный необязательный компонент, который можно добавить в вашу среду, чтобы упростить управление.

<div id="installation">
  #### Установка
</div>

Private API ClickHouse поставляется в виде Docker-образа и Helm-чарта, которые необходимо скопировать в ваш приватный репозиторий ECR и установить в кластере EKS.

<div id="prerequisites">
  ##### Предварительные требования
</div>

* Должен быть установлен ClickHouse Operator (см. [Установка ClickHouse Operator через Helm](/ru/products/clickhouse-private/deployment/aws#install-operator-via-helm))
* Должен быть развернут как минимум один кластер ClickHouse (см. [ClickHouseCluster CR](/ru/products/clickhouse-private/deployment/aws#clickhousecluster-cr))
* Доступ к приватному репозиторию ECR ClickHouse
* В вашей учетной записи AWS должен быть создан целевой репозиторий ECR:
  * `airgap-management`
  * `helm/airgap-management`

<div id="copy-ecr-artifacts-for-private-api">
  ##### Копирование артефактов ECR для Private API
</div>

**Мы настоятельно рекомендуем использовать [skopeo](https://github.com/containers/skopeo) для копирования образов**, так как он сохраняет все архитектуры в Docker-образах. Обязательно укажите ниже ваш регион ECR и хост в `TARGET_REGION` и `TARGET_ECR_REPO`.

```bash
SOURCE_REGION=us-east-1
SOURCE_ECR_REPO=349290138304.dkr.ecr.$SOURCE_REGION.amazonaws.com

TARGET_REGION=us-west-2
TARGET_ECR_REPO=0000000000.dkr.ecr.$TARGET_REGION.amazonaws.com

# войти в наш ECR
aws ecr get-login-password --region $SOURCE_REGION | skopeo login --username AWS --password-stdin $SOURCE_ECR_REPO

# войти в целевой репозиторий AWS
aws ecr get-login-password --region $TARGET_REGION | skopeo login --username AWS --password-stdin $TARGET_ECR_REPO

# скопировать каждый образ в целевой ECR, не забудьте указать флаг --all
skopeo copy --all docker://$SOURCE_ECR_REPO/airgap-management:<<API_TAG>> docker://$TARGET_ECR_REPO/airgap-management:<<API_TAG>>
skopeo copy --all docker://$SOURCE_ECR_REPO/helm/airgap-management:<<API_HELM_TAG>> docker://$TARGET_ECR_REPO/helm/airgap-management:<<API_HELM_TAG>>
```

<div id="install-private-api-via-helm">
  ##### Установка Private API с помощью Helm
</div>

Private API следует устанавливать в отдельном пространстве имен. При необходимости обновите хост ECR, теги версий и параметры аутентификации.

```bash
# при необходимости обновите ECR_HOST
ECR_HOST=0000000000.dkr.ecr.us-west-2.amazonaws.com

# укажите версию Helm-чарта API
API_HELM_VERSION=<<API_HELM_TAG>>

# задайте тег образа API
API_IMAGE_TAG=<<API_TAG>>

helm install clickhouse-private-api \
   oci://$ECR_HOST/helm/airgap-management \
   --version=$API_HELM_VERSION \
   --create-namespace \
   -n clickhouse-private-api \
   --set-json="image.repository=\"$ECR_HOST/airgap-management\"" \
   --set-json="image.tag=\"$API_IMAGE_TAG\""
```

**Примечание об аутентификации:**

* По умолчанию базовая аутентификация отключена. В производственной среде ее можно включить, задав `api.basicAuth.enabled=true` и указав безопасные учетные данные.
* Имя пользователя и пароль следует хранить в защищенном месте и регулярно менять в соответствии с политиками безопасности вашей организации.

<div id="verify-installation">
  ##### Проверка установки
</div>

Убедитесь, что под Private API запущен:

```bash
kubectl get pods -n clickhouse-private-api
```

Вы должны увидеть примерно такой вывод:

```
NAME                                    READY   STATUS    RESTARTS   AGE
clickhouse-private-api-xxxxxxxxxx-xxxxx   1/1     Running   0          1m
```

Убедитесь, что API доступен, выполнив проброс порта сервиса:

```bash
kubectl port-forward svc/clickhouse-private-api-airgap-management 8080:8080 -n clickhouse-private-api
```

Проверьте конечную точку проверки работоспособности API:

```bash
curl http://localhost:8080/readiness
```

Если включена аутентификация, укажите учетные данные:

```bash
curl -u admin:YOUR_SECURE_PASSWORD_HERE http://localhost:8080/readiness
```

<div id="configuration-options">
  ##### Параметры конфигурации
</div>

Следующие ключевые параметры конфигурации доступны через значения Helm:

* `image.repository`: репозиторий ECR для образа Private API
* `image.tag`: тег образа для развертывания
* `api.port`: порт, на котором API прослушивает соединения (по умолчанию: 8080)
* `api.basicAuth.enabled`: включает базовую HTTP-аутентификацию (по умолчанию: false)
* `api.basicAuth.username`: имя пользователя для базовой аутентификации (по умолчанию: &quot;admin&quot;)
* `api.basicAuth.password`: пароль для базовой аутентификации (по умолчанию: &quot;changeme&quot;)
* `serviceAccount.enabled`: создать сервисную учетную запись для API (по умолчанию: true)
* `serviceAccount.annotations`: аннотации для сервисной учетной записи (например, для IRSA)

Полный список параметров конфигурации см. в `README.md` Helm-чарта.

<div id="tutorial-managing-backups-through-the-api">
  #### Руководство: Управление резервными копиями через API
</div>

ClickHouse Private API предоставляет средства, упрощающие управление резервными копиями. REST-ресурс `api/v1/backups` доступен для работы с
резервными копиями развернутого кластера ClickHouse.

В этом руководстве мы будем исходить из того, что API доступен по адресу `http://localhost:8080/`, например через проброс порта Kubernetes-пода. Для взаимодействия с API и выполнения HTTP-запросов мы будем использовать [curl](https://curl.se/). Также мы будем считать, что развернут кластер ClickHouse с именем default-xx-01 (подробнее о развертывании кластера ClickHouse см. в [руководстве по настройке](/ru/products/clickhouse-private/deployment/aws)).

Сначала создадим резервную копию. Создайте полную резервную копию следующим образом:

backup.json

```json
{
    "incremental": false
}
```

Команда cURL

```sh
curl -X POST "http://localhost:8080/api/v1/backups?instance_id=default-xx-01" \
    -H "Content-Type: application/json" \
    --data-binary "@backup.json"
```

Чтобы указать кластер ClickHouse, для которого нужно создать резервную копию, используется параметр запроса `instance_id`. При этом используется имя кластера ClickHouse, заданное во время развертывания.

Это создаст полную резервную копию, а не инкрементную, как указано в поле `incremental` в теле запроса. Кроме того, `backupObject` можно использовать, чтобы указать, какие таблицы или базы данных нужно включить в резервную копию. В данном случае используется `type` Common, то есть все таблицы и базы данных.

Ответ будет содержать информацию о созданной резервной копии, включая UUID, который можно использовать для ссылки на эту резервную копию.

На уровне API будет создан объект `Backup` в пространстве имен кластера ClickHouse.
ClickHouse Operator будет отслеживать `Backup` в пространстве имен кластера ClickHouse, и если будет создан новый объект `Backup`, оператор выполнит соответствующий SQL-оператор `BACKUP` на кластере и будет отслеживать его состояние (используя системные таблицы).

Этот UUID резервной копии можно использовать для отслеживания состояния резервной копии через API:

```sh
curl "http://localhost:8080/api/v1/backups/{uuid}?instance_id=default-xx-01
```

Это вернёт объект резервной копии, а поле `status` можно использовать для получения информации о ней. Если создание резервной копии завершилось успешно, поле `state` будет иметь значение `Ready`.

Кроме того, вы можете отслеживать все созданные резервные копии следующим образом:

```sh
curl "http://localhost:8080/api/v1/backups?instance_id=default-xx-01"
```

<div id="tutorial-vertically-scaling-clickhouse-clusters-through-the-api">
  #### Руководство: Вертикальное масштабирование кластеров ClickHouse через API
</div>

Private API ClickHouse поддерживает вертикальное масштабирование кластера ClickHouse за счёт изменения ресурсов CPU и памяти. REST-ресурс `api/v1/instances/{instance_id}/scale` позволяет изменить выделение ресурсов для развернутого кластера ClickHouse.

В этом руководстве мы будем исходить из того, что API доступен по адресу `http://localhost:8080/`, например через проброс порта Kubernetes-пода. Для взаимодействия с API и отправки HTTP-запросов мы будем использовать [curl](https://curl.se/). Мы также будем считать, что уже развернут кластер ClickHouse с именем default-xx-01 (подробные сведения о развертывании кластера ClickHouse см. в [руководстве по настройке](/ru/products/clickhouse-private/deployment/aws)).

Давайте масштабируем кластер, изменив его ресурсы. Создайте запрос на масштабирование следующим образом:

scale.json

```json
{
  "vertical": {
    "resources": {
        "cpu": "4",
        "memory": "16Gi"
    }
  }
}
```

Команда curl

```sh
curl -X POST "http://localhost:8080/api/v1/instances/default-xx-01/scale" \
    -H "Content-Type: application/json" \
    --data-binary "@scale.json"
```

Чтобы указать ClickHouse cluster, который нужно масштабировать, используется параметр пути `instance_id`. Для этого используется имя ClickHouse cluster, заданное при развертывании.

Поле `resources` задает выделение CPU и памяти для кластера. И CPU, и память указываются в формате Kubernetes resource quantity (например, &quot;4&quot; для 4 ядер CPU, &quot;16Gi&quot; для 16 гибибайт памяти).

**Важно**: API требует соблюдения соотношения CPU к памяти 1:4 (1 ядро CPU на 4 GiB памяти) с допуском 5%. Если указать только один тип ресурса, API автоматически вычислит второй, чтобы сохранить это соотношение. Например, если указать только `"memory": "16Gi"`, CPU автоматически будет установлен в 4 ядра.

ClickHouse хорошо масштабируется при добавлении ресурсов, и обычно рекомендуется сначала вертикально масштабировать ClickHouse, прежде чем рассматривать горизонтальное масштабирование. ClickHouse будет использовать все доступные ядра для повышения производительности запросов.

На уровне реализации API обновляет `ServerPodPolicy` пользовательского ресурса `ClickhouseCluster` в Kubernetes. ClickHouse Operator обнаружит это изменение и запустит rolling restart StatefulSet, управляющих ClickHouse server, с новым выделением ресурсов.

**Важно**: В отличие от ClickHouse Cloud, в ClickHouse Private возможность вертикального масштабирования не использует [масштабирование Make Before Break (MBB)](/ru/products/cloud/features/autoscaling/overview#how-scaling-works-in-clickhouse-cloud). Это означает, что вертикальное масштабирование потенциально может вызвать перебои в работе сервиса, поскольку к StatefulSet, управляющим ClickHouse server, применяется rolling restart.

<div id="tutorial-resetting-the-main-clickhouse-user-password">
  #### Руководство: сброс пароля основного пользователя ClickHouse.
</div>

Private API ClickHouse поддерживает сброс пароля для пользователей кластера ClickHouse. Конечная точка `api/v1/instances/{instance_id}/reset-user-password` доступна для обновления учетных данных пользователя в развернутом кластере ClickHouse.

В этом руководстве мы будем исходить из того, что вы можете обращаться к API по адресу `http://localhost:8080/`, например с помощью проброса порта Kubernetes-пода. Для взаимодействия с API и выполнения HTTP-запросов мы будем использовать [curl](https://curl.se/). Мы также будем исходить из того, что был развернут кластер ClickHouse с именем default-xx-01 (подробные сведения о развертывании кластера ClickHouse см. в [руководстве по настройке](/ru/products/clickhouse-private/deployment/aws)).

**Важно**: Сброс пароля нельзя выполнять для дочерних экземпляров Hydra. Если вам нужно сбросить пароль для дочернего экземпляра Hydra, вместо этого необходимо выполнить сброс для родительского экземпляра.

Перед сбросом пароля необходимо сгенерировать хеш пароля. API требует, чтобы пароль был хеширован с использованием SHA-256 (или другой поддерживаемой хеш-функции), а затем закодирован в base64. Сгенерируйте хеш пароля следующим образом:

```sh
# это будет новый пароль для пользователя
PASSWORD='My super secret p@$$w0rd'
HASHED_PASSWORD=$(echo -n $PASSWORD | shasum -a 256 | awk '{printf $1}' | base64)
```

Теперь создайте запрос на сброс пароля. Тело запроса должно содержать пароль в виде хеша:

password&#95;reset.json

```json
{
  "user_hashed_password": "<base64-encoded-sha256-hash>",
  "hashing_function": "sha256",
  "username": "default"
}
```

Поля:

* `user_hashed_password` (обязательно): хеш нового пароля в кодировке base64
* `hashing_function` (необязательно): используемый алгоритм хеширования. Если не указано, по умолчанию используется `"sha256"`
* `username` (необязательно): имя пользователя, для которого нужно сбросить пароль. Если не указано, по умолчанию используется `"default"`

Команда cURL:

```sh
curl -X POST "http://localhost:8080/api/v1/instances/default-xx-01/reset-user-password" \
    -H "Content-Type: application/json" \
    --data-binary "@password_reset.json"
```

Чтобы указать кластер ClickHouse, для которого нужно сбросить пароль, используется параметр пути `instance_id`. В качестве его значения используется имя кластера ClickHouse, заданное при развертывании.

Если запрос выполнен успешно, вы получите ответ:

```json
{
  "message": "User password reset successfully"
}
```

На уровне Kubernetes API обновляет поле `CustomerAccount` в пользовательском ресурсе `ClickhouseCluster`. ClickHouse Operator обнаружит это изменение и соответствующим образом обновит учетные данные пользователя в кластере ClickHouse.

**Примечание**: Сброс пароля вступит в силу после того, как оператор обработает это изменение. Проверить, что пароль обновился, можно, попробовав подключиться к кластеру с новым паролем.

<div id="how-to-check-the-current-state-of-a-clickhouse-cluster-and-monitor-state-transitions">
  #### Как проверить текущее состояние кластера ClickHouse и отслеживать переходы состояний
</div>

Private API ClickHouse предоставляет конечную точку `http://{api_base_url}/api/v1/instances/{instance_id}/status` для проверки текущего состояния указанного кластера ClickHouse.

Конечная точка статуса возвращает JSON со следующими полями:

* `state`: текущее состояние кластера ClickHouse.
* `previousState`: состояние, из которого кластер ClickHouse перешел в текущее состояние.
* `message`: сообщение, связанное с переходом состояния. Оно содержит сведения о том, почему кластер перешел в это состояние.
* `stateProvidedBy`: процесс, который инициировал переход состояния.

Эта конечная точка может быть полезна в нескольких случаях. Например:

* Вы запустили через API операцию вертикального масштабирования и хотите узнать, завершил ли оператор масштабирование.
* Вы сбросили пароль пользователя и хотите узнать, применил ли API эти изменения ко всему кластеру.

<div id="how-to-incremental-backups">
  #### Практическое руководство: Инкрементные резервные копии
</div>

Инкрементные резервные копии можно использовать, чтобы сохранять только данные, изменившиеся с момента последней резервной копии. Это уменьшает общий объем хранилища, необходимый для

Инкрементные резервные копии всегда создаются в виде цепочки резервных копий, где каждая резервная копия ссылается на предыдущую, а отправной точкой служит полная резервная копия.

Их можно создать следующим образом, если у вас уже есть ранее созданная резервная копия:

```json
{
    "incremental": true,
    "baseBackupUuid": <uuid of previous backup>
}
```

```sh
curl -X POST "http://localhost:8080/api/v1/backups?instance_id=default-xx-01" \
    -H "Content-Type: application/json" \
    --data-binary "@backup.json"
```

Чтобы найти последнюю успешную резервную копию и определить UUID, API List backups (`http://localhost:8080/api/v1/backups`) поддерживает параметры запроса для поиска последней успешной резервной копии: `http://localhost:8080/api/v1/backups?instance_id=default-xx-01&status__state__eq=Ready&sort=status__effictiveFinishTime&limit=1 | jq -r '.[].id'`.

<div id="how-to-scheduling-backups">
  #### Практическое руководство: Планирование резервного копирования
</div>

Настроить резервное копирование по расписанию с помощью Kubernetes CronJobs очень просто:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: clickhouse-daily-backup
  namespace: clickhouse-private-api
spec:
  schedule: "0 2 * * *"  # Запускать ежедневно в 2:00
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: curlimages/curl:latest
            command:
            - /bin/sh
            - -c
            - |
              curl -X POST "http://clickhouse-private-api-airgap-management:8080/api/v1/backups?instance_id=default-xx-01" \
                -H "Content-Type: application/json" \
                -d '{
                  "incremental": false
                }'
          restartPolicy: OnFailure
```

Указанный выше CronJob запускает полное резервное копирование ежедневно в 2:00. Предполагается, что Private API доступен по адресу `http://clickhouse-private-api-airgap-management:8080`.

<div id="how-to-backing-up-only-specific-tables-or-databases">
  #### Практическое руководство: Резервное копирование только определённых таблиц или баз данных
</div>

Можно указать, какие именно таблицы и базы данных нужно включить в резервную копию. Это задаётся с помощью полей `databases` и `tables`
в теле запроса.

Обратите внимание, что для поля `tables` требуется указывать полные имена таблиц (то есть `db.table`).

Чтобы создать резервную копию только для определённых баз данных и таблиц, используйте следующий запрос:

```json
{
    "incremental": false,
    "databases": ["mydb"],
    "tables": ["mydb2.table"]
}
```

```sh
curl -X POST "http://localhost:8080/api/v1/backups?instance_id=default-xx-01" \
    -H "Content-Type: application/json" \
    --data-binary "@backup.json"
```

<div id="how-to-restoring-backups">
  #### Инструкция: Восстановление резервных копий
</div>

Для восстановления резервных копий рекомендуется развернуть новый кластер ClickHouse (следуя инструкциям по [созданию ресурса ClickHouseCluster](/ru/products/clickhouse-private/deployment/aws#clickhousecluster-cr)) и выполнять восстановление в него, чтобы избежать перегрузки исходного кластера.

API предоставляет конечную точку `api/v1/backups/<uuid>/restore?instance_id=default-xx-01&target_instance_id=default-xx-02`, которая запускает восстановление указанной резервной копии на целевом экземпляре. При этом на целевом экземпляре будет выполнен `RESTORE ALL` из этой резервной копии.

В целях безопасности этот API не допускает восстановление на том же экземпляре.

Кроме того, резервную копию можно восстановить вручную, что позволяет точнее управлять тем, что именно восстанавливать. Например, для базы данных `example` можно выполнить следующий SQL-оператор:

```sql
RESTORE DATABASE example
AS example_restored
FROM S3('https://<bucket_name>.s3.amazonaws.com/backups/<uuid>')
```

Это восстановит базу данных `example` из резервной копии с указанным UUID под новым именем `example_restored`.

<div id="how-to-manage-the-lifecycle-of-backups-on-s3">
  #### How-To: Управление жизненным циклом резервных копий в S3
</div>

При управлении жизненным циклом резервных копий нужно учитывать несколько моментов:

* Как долго вы хотите хранить резервные копии? Например, нужно ли сохранять исторические резервные копии для соблюдения требований compliance? Сколько вы готовы платить за хранение?
* Если вы создали инкрементные резервные копии, необходимо обеспечить доступность всей цепочки резервных копий.

В общем случае для управления жизненным циклом в S3 есть два подхода:

* Использовать правила жизненного цикла S3
* Удалять резервные копии вручную, например с помощью cronjob.

Ниже приведен пример политики жизненного цикла для S3:

```json
{
  "Rules": [
    {
      "ID": "ClickHouseBackupLifecycle",
      "Prefix": "backups/",
      "Status": "Enabled",
      "Transitions": [
        { "Days": 7, "StorageClass": "STANDARD_IA" },
        { "Days": 30, "StorageClass": "GLACIER_IR" }
      ],
      "Expiration": { "Days": 90 }
    }
  ]
}
```

Эта политика переводит все резервные копии старше 7 дней на более низкий уровень хранения S3 (Intelligent Archive), а через 30 дней — в Glacier. Через 90 дней резервные копии будут удалены.

Политики жизненного цикла S3 не могут отслеживать резервные копии, входящие в цепочку резервного копирования. Например, если бы в приведённом выше примере мы удаляли резервные копии через 7 дней и делали полную
резервную копию только каждые 14 дней, то нарушили бы цепочку резервного копирования, а это привело бы к неработоспособности резервных копий.

Поэтому мы рекомендуем внимательно подходить к выбору способа управления жизненным циклом резервных копий и регулярно проверять, можно ли их восстановить.

<div id="how-to-understanding-resource-quantity-formats">
  #### How-To: Форматы значений ресурсов
</div>

API принимает значения ресурсов Kubernetes для CPU и памяти в следующих форматах:

**Значения CPU:**

* Целые значения: `"4"` (4 ядра CPU)
* Десятичные значения: `"2.5"` (2,5 ядра CPU)
* Миллиядра: `"500m"` (0,5 ядра CPU)

**Значения памяти:**

* Двоичные единицы: `"16Gi"` (16 гибибайт), `"4096Mi"` (4096 мебибайт)
* Десятичные единицы: `"16G"` (16 гигабайт), `"16000M"` (16000 мегабайт)

Обратите внимание: для памяти рекомендуется использовать двоичные единицы (Ki, Mi, Gi), чтобы соблюдать соглашения Kubernetes.
